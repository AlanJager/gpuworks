# 部署模型与解释调度结果

**适用场景**：把一个模型部署成可调用的推理服务，并看懂调度器为什么这样放置。

**前置条件**：至少一个在线节点（见[接入节点](connect-nodes.md)）；模型已在目标节点 `present`，或可以下载/同步到目标节点（见[下载、缓存和节点间同步模型](download-and-sync-models.md)）；需要的运行镜像能在目标节点拉取（离线环境见[离线环境部署](deploy-offline.md)）。

## 步骤

1. **选模型和运行方案。** 在部署页选择已登记的模型，或搜索内置目录中的具体模型，再选该模型的一条运行方案。模型检索与方案检索是分开的，同名方案以来源和名称共同区分。目录里没有你的组合时，可以用自己的镜像和配置。模型没有声明任何推理接口（对话、文本补全、向量等）、所选模板配方也没有声明时（从模板部署会把配方的接口写给接口为空的模型，包括接口列表为 `[]` 的：登记时认不出任务的模型、被人清空接口的模型都一样；已经有接口的模型保持原样，不被配方改写），表单顶部会提示“这个部署不会暴露任何推理接口”：这样的部署在试验场里不出现，也无法开启健康检查；先到「模型」页给它设置接口再部署。
2. **选芯片厂商、副本形状和候选节点。** 选好厂商后先选副本形状：单机、多机或 PD 分离。单机下候选节点默认是“自动”：每个副本启动时在候选节点里挑一台放得下的，扩容和重建都会重新挑，页面显示当前草稿有多少台候选节点，并按服务端试算回显首个副本会落在哪台、用哪些 GPU；“自动”下还可以在“限定节点”里列出几台节点，副本只在这几台里挑；切到“手动”把部署钉在一台节点上（可以指定 GPU 序号）。候选节点由三类条件共同限定：厂商、节点页给节点编辑的 key=value 标签、以及“硬件与网络”（GPU 型号、架构、计算/存储同步/服务网络等系统标签，选项与台数都来自服务端，同一类多选为“其中之一”）。它们与手动选的节点一起存为部署的节点条件，同时满足才是候选，不会扩大到范围外；节点条件在每次启动副本前重新检查，标签、换卡或网络变化不会迁移运行中的实例。“放置选项”里可以把默认的分散（副本优先落在本部署副本最少的节点）改成集中（先填满剩余资源最少的节点），见[调度与显存估算](../explanation/scheduling-and-estimation.md#单机副本落在哪台节点)。然后按需设置并行度、dGPU 显存上限和副本数。部署详情里副本在等节点时会显示等待数量、原因和最接近的节点，“查看候选节点”分页列出全部节点各自卡在哪一步。部署之后要换节点范围（加入新节点、换一组标签、从一台扩到几台、改分散/集中），在部署详情“节点条件”旁点“编辑”，不用重新部署：只影响此后启动的副本，运行中的副本留在原处，重启副本即按新条件重新放置；新条件下一台节点也放不下时直接拒绝，原条件不变。厂商由镜像决定，不能改。
3. **确认启动配置。** “快捷部署”视图只放常用参数（哪些参数在这里由服务端参数字典的 quick 布局决定，如 KV Offload、日志级别、前缀缓存、推测解码）；切到“专家部署”会按服务端参数字典展开全部参数，两种视图共用同一份草稿，环境变量、挂载和手工命令不会因为切换视图而重置。未改动的控件不用管，默认值由服务端统一补上；字典之外的 flag 填进自定义参数即可。“未设置”“清除”的含义见[部署启动配置的语义](../explanation/launch-config.md#未设置与清除)，参数冲突怎么处理见[冲突怎么处理](../explanation/launch-config.md#冲突怎么处理)。
4. **确认运行镜像和启动方式。** 直接改运行镜像地址就能用私有或专用镜像，不用先登记到镜像目录；更换镜像会保留本次参数和启动方式。启动方式默认是引擎生成命令，也可以显式选镜像入口或手工命令，三档的区别见[命令模式](../explanation/launch-config.md#命令模式的三档)。镜像兼容性未知时会提示，已知的资源和放置冲突仍需处理。
5. **确认权重来源和保存位置。** 部署不选择镜像或模型从哪里来：自动调度时页面只显示“镜像和模型在调度后按拉取设置自动获取”，指定了节点（手动放置或多机）时逐节点显示预估（已有、从哪个节点复制、按什么顺序拉取或下载）。你只需要确认运行哪家权重（Hugging Face 或 ModelScope）和模型保存到哪个存储；拉取规则由管理员在[拉取设置](configure-pull-settings.md)里配置，详见[下载、缓存和节点间同步模型](download-and-sync-models.md)。
6. **看评估结果，再提交。** 页面在输入停顿 400ms 后自动评估。所有判断（校验错误、默认值、参数模板投影、节点合格性、权重来源、多机预检结论）都来自这次评估的响应：字段错误显示在对应控件旁，无法归因到控件的错误显示在页面级提示。提交前先看服务端返回的显存拆分、token 容量和调度解释，再核对命令、配置环境、准备脚本、挂载和容器参数。多机命令按 rank 展示与复制，不能把多个 rank 的脚本顺序拼成一条。改过配置之后，要等对应的新评估结果出来再提交。
7. **健康检查。** 表单里的「开启健康检查」默认按模型决定：模型提供对话、文本补全或向量接口就勾选。开启后服务端每分钟经网关给服务发一个最小请求（对话发一条“1”、只生成 1 个 token；只有补全接口时发提示词“1”、生成 1 个 token；向量输入“1”），阈值（默认 60 秒，可设 1–600）内回复为正常，超过记为超时，返回错误或连不上副本记为失败；没有醒着在运行的副本时不发送，显示「无可用副本」。检查只显示结果，不重启、不摘除副本，也不计入网关的请求数、token 与延迟统计（引擎自己导出的指标仍会算上这每分钟一次的请求）。部署列表与详情并排显示「状态 / 健康 / 副本」（副本为运行中 / 期望）；详情里可随时开关、改阈值，不需要重启（`PUT /api/v1/deployments/{id}/health-check`）。升级前已有的部署默认不开启。表单里的「开放分词接口」默认勾选：网关把 `/v1/tokenize`、`/v1/detokenize` 转给该部署的引擎（不计入请求统计），详情里可随时开关，不需要重启，见 [OpenAI 兼容网关](../reference/openai-gateway.md#分词tokenize)。
8. **提交后观察，多副本时选路由策略。** 启动失败时实例和日志会保留，先检查镜像、模型文件、端口和运行时，再改参数重试（怎么看日志见[查看指标与检索日志](monitor-and-logs.md)）。多副本部署的网关默认用 `least_request` 分摊请求，也可以用 `PUT /api/v1/deployments/{id}/routing`（body 为 `{"routing_policy": "..."}`）改成 `prefix_affinity` 或 `failover`；路由策略不属于引擎启动参数，改它不会重启实例。多机、副本数能组合到什么范围，以服务端当前能力为准，见[多机推理](multi-node-inference.md)；PD 分离部署见[PD 分离部署](pd-disaggregation.md)。

命令预览里配置环境展示的只是本次配置产生的环境变量，不等于容器最终的进程环境，原因见[配置环境与镜像环境](../explanation/launch-config.md#配置环境与镜像环境)。SGLang 的日志环境和准备脚本由服务端生成，说明见[SGLang 日志注入的行为与边界](../explanation/sglang-logging.md)。镜像目录不承载启动配置，所有部署只按模板与本次输入启动（[ADR 0031](../adr/0031-image-catalog-carries-no-launch-config.md)）；每一项从哪一层来，见[部署启动参数来源](../reference/deployment-launch-sources.md)。

## 同一个模型名的多个部署

一个部署的所有副本形状相同：张量并行、每副本卡数和启动参数都随部署固定，扩容时每台节点都按同一套配置试算，不会因为节点的卡更大而改成更小的 TP，也不会把单机副本拆到两台机器上。要让同一个模型在不同硬件上用不同配置（例如 RTX 2080 Ti 上 tp=2、RTX 8000 上 tp=1，或 NVIDIA 与昇腾同时提供服务），按硬件各建一个部署。

对外模型名（`served_name`）在部署之间唯一：已有部署（运行中或已停止）占用的名字，新建或克隆时返回 409 `SERVED_NAME_IN_USE`，参数里给出占用它的部署；正在删除的部署不再占用名字，可以立刻用原名重建。部署表单预填的对外模型名是模型名加 `-` 和 4 位随机小写字母或数字（如 `Qwen3-0.6B-x7k2`），可以手动改成别的名字；不填时服务端用模型名，被占用同样返回 409。克隆的副本也在原名后加同样形状的随机后缀。

这条规则之前建的、已经同名的部署保持原样，网关不在它们之间分流：请求交给**最新创建的、当前能应答的**那个部署，旧部署只在所有更新的部署都无法应答（全部休眠、失败或仍在启动）时接手。部署内各副本之间的分流仍按该部署的路由策略。

要让几套硬件一起承担同一个模型名的流量，给每个部署取不同的模型名，在网关前放一层按模型名聚合多个后端的路由，例如 [LiteLLM](https://docs.litellm.ai/docs/routing)：

```yaml
model_list:
  - model_name: qwen3-8b            # 对客户端暴露的名字
    litellm_params:
      model: openai/qwen3-8b-2080   # gpuworks 部署的 served_name
      api_base: http://<server>/v1
      api_key: <gpuworks API key>
  - model_name: qwen3-8b
    litellm_params:
      model: openai/qwen3-8b-rtx8000
      api_base: http://<server>/v1
      api_key: <gpuworks API key>
```

这种组合下，各部署仍分别计量、分别休眠与扩缩；分流策略、权重与重试以所用路由的文档为准。

## 常见问题

提交失败时，错误会显示在页面上，同时带着下面这些稳定的错误码。更多排查见[故障排查](troubleshooting.md)。

| 错误码 | 含义与处理 |
|---|---|
| `AUTOMATIC_PLACEMENT_STALE` | 评估之后资源被占走（比如其它部署占满了显存），或所选节点不再满足节点条件，自动放置的结果失效了。服务端不会悄悄换节点，回到部署页重新评估再提交 |
| `ACQUISITION_CANDIDATE_STALE` | 请求指定的保存存储已不存在，或所选权重来源（Hugging Face / ModelScope）已不在模板里。重新评估后再提交，服务端不会替换 |
| `LAUNCH_CONFIG_CONFLICT` | 同一个参数在表单字段和额外参数（`extra_args`）里给了不同的值。错误里会写出两处的值，只保留其中一处 |
| `LAUNCH_CONFIG_UNSET_CONFLICT` | 某个参数在表单里被关闭（清除），但额外参数里还写着它。删掉那个值，或重新启用该参数 |
| `NODE_REQUIREMENTS_NOT_EDITABLE` | 多机与 PD 部署按 rank 列节点，没有可编辑的节点条件；用“调整副本”改它们的节点 |
| `NODE_REQUIREMENTS_UNMET` | 所选节点不满足部署的节点条件（标签、厂商等）。改选满足条件的节点，或调整条件 |
