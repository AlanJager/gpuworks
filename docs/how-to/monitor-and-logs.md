# 查看指标与检索日志

**适用场景**：查看集群和部署的 GPU 指标、排查某个实例为什么起不来或报错、按关键字检索历史日志。

**前置条件**：至少一个在线节点（agent 通过 `metrics` 流上报指标，见[接入节点](connect-nodes.md)）；要看日志的实例已经创建过（部署见[部署模型](deploy-models.md)）。

## 1. 看概览与指标

打开监控页（控制台侧边栏「监控中心」），从 agent 的 `metrics` 流展示 GPU 利用率、显存、温度和实例状态。

页面右上角选时间范围：15 分钟到 7 天几个预设都以「现在」为终点，并按「跟随最新」定时刷新；也可以用日期选择器选任意一段（最长 30 天、不能晚于现在，受[数据保留](../reference/api.md#analytics运营分析)里指标原始样本的保留时长限制）。选了自定义时间段时页面不再刷新，图表、请求分布、延迟拆解和信号都按这一段计算，服务列表、副本和健康检查仍显示当前状态，页面上有一行文字说明。这个选择记在地址栏（`?from=…&to=…`），可以直接分享。更长期的趋势（按小时、按天的 Token 用量、服务质量、GPU 利用和卡时）在「运营分析」页看，见[查看运营分析](analyze-operations.md)。

页面顶部的「数据截至 …」是最近一个样本的时间。最近 30 秒内没有新样本（例如节点断线）时，该行会追加「数据滞后」提示，页面显示的是最后一次样本，而不是把旧值伪装成实时值；还没有任何样本时显示「暂无样本」。

网卡、RDMA 端口和按角色的网络流量见[网络指标参考](../reference/network-metrics.md)。

部署的推理指标有两个来源，名字与含义见[推理指标词表](../reference/inference-metrics.md)：

- **引擎**：agent 采集引擎自己的 Prometheus 端点。vLLM / SGLang 部署自动采集；`callable` 引擎导出 `vllm:` / `sglang:` 前缀的指标时自动识别，其他引擎需要在模板里声明映射，见[为推理模板声明引擎指标](declare-engine-metrics.md)。
- **网关**：网关对经过它的每个请求测量首 token 时间（TTFT）、端到端耗时、在途请求数，并读取回复 `usage` 里引擎报告的 token 数。每个部署都有，包括没有 `/metrics` 的引擎（如 Strata）。

「请求对账（近 5 分钟）」把网关转发的请求数与引擎自报的完成数对比，缺口持续超过在途数时用红字报丢失；引擎没有上报完成计数（SGLang 没开 `--enable-metrics`、没有 `/metrics` 的引擎）时这张卡片不显示，因为没有可对比的数。

TTFT、端到端延迟、TPOT、分段时长（排队 / Prefill / Decode）、输入/输出 token 吞吐、运行请求这几项，引擎上报了就用引擎的值，引擎没有上报才用网关的，界面不标注来源。两者口径不同：网关的 TTFT 和端到端从请求交给实例开始计，包含排队和网络，通常比引擎的大；网关的 TPOT 从它看到的第一个生成 token 算到最后一个，按输出 token 数平均，含网络抖动；网关的分段时长是引擎在每个回复里自报的数汇总而成，所以只有回复里带逐请求统计的引擎才有（TensorFold、Strata 有 Prefill 与 Decode，没有排队）；网关的"运行请求"是在途请求数，包含排队中的请求。KV 使用率、排队请求、抢占只有引擎能提供，引擎没有上报指标时，服务监控页这些图会注明"只有引擎能提供"，部署详情的指标面板改为显示网关的统计。

服务页的「KV Cache」图按副本画两条线：左轴是使用率，右轴是前缀缓存命中率，都是 0–100%。命中率对导出命中/查询计数的引擎（vLLM）按每个时间点内的命中数除以查询数算，对只报瞬时命中率的引擎（SGLang）直接用它；某个时间点没有查询时这一点留空，不画成 0。

## 2. 看请求视图与请求分布

TTFT、TPOT 这些分位数只说明「慢」，不说明为什么慢。网关为每个转发的请求（`/v1` 与 Playground）记一条记录：谁发的（API key 或登录用户）、输入与缓存命中、输出与思考 token、什么时候发给实例、首个思考与首个答案什么时候到、什么时候结束、怎么结束，以及引擎自报的排队、Prefill、Decode 耗时（[逐请求统计](../reference/inference-metrics.md#逐请求统计)）。

- **监控中心的输入输出分布**：全集群在所选时间范围内结束的请求，按输入 token × 输出 token 计数，两个维度都按 2 的幂分档，用来看流量是长输入短输出（RAG、摘要）还是短输入长输出（生成、思考）。
- **服务页的结构**：顶部常驻两行：第一行左边是端到端延迟拆解，右边是健康（健康检查的最近结果、最近 10 次的色条与平均耗时，以及运行中副本数 / 期望副本数与各副本状态）；第二行左边是在途请求的阶段条，右边是泳道散点；下面三个页签：「概览」（请求对账、各项图表与分布、副本、日志）、「实时请求」、「历史请求」。
- **端到端延迟拆解**：所选时间范围内完整回复（正常完成或在最大 token 处停下）的端到端时间，按请求经过的阶段拆成一条：网关、引擎预处理、引擎排队、Prefill（引擎自报了才拆开；只报 Prefill 不报排队的引擎如 TensorFold、Strata，Prefill 单列，其余仍合为「等首字」；都不报时整段是「等首字」）、思考、正式回答、引擎后处理。「网关」是网关自身从收到请求到转给副本的实测耗时（通常几毫秒）；「引擎预处理」只在引擎报了排队时出现，是首字前的等待减去引擎自报的排队与 Prefill 后剩下的部分：引擎进入调度队列之前做的事（渲染 chat template、分词、等正在跑的那一步 GPU 计算结束才把新请求收进调度器），加上首个 token 送回网关的时间（含网络）。并发高、单步耗时长时这一段会明显变大（例如 vLLM 分块 prefill 一步几百毫秒，同一步里到达的请求都要等这一步结束）。升级前写入的时段没有单独记网关耗时，整段算作引擎预处理。PD 分离部署在「网关」之后多一段「Prefill」（网关等 prefill 实例的时间；请求视图里同一段叫「PD Prefill」），引擎排队显示为「KV 传输·排队」（decode 实例等远端 KV 的时间计在排队里），decode 实例自己的 Prefill 显示为「首 token 重算」，它只重算最后一个 prompt token，占端到端平均的 1% 或更少时不画出（条与图例都不出现，其余各段仍按比例铺满），见 [PD 分离部署](pd-disaggregation.md#运行中)。「引擎后处理」是最后一个带文字的分片之后到响应结束的时间：引擎发结束分片、usage 分片与 `[DONE]`，以及网关把它们写给客户端（客户端读得慢也算在这里），通常几毫秒。每段是该阶段的平均时长（没有这一段的请求按 0 计），所以各段加起来正好是端到端平均；顶部是端到端平均与 p50 / p95。悬停或聚焦一段，看它的占比、p50 / p95（只算有这一段的请求）和平均速度（Prefill 按未命中缓存的输入算，思考按思考 token、回答按其余输出 token 算，usage 不带思考 token 数时回答速度用整个生成阶段的速度）。拆解按全部请求累加，不受请求日志抽样影响；分位数来自四分之一倍频程的分档，误差约 10%。拆分规则与请求视图每行的色条是同一套（服务端 `uxrecord.SegmentsOf`），各时间点的取法、拆分算法与汇总方法见[请求时间线与阶段拆分](../reference/request-timeline.md)。
- **服务页的两张分布卡**：该部署的输入输出分布，以及非缓存输入 token × 首 token 时间。后者把「首字慢」分成两类：未命中缓存的输入多而首字慢，是 Prefill 本身的代价；未命中的输入少而首字仍慢，多半是排队。卡片注明有多少请求带了 usage、有多少报了缓存命中，没带的请求不在图里。
- **健康**：服务开启了健康检查时（见[部署模型](deploy-models.md)），卡片显示最近一次检查的结果与耗时、回复它的副本，最近 10 次检查的色条（绿为正常、橙为超时、红为失败，旧的在左，悬停看每次的时间、耗时、副本与失败原因）和其中阈值内回复的平均耗时。没开启时显示「未开启」并链接到部署详情去开启。检查每分钟一次，结果只保存在服务端内存里，服务端重启后一分钟内重新出现。
- **在途请求（阶段条与泳道散点）**：每 2 秒刷新。阶段条把当前所有在途请求按等首字、思考中、输出中计数，下面写出等首字最久的时长和卡顿的请求数（思考或输出中、超过 2 秒没有新输出）。泳道散点把每个在途请求画成一个点：按阶段分三条泳道，横轴是它已经进行了多久（对数刻度，至少到 60 秒）；点挤在等首字泳道右侧说明在排队，远离其他点的单独一点是卡住的请求，红色描边是卡顿的请求。悬停一个点看调用方、阶段与已过时间、落到的副本、已收到的块数和已静默多久。一次最多画 500 个（等首字最久的优先），超过时下方注明在途总数；同样的请求以表格形式在「实时请求」页签里。
- **服务页的请求视图**：「实时」列出进行中的请求，按等首字最久、思考中、输出中排序，顶部是各阶段的在途数；每 2 秒刷新，可暂停；默认 20 行，可显示全部（最多 200 行）。每行显示请求体大小、已收到的块数和已过去的时间；排队与 Prefill 在请求结束前合在一起显示为「等首字」。「历史」按时间倒序列出已结束的请求，每页 50 行，用「上一页 / 下一页」翻（游标分页，翻到多深都一样快）；可另选时间范围，按结果（正常完成、长度截断、客户端退出、连接中断、出错）和端到端时间筛选，底部显示这段时间网关结束的请求总数（不受筛选和抽样影响）。请求多时正常请求会抽样保存，一行可能代表多个请求，悬停可见。两个页签都可按 API key 和副本筛选，每行标出请求落到的副本（序号与节点）。每行的色条按该请求自己的总时长画出各段占比：排队、Prefill（引擎报了才分开，否则合为等首字）、思考、正式输出；悬停或用键盘聚焦一行，看各段时长、Prefill 与 Decode 速度、token 数与结束原因。

数据来源与限制：

- **usage 的覆盖**：vLLM / SGLang 的流式请求由网关代为要 usage 并去掉多出的块，客户端收到的回复不变；TensorFold、Strata 总是带。其他 callable 引擎不带 usage 时，这些请求只有时间线，不进分布图（[ADR 0042](../adr/0042-gateway-request-records.md)）。
- **排队与 Prefill 的拆分**要引擎自报：vLLM 需要部署带「返回逐请求耗时」（`--enable-per-request-metrics`，vLLM 0.25.0 及以上镜像的新部署默认打开，更旧或版本未知的镜像上开关显示为「自动」、不传参数，可以手动打开），TensorFold、Strata 的内置模板已声明；SGLang 暂不拆。
- **存储**：记录写在数据目录的 `ux.db`，按天分表，保留 7 天，文件超过 2 GB 时从最老的一天删起。分布与计数按全部请求统计；请求列表在每秒超过 300 条时抽样：异常请求（非 2xx、断开、截断、首个输出 ≥ 10 秒）全留，正常请求按比例保留，每条记录带 `weight` 表示它代表几个请求。写入跟不上时丢弃记录并计数，不会拖慢转发。
- **请求详情与查找**：点一行（或聚焦后按回车）打开请求详情，可复制请求 ID 与 trace id；设置了 trace 链接（见[导出请求 trace 到 OpenTelemetry](export-request-traces.md)）时可直接在外部追踪系统中打开。监控中心右上角的搜索框按 trace id（32 位十六进制，列出该 trace 的全部请求，可跨部署）或请求 ID 查找已结束的请求。查找按时间窗进行：网关自己起的 trace id 带有时间，直接定位；其余默认查最近 1 小时，可扩大到最近 24 小时。被抽样掉的正常请求查不到。
- 接口：`GET /api/v1/monitor/deployments/{id}/requests`、`GET /api/v1/monitor/requests/lookup`、`GET /api/v1/monitor/distributions`，见 [API 参考](../reference/api.md)。

## 3. 看实例事件和实时日志

在部署页打开实例详情，事件时间线（状态变化、调度结果、错误）和日志合并在同一条时间线里。实例运行中显示实时日志；容器退出后显示已持久化的日志，也可以选择一个历史时间范围回看。启动失败时实例和日志会保留，先在这里看错误再改参数重试。

## 4. 在「日志」页检索

历史日志写入内置分表 FTS5 logstore，「日志」页在它上面检索。

1. **选过滤条件**，可以任意组合：

   | 条件 | 说明 |
   |---|---|
   | 实例 | 前缀匹配，填 8 位短 ID 即可 |
   | 级别 | `level=warn` 表示 ≥warn，即 warn 及更高 |
   | 来源 | `source=instance\|node\|agent\|server`；不指定时 API 默认 `instance` |
   | 时间范围 | 页面提供最近 30 分钟到 7 天、全部等预设；选「自定义」可精确到秒指定起止时间 |
   | 关键字 | 全文检索，例如 `CUDA out of memory` |

2. **看结果**。关键字留空时回退为最近日志（相当于 tail）。命中数在 `with_total=1` 时返回，封顶 100 万（页面显示为 `N+`）。结果多于一页时用 `cursor_ts`/`cursor_id` 游标翻页，页面上是「加载更多」。
3. **展开上下文**。对单条命中点「上下文」，可看它前后若干行，等价于 `grep -C`；接口是 `GET /api/v1/logs/context?instance=..&ts=..&id=..&before=..&after=..`。agent、server 这类基础设施日志没有实例 UUID，改用 `node` 参数限定范围。
4. **看直方图**。搜索结果上方按时间桶 × 级别统计日志量（红为 error/fatal，蓝为其余级别，含没有级别的行），接口是 `GET /api/v1/logs/histogram`，过滤条件与检索一致，用来先找到异常时间段再缩小范围。
5. **回到原始事件**。命中里的级别、时间、来源和实例 UUID 可以对回实例详情里的对应事件。

## 设置引擎日志级别

SGLang 默认日志不带级别，平台的级别过滤和直方图就看不到真正的错误。SGLang 单卡、引擎接管模式下，平台会在适用时自动注入带级别的日志配置，日志仍写入容器 stderr。

日志级别在快捷部署的「功能」区直接选择：

- 默认 INFO；可换成其他级别，或选「未设置」。选项和默认值由服务端参数字典提供，表单提交所选值。
- 切换快捷/专家模式不会丢失这个选择。
- 「未设置」表示不带 `--log-level`，也就不注入配置，由引擎决定默认级别。

部署命令预览里能看到 `SGLANG_LOGGING_CONFIG_PATH` 和写入配置的启动前脚本，实例详情也可以查看保存的脚本和 env。`/tmp/gpuworks-sglang-logging.json` 是配置文件，不是日志输出文件。

哪些启动方式不会自动注入、多卡并行时日志为什么仍可能没有级别、怎么自己接管完整脚本，见[SGLang 日志注入的行为与边界](../explanation/sglang-logging.md)。
