# 查看指标与检索日志

**适用场景**：查看集群和部署的 GPU 指标、排查某个实例为什么起不来或报错、按关键字检索历史日志。

完成后，能从异常时间段或请求 ID 找到相关副本，结合指标、事件和日志确定下一步排查方向。

**前置条件**：能登录控制台；查看实时节点指标时节点已[接入](connect-nodes.md)且在线。查看实例历史日志时，实例需已创建并产生过日志；查看网关请求时，需有经过 `/v1` 或 Playground 的调用。

## 1. 看概览与指标

1. 打开侧边栏**监控中心**，查看 GPU 利用率、显存、温度和实例状态，并选择问题发生的时间范围。
2. 先看顶部「数据截至 …」。最近 30 秒没有新样本时会显示「数据滞后」，此时图中是最后一次样本；
   「暂无样本」表示还未收到数据。节点离线时先恢复连接，不能用旧值判断当前负载。
3. 进入相关服务的监控页，查看请求对账、延迟、吞吐和运行请求。网卡、RDMA 端口与角色流量的含义见[网络指标参考](../reference/network-metrics.md)。

服务或节点删除后，原始样本仍保留到期（默认 72 小时）。监控中心的服务列表、显存条只显示现有的服务和节点；指标浏览器按节点或部署分组时，已删除的仍按删除时的名字显示并标「已删除」。打开已删除服务的监控页，会提示它已删除，并提供到用量分析的链接，那里保留它的历史用量、服务质量和卡时。

页面右上角选时间范围：15 分钟到 7 天几个预设都以「现在」为终点，并按「跟随最新」定时刷新；也可以用日期选择器选任意一段（最长 30 天、不能晚于现在，受[数据保留](../reference/api.md#analytics用量分析)里指标原始样本的保留时长限制）。选了自定义时间段时页面不再刷新，图表、请求分布、延迟拆解和信号都按这一段计算，服务列表、副本和健康检查仍显示当前状态，页面上有一行文字说明。这个选择记在地址栏（`?from=…&to=…`），可以直接分享。更长期的趋势（按小时、按天的 Token 用量、服务质量、GPU 利用和卡时）在「用量分析」页看，见[查看用量分析](analyze-operations.md)。

部署指标有两个来源，比较不同引擎前先确认口径：

- **引擎**：agent 采集实例的指标端点，按模板映射为平台指标。vLLM / SGLang 有内置映射；未声明映射的 `callable` 引擎导出 `vllm:` / `sglang:` 前缀的指标时自动识别，其他引擎需[声明指标映射](declare-engine-metrics.md)。
- **网关**：测量经过网关的请求耗时和在途数，并读取回复 `usage` 中的 token 数。即使引擎不提供指标端点，也能有网关统计；直接访问实例的请求不计入这些统计。

| 看到的指标 | 如何理解或继续处理 |
|---|---|
| TTFT、端到端、TPOT、输入 / 输出 token 吞吐、运行请求 | 优先使用引擎值，否则使用可用的网关统计，界面不标注来源；两边都缺少时没有数值。网关的运行请求是包含排队的在途数，不能直接等同于引擎执行数 |
| 排队 / Prefill / Decode 时长 | 没有引擎指标时，网关只能汇总回复里实际自报的逐请求统计；缺少字段就无法拆出对应阶段 |
| KV 使用率、排队请求、抢占 | 只能由引擎提供。缺失时服务监控页会注明，不能将其当作 0 |
| 请求对账（近 5 分钟） | 比较网关转发数与引擎完成数；缺口持续超过在途数时标红。到后面的请求视图与实例日志核对失败，不凭红字直接确定根因。引擎不报完成计数时卡片不显示 |

网关指标中的 TTFT 从请求交给实例计到首个生成 token（包括思考），端到端计到回复结束，包含实例排队与网络耗时；它们与引擎内部计时不同。

网关 TPOT 是首个生成 token 到最后一个文本块的时间除以输出 token 数减一，包含网络抖动；需要 usage 中的输出计数且至少有两个 token，不能把流式块数当作 token 数。

TPOT 与阶段时长的网关回退只为内置映射缺少对应指标的引擎生成；关闭 vLLM / SGLang 的指标采集不会因此额外生成这些回退，缺数据时仍需恢复引擎采集。

没有引擎指标时，部署详情的指标面板会改为显示可用的网关统计。完整指标名、来源和单位见[推理指标词表](../reference/inference-metrics.md)。

服务页的「KV Cache」图按副本画两条线：左轴是使用率，右轴是前缀缓存命中率，都是 0–100%。命中率对导出命中/查询计数的引擎（vLLM）按每个时间点内的命中数除以查询数算，对只报瞬时命中率的引擎（SGLang）直接用它；某个时间点没有查询时这一点留空，不画成 0。

## 2. 看请求视图与请求分布

这里记录经过 `/v1` 与 Playground 的请求；直接调用实例端口的请求不在网关请求视图内。
服务页顶部常驻延迟拆解、健康、阶段条和泳道散点，下方是**概览**、**实时请求**和**历史请求**。

### 查找已结束的请求

按手头的信息选择入口：

- **已有请求 ID 或 trace id**：在监控中心右上角搜索框粘贴 ID。trace id 为 32 位十六进制，可跨部署列出同一 trace 的请求。
  网关生成的 trace id 可直接定位时间；其他 ID 默认查最近 1 小时，可扩大到最近 24 小时。
  请求所属的部署已删除时，按删除时的名字显示并标「已删除」。
- **还不知道具体请求**：进入服务页的**历史请求**，按时间倒序查找。选择时间范围，按结果（正常完成、长度截断、客户端退出、连接中断、出错）和端到端时间筛选。
  每页 50 行，用**上一页 / 下一页**继续查找；底部请求总数不受筛选和列表抽样影响。

找到请求后，点击请求行或聚焦后按回车，核对调用方、落到的副本、token 数、结束原因和阶段时间线。
可复制请求 ID、trace id；配置了 [Trace 链接](export-request-traces.md)后，可点**在追踪系统中打开**。

**历史请求**和**实时请求**均可按 API key 和副本筛选。每行标出副本序号与节点，色条按该请求自身总时长表示各阶段占比；
悬停或用键盘聚焦可查看阶段耗时、Prefill / Decode 速度、token 数与结束原因。

### 查看实时请求与卡顿

请求还没结束时，打开**实时请求**。列表按等首字最久、思考中、输出中排序，每行显示请求体大小、已收到的块数和已过时间。
每 2 秒刷新，可暂停，默认显示 20 行，最多显示 200 行。

请求结束前引擎尚未返回排队、Prefill 统计，首字之前合并显示为**等首字**。发现异常请求时，记录副本和时间，继续查看该实例的事件与日志。

**阶段条**每 2 秒更新当前等首字、思考中、输出中的请求数，同时列出等首字最久的时间与卡顿数。
思考或输出超过 2 秒没有新块时标为卡顿。

**泳道散点**按这三个阶段分泳道，横轴是已过时间（对数刻度，至少到 60 秒）；红色描边表示卡顿，悬停可看调用方、副本、块数与静默时长。
等首字泳道右侧聚集说明很多请求仍在等待，孤立的长耗时点值得单独检查，但不能仅凭位置确定排队或故障原因。

散点最多显示 500 个，优先显示等首字最久的请求；数量上限不代表其余请求不存在。

### 查看服务趋势与分布

需要判断整个服务的趋势时，在服务页**概览**查看分布；顶部的延迟拆解与健康也可结合判断。

- **输入输出分布**：按输入 token × 输出 token 计数，两轴按 2 的幂分档，用于判断长输入短输出还是短输入长输出。
  监控中心看全集群，服务页看当前部署，均使用所选时间范围内结束的请求。
- **非缓存输入 token × 首 token 时间**：观察长输入与首字变慢是否同时发生。未命中输入少但首字慢时，再检查排队、预处理和网络；分布本身不能证明原因。
  卡片标明 usage 和缓存上报覆盖数。

### 查看健康和副本状态

已开启健康检查时，**健康**卡片显示最近结果、耗时、回复副本和最近 10 次检查。绿为正常、橙为超时、红为失败，旧结果在左；
悬停查看每次时间与失败原因。平均耗时只算阈值内成功回复。

未开启时，可从卡片进入部署详情开启。每分钟检查一次，结果仅留在 server 内存，重启后等待新结果。
卡片还显示就绪 / 期望副本数与各副本状态。

### 解读端到端延迟

**端到端延迟拆解**统计所选时间范围内的完整回复（正常完成或长度截断），用于查看时间主要花在网关、等待、Prefill、思考、回答还是收尾。
悬停或聚焦某段查看占比、p50 / p95 与速度；缺少引擎自报时，无法拆开的部分显示为**等首字**。

这里的端到端从网关收到请求计到响应结束，包含网关处理；与第 1 节从交给实例开始计时的网关指标不是同一起点。
首个 token 取首个思考与首个回答中较早的那个，最后一块只指带生成文本的块，不含结束或 usage 块。

这些生成时间点只在流式回复中可观察；非流式回复若报齐引擎排队、Prefill、Decode，也可按自报拆分，不能把未观察到的首字或思考时间当作 0。

#### 各阶段表示什么

下表以流式回复为例：

| 阶段 | 含义与判断条件 |
|---|---|
| **网关** | 收到请求到交给副本的时间；PD 顺序交接另列的 Prefill 时间不重复计入 |
| **引擎预处理** | 引擎报了排队和 Prefill 后，首字前等待扣除这两项的剩余时间，包括模板处理、分词、进入调度前等待及首 token 返回的网络时间。并发高或单步计算长时可能增大，不等于纯 CPU 处理时间 |
| **引擎排队 / Prefill / 等首字** | 排队和 Prefill 取引擎自报。只报 Prefill 时，Prefill 单列，其余合为**等首字**；未报 Prefill 时整段等待合为**等首字**，不能据此当作纯排队 |
| **思考 / 正式回答** | 思考从首个思考块到首个回答块（无回答时到最后一块）；回答从首个回答块到最后一块 |
| **引擎后处理** | 最后一个文本块到响应结束，包括结束块、usage、`[DONE]` 及网关写回客户端；客户端读得慢也算在这里，不能只归因于引擎 |

#### PD 模式与旧记录

两个 vLLM PD 模式顺序交接时，**网关**之后多出一段 **Prefill**，表示网关等 prefill 实例的时间（单条请求里叫 **PD Prefill**）。
decode 自报排队显示为 **KV 传输·排队**，包含等待远端 KV；decode 的 Prefill 显示为 **首 token 重算**，占端到端平均不超过 1% 时不画出。

旧记录若未单独记录网关耗时，不能用它与新记录的**引擎预处理**直接比较。

#### 平均值、分位数与速度

各段平均按所有完整回复计算，没有该阶段的回复按 0 计，所以各段之和等于端到端平均；这不表示未上报的引擎阶段实际耗时为 0。
顶部显示端到端平均及 p50 / p95；阶段分位数只统计出现该阶段的请求，分档误差约 10%。汇总使用全部请求，不受请求日志抽样影响。

速度按有对应 token 数和时长的请求，累加 token 后除以累加时长：

- **Prefill**：使用未命中缓存的输入与引擎 Prefill 时间；顺序 PD 用 P 实例的自报时间。
- **思考**：使用思考 token 与思考阶段时长。
- **回答**：使用输出减思考 token 与回答阶段时长；usage 没有思考计数时，只纳入没有思考阶段的回复。
- **Decode**：优先用引擎自报耗时，否则用首个到最后一个生成 token 的间隔及输出 token 数减一。

缺少 token 或相应阶段时无法计算速度。字段与完整拆分规则见[请求时间线与阶段拆分](../reference/request-timeline.md)。

### 请求查不到或缺少数据

#### 没有 token 分布或速度

没有 usage 的请求仍可有时间线，但不进入 token 分布；缓存分布还要求引擎报告缓存命中数。

vLLM / SGLang 流式请求由网关请求 usage，并去掉为统计额外取得的 usage 块，保持客户端原有回复。
TensorFold、Strata 内置模板的回复带 usage，其他 callable 引擎需自行提供。

#### 没有排队或 Prefill 拆分

vLLM 需要**返回逐请求耗时**（`--enable-per-request-metrics`）；0.25.0 及以上镜像的新部署默认开启，旧版本或未知版本默认不传，可手动选择但须确认镜像支持。
TensorFold、Strata 内置模板报告 Prefill 与 Decode，不报排队；SGLang 暂不拆。

#### 请求记录缺失

记录保留 7 天，存储超过 2 GB 时会提前删除最老的一天。

每秒超过 300 条时正常请求按比例保存，异常请求（非 2xx、断开、截断、首个输出 ≥ 10 秒）保留。
一行可能代表多个请求，悬停查看权重；分布和计数不受列表抽样影响。

写入跟不上时也可能丢记录。未保存的请求不能从列表或 ID 搜索找回。

API 方式可使用 `GET /api/v1/monitor/deployments/{id}/requests`、`GET /api/v1/monitor/requests/lookup`、
`GET /api/v1/monitor/distributions`，参数见 [API 参考](../reference/api.md)。

## 3. 看实例事件和实时日志

在部署页打开实例详情，事件时间线（状态变化、调度结果、错误）和日志合并在同一条时间线里。实例运行中显示实时日志；容器退出后显示已持久化的日志，也可以选择一个历史时间范围回看。启动失败时实例和日志会保留，先在这里看错误再改参数重试。

## 4. 在「日志」页检索

从实例详情确定时间段和实例 ID 后，打开侧边栏**日志**检索历史记录；节点、agent 和 server 日志也可以在这里查询。

1. **选过滤条件**，可以任意组合：

   | 条件 | 说明 |
   |---|---|
   | **实例** | 前缀匹配，填 8 位短 ID 即可 |
   | **级别** | `level=warn` 表示 ≥warn，即 warn 及更高 |
   | **来源** | `source=instance\|node\|agent\|server`；不指定时 API 默认 `instance` |
   | **时间范围** | 页面提供最近 30 分钟到 7 天、全部等预设；选**自定义**可精确到秒指定起止时间 |
   | **关键字** | 全文检索，例如 `CUDA out of memory` |

2. **看结果**。关键字留空时回退为最近日志（相当于 tail）。结果多于一页时点**加载更多**；命中数封顶 100 万，超过统计上限时显示为 `N+`，不是精确总数。
3. **展开上下文**。对单条命中点**上下文**，可看它前后若干行。查 agent、server 日志时用节点和来源限定范围，不要沿用实例过滤条件。
4. **看直方图**。搜索结果上方按时间桶 × 级别统计日志量（红为 error/fatal，蓝为其余级别，含没有级别的行），使用当前过滤条件；先找到异常时间段，再缩小范围。
5. **回到原始事件**。命中里的级别、时间、来源和实例 UUID 可以对回实例详情里的对应事件。

通过 API 检索时，使用 `GET /api/v1/logs/search`，加 `with_total=1` 取命中数，用 `cursor_ts` / `cursor_id` 翻页。
上下文用 `GET /api/v1/logs/context?instance=..&ts=..&id=..&before=..&after=..`；agent、server 等没有实例 UUID 的日志改用 `node` 限定范围。
直方图用 `GET /api/v1/logs/histogram`，过滤条件与检索一致；完整参数见 [API 参考](../reference/api.md)。

## 设置引擎日志级别

SGLang 默认日志不带级别，平台的级别过滤和直方图就看不到真正的错误。SGLang 单卡、引擎接管模式下，平台会在适用时自动注入带级别的日志配置，日志仍写入容器 stderr。

日志级别在快捷部署的**功能**区直接选择：

- 默认 INFO；可换成其他级别，或选**未设置**。选项和默认值由服务端参数字典提供，表单提交所选值。
- 切换快捷/专家模式不会丢失这个选择。
- **未设置**表示不带 `--log-level`，也就不注入配置，由引擎决定默认级别。

部署命令预览里能看到 `SGLANG_LOGGING_CONFIG_PATH` 和写入配置的启动前脚本，实例详情也可以查看保存的脚本和 env。`/tmp/gpuworks-sglang-logging.json` 是配置文件，不是日志输出文件。

哪些启动方式不会自动注入、多卡并行时日志为什么仍可能没有级别、怎么自己接管完整脚本，见[SGLang 日志注入的行为与边界](../explanation/sglang-logging.md)。
