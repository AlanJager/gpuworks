# 接入 Slurm 集群

**适用场景**：已有 Slurm 集群，想让其中的 GPU 节点跑 gpuworks 的推理服务，而不逐台安装 agent。

阿里云 E-HPC 集群在云账号里直接接入，见[阿里云 E-HPC](#阿里云-e-hpc)。接入前可以先让平台（或命令的 `--check` 选项）只检查、不改动任何东西，说明它会做什么，见[先检查，再应用](#先检查再应用)。

## 你会得到什么

一个集群对应「外部平台」页里的一个条目，一个接入令牌。在集群的 Slurm 管控节点（运行 slurmctld 的那台，E-HPC 里叫「管控节点」；不是 gpuworks 的管理节点）上以 root 执行一次接入命令，它把一个健康检查程序（`HealthCheckProgram`）写进 `slurm.conf`；之后每台 GPU 计算节点上的 slurmd 按健康检查周期运行它，它在本机装好 agent，agent 用条目的令牌换取自己的节点 token，与普通节点一样出现在「计算节点」页。以后扩容出来的 GPU 节点自己加入，不用再操作。

卡仍然归 Slurm 分配：其他作业占着的卡显示为平台外占用、不调度；部署要用卡时，agent 提交一个占位作业把卡借过来，部署停止后再还给 Slurm。设计见 [ADR 0075](../adr/0075-slurm-allocates-node-cards.md)。

## 要求

- Slurm 用 GRES 分配 GPU（`scontrol show node <节点>` 的 `Gres` 含 `gpu`），NVIDIA 卡。没有 NVIDIA GPU 的节点（CPU 队列）不会装 agent，也不会出现在平台。
- 节点有 Docker（或其他 agent 支持的运行时）与 NVIDIA Container Toolkit，同普通节点。
- 节点能访问 gpuworks server（接入时填的「管理节点接入地址」）：agent 主动外连，也要从这个地址下载 agent。接入命令、检查命令和「检查并应用」会实际验证：用 `curl` 在 Slurm 管控节点上、以及能逐台执行命令的每台 GPU 节点上访问 `<地址>/healthz`，访问不到的主机逐台列出原因（域名解析失败、连接被拒绝或没有路由、连接超时、TLS 错误等），这一步没通过时命令以「有要手工处理的」收尾。**不要把 `gpuworks expose` 的临时公网地址（`*.trycloudflare.com`）填成接入地址**：它在连接器重建后会变，节点会因此连不上 server；表单发现填的就是平台此刻的临时公网地址时会提示，但不阻止。
- 能在 Slurm 管控节点上以 root 执行一次接入命令（它改 `slurm.conf` 并执行 `scontrol reconfigure`）。
- 脚本目录（默认 `/opt/gpuworks-slurm`）在每个节点上是同一路径、都能读到：放在共享存储上最省事；不在共享存储上时，接入命令用 Slurm 管控节点 root 的免密 SSH（有 `clush` 或 `pdsh`/`pdcp` 就用它们）把脚本并行复制到 `sinfo` 列出的所有其他节点（CPU 节点也要：集群原有的健康检查经 `check.sh` 运行，在它们上面也要继续生效）。**脚本目录不在共享存储上时，之后新加入集群的节点没有这些文件**，健康检查在它们上面不存在：扩容后再执行一次接入命令，或者把脚本目录放到共享存储上。
- agent 运行的账号（默认 root）能用 `sbatch`、`squeue`、`scancel`、`scontrol`。开了记账并强制关联时，这个账号要有关联（`sacctmgr show assoc user=root`），或者在表单里指定记账账号、或在 sbatch 参数里用 `-A` 指定账户。

## 接入线下 Slurm 集群

1. 在「外部平台」页点右上角「添加外部平台」，在「外部平台」下选「Slurm 集群」；也可以点「快速接入」区的「Slurm 集群」卡片（只有管理员能看到）。
2. 填名称和「管理节点接入地址」（计算节点能访问到的 gpuworks server 地址）。需要时展开「高级」：

   | 字段 | 默认 | 说明 |
   |---|---|---|
   | 运行账号 | `root` | agent 在每个节点上以哪个账号运行（systemd 单元的 `User=`）。创建后不能改。账号必须已经存在于每个节点；安装目录归它所有。非 root 账号有已知限制，见下文[用普通账号运行 agent](#用普通账号运行-agent) |
   | 占位作业记账账号 | agent 自己的账号 | 借卡的占位作业记在哪个账号下，`squeue` 与记账里看到的就是它。agent 以 root 运行时用 `sbatch --uid=<账号>` 提交；agent 本身不是 root 时这一项不起作用。可以修改 |
   | 安装目录 | `/var/lib/gpuworks` | agent 在每个节点上的安装与状态目录，应是本地盘：它在共享存储上时，几个节点会共用一份 agent 状态。创建后不能改 |
   | 脚本目录 | `/opt/gpuworks-slurm` | 存放健康检查脚本与令牌文件，各节点同一路径，最好在共享存储上。创建后不能改 |
   | sbatch 参数 | 无 | 追加给每个占位作业，如 `-p gpu -A research --qos=serving --time=7-0`。没写 `-c`/`--cpus-per-task` 时用 `-c 1`，没写内存时用 `--mem=1G`，没写 `-p`/`--partition` 时用本节点所在的分区，没写 `--requeue` 时加 `--no-requeue`（节点故障后 Slurm 不会把占位作业重新排队）。可以修改 |
   | 空闲归还 | 60 秒 | 卡上最后一个实例停止后，借来的卡多久还给 Slurm（1 到 86400 秒）。可以修改 |
   | 排队超时 | 600 秒 | 占位作业在 Slurm 队列里排了这么久还没跑起来就取消，这次部署启动失败（30 到 86400 秒）。可以修改 |

   管理节点接入地址创建后也不能改，要改就删掉条目重建。
3. 点「接入」，弹窗里是接入命令（含令牌，只有管理员看得到，请像密码一样保管）。在 Slurm 管控节点上以 root 执行：

   ```bash
   curl -fsSL 'https://server.example/slurm/setup.sh?token=…' | sudo sh
   ```

   命令输出每一步的结果，以 `Done.` 收尾，或者以 `Finished, but some steps above need your attention.` 收尾（做完了，但有要手工处理的，见下文）。可以重复执行。弹窗里命令的上面还有一条「检查命令」，是同一条命令加 `-s -- --check`，只说明会做什么、什么都不改，建议先执行它，见[先检查，再应用](#先检查再应用)。
4. 等一到一个半健康检查周期（默认 300 秒，已有健康检查周期的集群沿用它的周期；节点在开始安装前随机等待最多半个周期、且不超过 300 秒，所以默认最多约 7 分半钟）。GPU 节点陆续出现在「计算节点」页，「来源」列写着这个 Slurm 集群，点来源筛选可以只看它的节点。

### 接入命令做什么

命令在 Slurm 管控节点上依次做这些事，每步都打印结果：

1. **预检查**：必须是 root，有 `scontrol`，slurmctld 能连上并报告 `ClusterName`，`slurm.conf` 可读。脚本目录以及它的每一级上级目录都必须归 root 所有、组和其他人不可写（上级目录是带粘滞位的公共目录，如 `/tmp`，可以；路径里有符号链接时，链接本身也要归 root，链接经过和指向的每一级目录都要满足）：slurmd 在每台节点上以 root 运行其中的 `check.sh`，别的账号能改它就等于在所有节点上拿到 root。不满足时拒绝执行（`script_dir_unsafe`），写明是哪一级目录和怎么改；开了 root squash 的共享存储会显示成属于 `nobody`，同样不能用。脚本目录不存在时由接入命令以 `0755` 创建；之前接入留下的自有脚本目录权限过宽、里面又只有 root 的普通文件时，直接收紧（检查命令只报告），里面有别的东西（目录、链接、别人能写的文件）就拒绝，因为可能有人趁它可写时动过。`--uninstall-agents` 同样检查，`--remove` 只警告、照常移除。目录权限只看属主和模式位，NFSv4、GPFS、Lustre 自己的 ACL 看不到，用了这类 ACL 要自己确认别的账号不能写。还必须在运行 slurmctld 的机器上执行：`scontrol show config` 在任何能连上集群的机器上都有答案，在计算节点上执行会改到 configless 的 slurmd 自己的副本（`/run/slurm/…`、`conf-cache`），所以 `SLURM_CONF` 指向这类副本、或本机既没有 slurmctld 进程、主机名与地址又不在 `SlurmctldHost` 里时，命令拒绝执行，什么都不改。
2. **写脚本**：把健康检查脚本 `check.sh` 写到脚本目录，把令牌写到同目录的 `token` 文件（权限 0600，仅 root 可读，写完读回确认）。`check.sh` 本身任何用户可读，里面没有令牌。
3. **串接原有健康检查**：集群原来运行的健康检查（以 `scontrol show config` 里 slurmctld 正在用的 `HealthCheckProgram`、`HealthCheckNodeState`、`HealthCheckInterval` 为准，而不只是读 `slurm.conf` 的文字：设置可能在 `Include` 进来的文件里，或者文件改了还没重新加载）记在脚本目录的 `chained` 文件里（第一行是程序，第二行是原来的 `HealthCheckNodeState`），由 `check.sh` 在自己之后调用，退出码原样返回，NHC 等不受影响。我们的块要在任何状态下都能安装 agent，所以 `HealthCheckNodeState` 是 `ANY`；原来的程序仍只在原来要求的节点状态下运行：`check.sh` 用 `scontrol` 查本机在 Slurm 里的状态，`IDLE`（含 drain 的空闲节点）、`NONDRAINED_IDLE`（未 drain 的空闲节点）、`ALLOC`、`MIXED` 与 Slurm 一样按状态匹配，`ANY` 或没写则不分状态。**近似**：原来带 `CYCLE` 时我们的块写成 `ANY,CYCLE`，slurmctld 仍把各节点的运行错开，但状态是在运行时由 `check.sh` 判断的，与 Slurm 自己按状态选节点不是同一时刻；查不到本机状态（`scontrol` 在节点上连不上控制器）时原来的程序照常运行，同没有我们之前一样。`check.sh` 永远不 drain 节点，自己不会失败。`slurm.conf` 含 `Include` 时命令明确警告：被包含的文件里的 `HealthCheck*` 看不到也改不了，是否生效见第 6 步的核对。
4. **分发**：脚本目录在共享存储（nfs、lustre、gpfs、beegfs、cephfs、fuse 等）上就不用复制；否则并行复制到其他所有节点（用 `ssh` 时一次最多 16 台，总共最多约 3 分钟，超时没开始的节点算失败，原因 `time_cap`），并列出每台成功还是失败及原因（`unreachable` 连不上、`copy` 复制失败、`verify` 复制后核对不通过、`unsafe` 该节点上的脚本目录或上级目录别的账号能改，检查同第 1 步，这台节点什么都不复制，令牌也不复制）。各节点上 root 的登录 shell 要兼容 POSIX sh（bash、dash 等；csh、tcsh 不行）。失败的节点要手工复制 `check.sh`（0755）、`token`（0600）和有则复制的 `chained`。不在共享存储上时输出还会提醒：之后加入的节点没有这些文件，要再执行一次接入命令。
5. **改 `slurm.conf`**：先备份为 `slurm.conf.gpuworks-<时间>.bak`，再追加一个以 `# BEGIN gpuworks` 和 `# END gpuworks` 包起来的块：`HealthCheckProgram=<脚本目录>/check.sh`、`HealthCheckInterval`（沿用原有的周期，没有就是 300 秒，也可以在命令后加 `-s -- --interval 秒数` 指定）、`HealthCheckNodeState=ANY`（原来有 `CYCLE` 时为 `ANY,CYCLE`）。原有的 `HealthCheck*` 行不删，在原位加 `#gpuworks-original#` 前缀注释掉。检查脚本里写进了这个周期：它在节点上后台安装 agent 之前随机等待最多半个周期，免得整个集群的节点在同一秒向 server 请求、下载 agent。
6. **`scontrol reconfigure` 并核对**：集群是 configless（`SlurmctldParameters` 含 `enable_configless`）时，节点自己取到新配置。不是 configless 的集群每个节点各有一份 `slurm.conf`，命令会提示把更新后的 `slurm.conf` 按你们惯常的办法分发到计算节点，否则健康检查在那些节点上不生效，这时命令以「有要手工处理的」收尾。reconfigure 之后命令再问一次 slurmctld 正在用的 `HealthCheckProgram`，不是我们的 `check.sh`（例如被 `Include` 的文件覆盖）就以「有要手工处理的」收尾并写出 slurmctld 实际在用的程序。

### 先检查，再应用

接入命令会改 `slurm.conf`、写脚本、复制到各节点，所以先看它会做什么再动手。和 Kubernetes 条目一样，创建条目和应用是两件事，应用前先有一次不改动任何东西的检查：

- 线下集群在命令后加 `-s -- --check`（弹窗里的「检查命令」，管理员才看得到）：

  ```bash
  curl -fsSL 'https://server.example/slurm/setup.sh?token=…' | sudo sh -s -- --check
  ```

  它不写任何文件、不复制、不改 `slurm.conf`、不 `scontrol reconfigure`（唯一创建的是预检查用的临时目录，结束时删掉）；它只读地问一件事：Slurm 管控节点和每台 GPU 节点（有 `clush`、`pdsh` 或免密 SSH 的话）能不能访问 server 地址的 `/healthz`，每台主机一条标记 `step=server_reach`，汇总 `step=server_reach_summary`，有主机访问不到就以「有要手工处理的」收尾。命令加 `--no-node-reach` 只问 Slurm 管控节点（平台自己逐个问节点时就这样）。预检查照常做，所以不是 root、不在运行 slurmctld 的机器上等问题同样被拒绝。每个事实由接入命令自己用的同一批函数算出，所以检查报告的就是随后接入命令要做的事：要写的检查脚本与令牌文件路径、要串接的原有健康检查程序及其节点状态、间隔、脚本目录所在的文件系统（共享就不用复制，否则要复制到哪些节点、哪些文件）、要在 `slurm.conf` 里原位注释掉的 `HealthCheck*` 行（行号、键、值）、要加的块、是不是 configless、之前武装的 agent 卸载会不会被取消。`Include` 文件、slurmctld 在跑而 `slurm.conf` 没写的程序、不是 configless 这些接入命令会警告的地方，检查同样警告，并以「有要手工处理的」收尾。机器可读的标记行同接入命令（`status=plan` 代替 `status=ok`，另有 `install_mode`、`distribute_plan`、`conf_comment`，最后是 `step=done mode=check`），见[接口](../reference/api.md#slurm集群接入)。`--check` 不能和 `--remove`、`--uninstall-agents` 同用。
- 从云账号接入的集群点「检查并应用」时，平台先让 Slurm 管控节点执行同样的检查，把计划列在弹窗里（要补的 `gres.conf` 行、脚本怎么到达各节点、要加的 `slurm.conf` 块、被注释和串接的原有健康检查、会被恢复的节点、Slurm 管控节点和各 GPU 节点能否访问 server 地址，以及需要注意的事项），你确认后才真正应用，见[阿里云 E-HPC](#阿里云-e-hpc)。

### 节点怎么加入

slurmd 在节点注册时和之后每个健康检查周期运行 `check.sh`；`scontrol reconfigure` 之后有时立即运行一次，但不保证（在 E-HPC 上实测过等到下一个周期才运行），它很快退出，不拖住 slurmd：

- 本机没有 NVIDIA GPU：什么也不做（CPU 节点不登记）。
- agent 服务已经在运行：什么也不做。
- 否则在后台、加锁地安装：先随机等待最多半个健康检查周期（不超过 300 秒），再读令牌文件，向 server 问令牌是否还有效（吊销了就不装），把 server 的 `install.sh` 下载到只有 root 能写的临时文件，以环境变量 `GPUWORKS_SLURM_ENROLL_TOKEN`、`GPUWORKS_SLURM_NODE` 把令牌和节点名交给它，它安装 agent（systemd 服务，`User=` 为所选账号），用令牌登记。下载或安装失败时日志写 curl 或安装脚本真实的退出码，下一次运行重试。输出在 `<安装目录>/slurm-check.log`（安装目录建不出来时在 `/tmp/gpuworks-slurm-check.log`；非 root 账号运行 agent 时在 `/var/log/gpuworks-slurm-check.log`，见下文）。
- 节点的 Slurm 名取 slurmd 启动时 `-N` 给的名字，没有则取 `scontrol` 认得的短主机名或全名。登记按「集群条目 + Slurm 节点名」幂等，重装 agent 得到的还是同一个平台节点。第一台登记的节点把令牌绑定到这个集群的 `ClusterName`，之后别的 Slurm 集群拿这个令牌登记会被拒绝；同一个 Slurm 集群里另一个条目在最近 15 分钟内持有这个节点名时也被拒绝，agent 停下并在日志里写原因。
- 令牌所在目录若是 root 受限的共享存储（root squash），节点上的 root 读不到 `token`，节点什么也装不了，`slurm-check.log` 里会写 `cannot read the enrollment token`：再执行一次接入命令，或手工把 `token` 以 0600 复制到该节点。

吊销后的条目：`check.sh` 问到令牌已吊销，新节点不再安装 agent，已经装好的 agent 照常运行。

### 用普通账号运行 agent

「运行账号」可以填普通账号（如服务账号 `gpusvc`），占位作业记在这个账号名下。准备好的前提：账号在每个节点上都存在、能提交作业（强制记账关联时给它建关联或用 `-A`）、能用 Docker。和 root 运行相比有这些已知限制：

- **Docker 权限**：把账号加进本机的 docker 组（`gpasswd -a gpusvc docker`，重新登录后生效）。用 NIS、LDAP 管账号的集群要用本机的 docker 组：目录服务里同名 docker 组的 gid 与本机 `/var/run/docker.sock` 的属组不同，加进去也打不开 Docker，agent 会改用 runveil。不给 Docker 权限时 agent 用 runveil，要求见[加速卡设备权限（非 root 安装）](connect-nodes.md#加速卡设备权限非-root-安装)，节点不能上网时镜像按[离线部署](deploy-offline.md)导入。
- **安装目录**：默认的 `/var/lib/gpuworks` 由安装过程建好并交给这个账号；改到别的目录时它必须在本地盘、这个账号可写。
- **root 不执行、不写穿 agent 目录里的东西**：安装目录归这个账号所有，它可以在里面放符号链接或替换文件，所以健康检查（以 root 运行）不运行安装目录里的程序，也不往里面的固定名字写文件：日志写到 root 才能写的 `/var/log/gpuworks-slurm-check.log`（不可写时 `/run`、`/tmp`）；卸载 agent 时不执行安装目录里的 `gpuworks-agent uninstall`，而是由 `systemctl disable --now` 停掉服务、删掉单元文件、`systemctl daemon-reload`，再删除 agent 的身份文件（`identity.json`、`agent.lock`、`gpuworks-agent.pid`、配置文件，这些删除不跟随符号链接）；已下载的模型和 agent 程序留着。
- **卡的顺序**：configless 节点的配置缓存只有 root 能读，非 root 的 agent 不能自己执行 `slurmd -G`。健康检查在每次运行时（以 root 运行，agent 在不在运行都一样）先在只有 root 能写的临时文件里生成 `slurmd -G` 的输出，再用 `install` 放到安装目录里的 `slurm-gres-devices`（替换这个名字，不写穿它），agent 先读它；这份文件没有时，agent 改按设备号（`/dev/nvidiaN`）排列 Slurm 的卡位置，日志里有 `taking Slurm's GPU positions in device minor order`。`gres.conf` 的 `File=` 按设备号顺序写或用 `AutoDetect=nvml` 时两种办法一致；`File=` 不按设备号顺序又没有这份文件时，作业会被对到错误的卡上，这种节点请用 root 运行 agent。节点自带 `slurm.conf` 的集群不受影响。

## 集群这一行

线下集群在「外部平台」页自己占一行；从云账号接入的集群在云账号展开后的集群组头里（见 E-HPC 一节），操作相同。

加入的节点带系统标签 `gpuworks.ai/slurm-cluster`（值是集群条目的 UUID，显示条目名，改名不影响匹配）和 `gpuworks.ai/slurm-node`（节点在 Slurm 里的名字），与 Kubernetes 节点的 `gpuworks.ai/kubernetes-cluster`、`gpuworks.ai/kubernetes-node` 对应，可用于节点页筛选、部署的节点要求和[同步组](configure-pull-settings.md#同步组)。手工装 agent、只是向 Slurm 借卡的节点没有这两个标签。

- **状态**：「未接入」（还没有节点登记）、「正常」、「长时间未接入」（创建 10 分钟后仍没有节点登记，且接入执行也已过去 10 分钟：健康检查在一到一个半周期内到各节点，刚执行完的 10 分钟里条目不算长时间未接入，详情写「已配置，GPU 节点会在一到一个半健康检查周期内接入」；旁边的「排查」给出要在 Slurm 管控节点和一台 GPU 节点上执行的检查命令和常见原因；平台自己配置的条目（从云账号的集群接入）不要你登录 Slurm 管控节点，「排查」先指向「检查并应用」，只留一台 GPU 节点上的检查命令）、「已吊销」。还没有节点登记时，条目详情里的那一行说明由 server 判断出的原因（「排查」里替换通用的开头）：云厂商的集群里还没有计算节点（实时读 E-HPC `ListClusters` 的 `Nodes`）；最近一次检查或应用发现有主机访问不到 server 地址（并列出这些主机）；接入刚执行完、节点还在路上（10 分钟内）；接入已执行超过 10 分钟、之后没有节点联系过 server；没有看到接入执行过。后三项是 server 自己看到的（有人取了接入命令的脚本，或平台应用过；用检查命令取脚本不算；节点问过令牌状态或登记过就算联系过），只存在 server 内存里，重启后忘记，所以对 server 本次启动之前创建的条目不下这些结论。
- **GPU 节点 N 台，在线 M 台**：已登记的 agent 每 10 分钟用 `sinfo -a`（含隐藏分区）上报一次集群的节点，N 是其中带 `gpu` GRES 的节点数，M 是 agent 在线的已接入节点数（点开是只列这个集群节点的「计算节点」页）；有已接入但 agent 离线的节点时再写「离线 K 台」。名单只由 agent 上报：一台 agent 都不在线时没有人能更新它，N 改写成「GPU 节点 N 台（名单截至 某时）」，那个时间是最后一个 agent 被看到的时候。节点刚接入时，名单可能还没轮到更新，所以 N 不会小于 M：接入的节点都有 GPU（只在有 GPU 的节点上装 agent），N 取名单与已接入节点数中大的一个。没有 `gpu` GRES 的节点只记名字，不计入 N、也不要求有 agent。名单只有最近一次，不保存历史；成员（节点名、GPU 数）变了才整表替换，状态与原因的变化只改变了的行，每个条目最多每分钟写一次；还没有上报时只显示「已接入 M 台」。
- **没有 agent 的 GPU 节点**：名单里没有在线 agent 的节点，列出节点名、原因（「从未接入」或「已接入，agent 离线」）和 Slurm 给的状态（如 `drained`、`down`），最多列 100 台。管理员可以在「已接入，agent 离线」的节点后点「移除」：只删除平台里的节点记录并把它从名单里去掉，不改动集群；节点其实还在集群里时，下一次健康检查会让它重新接入，下一次上报也会把它放回名单。常见原因：脚本目录在这台节点上不可见（不是共享存储又没复制过去）；节点连不上管理节点接入地址；节点在 Slurm 里被 drain 或 down，健康检查可能没有在上面运行。
- **节点随集群缩容**：节点的 agent 离线 15 分钟、而且不在最近一次上报的集群节点名单里（没有 GPU GRES 的节点、隐藏分区里的节点仍在名单里，不算离开），连续两次检查（约隔 5 分钟）都这样、节点上又没有实例时，平台自动删除这个节点。名单为空（还没有 agent 上报过）时不会删除任何节点。被缩容掉的正好是最后一台有 agent 的节点时，没有 agent 能上报不含它的名单：从阿里云 E-HPC 接入的条目改问云厂商（E-HPC 的 `ListNodes`，只在条目有离线超过 15 分钟的节点时问，每次检查每个条目一次），云厂商已经没有这台节点的，同样连续两次检查都这样、节点上没有实例时删除，并把它从名单里去掉；读不到云厂商的节点清单时不删。自己接入的集群没有这样的来源，用上面的「移除」。

## 修改、吊销、卸载、删除

管理员在这一行的「操作」里：

- **编辑**：可以改名称、记账账号、sbatch 参数、空闲归还和排队超时。保存不会在集群上做任何事，在线的 agent 在下一次上报时取到新设置（最迟 10 分钟）；已提交的占位作业保持原来的账号。其余字段创建后固定。
- **复制接入命令**：再给一次接入命令。
- **查看脚本**：打开接入脚本全文（Slurm 管控节点拿到的就是它），可以复制。脚本里的接入令牌显示为 `REDACTED-ENROLLMENT-TOKEN`，真正带令牌的是上面的命令。
- **吊销**：令牌作废，新节点不能再接入，已接入的节点不受影响；卸载用的脚本仍然可取。
- **卸载**：分两步，保证每个节点把自己的 agent 卸掉再摘掉健康检查。
  1. 在 Slurm 管控节点上以 root 执行 `curl -fsSL '…' | sudo sh -s -- --uninstall-agents`：脚本目录里放一个 `uninstall-agents` 标记（不在共享存储上时同样复制到各节点），每个节点的 `check.sh` 在下一次运行时执行 `gpuworks-agent uninstall`（见 [CLI 参考](../reference/cli.md#gpuworks-agent-uninstall)；agent 以普通账号运行时见上文，由 systemd 卸载），也不再安装。
  2. 等一个健康检查周期后执行 `… | sudo sh -s -- --remove`：把 `slurm.conf` 里的块去掉，还原被注释的原有 `HealthCheck*` 行（备份仍留着），`scontrol reconfigure`，并删掉 Slurm 管控节点脚本目录里的 `token` 和 `uninstall-agents`（脚本目录不在共享存储上时，各节点上复制过去的 `token` 不会被删，要的话自己删）。没有我们的块时什么也不做。

  弹窗里两条命令都给出；从云账号接入的集群由平台代为执行（两个按钮，第一步之后界面倒数一个健康检查周期，倒数完第二步才能点）。只执行第二步不卸 agent：已装的 agent 照常运行。
- **删除**：只删这里的集群记录，不卸载 agent，也不动 `slurm.conf`。集群下还有节点时拒绝删除（`SLURM_CLUSTER_HAS_NODES`）。卸载 agent、节点都离线之后，确认框里勾选「连同它的 N 个节点一起删除」可以一并删除；还有节点的 agent 在线、或节点上有实例时不能连同删除，确认框会说明原因。连同节点删除时先吊销条目、再删节点、最后删条目：节点删掉的瞬间健康检查不能再用令牌把它登记回来；吊销之后若有一步失败，条目保持已吊销。

## 阿里云 E-HPC

E-HPC 集群（2.0，Slurm 调度）的计算节点是普通 ECS 实例，集群在云账号下接入，不需要自己登录 Slurm 管控节点：

1. 按[租用云 GPU · 阿里云](rent-cloud-gpus.md#阿里云)添加阿里云账号并同步实例，账号的 RAM 权限要包含下面「云账号的权限」里的几项。
2. 展开账号。账号下的 E-HPC 集群由平台向阿里云读取（展开时先显示上次读到的列表，同时在后台重新读取，读完自动更新；同步之后等新的读取完成），每个集群一组，与账号的托管 Kubernetes 集群（ACK）并列、各自读取：一个读不到不影响另一个。平台先问 E-HPC 在哪些地域有服务，只在这些地域各自的 E-HPC 地址上询问，所以一个集群只列一次，地域就是它真正所在的地域。集群里还没有 GPU 节点、或账号还没同步过，集群照样列出，也能接入。组头写着集群名和 `Slurm 22.05.8` 这样的调度器版本，右侧是状态（运行中、创建中、初始化中、待配置、异常、已停止、释放中等，用颜色区分：运行中绿色，创建和初始化中蓝色，异常红色，其余灰色，只在组头说一次）；组内是「标签 值」的集群信息：集群 ID、地域、调度器和计算节点数（云厂商此刻列出的该集群计算节点数，含创建中和异常的，实时读取；云厂商不说其中哪些带 GPU，所以不写成 GPU 节点数；读不到这个数时改写「GPU 节点」，是上次同步到的带 GPU 的计算节点数）；接入后再加条目的信息（已接入节点、管理节点接入地址、脚本目录等）。集群的计算节点由队列扩缩，不在这里逐台列出（Slurm 管控节点和登录节点没有 GPU，也不列出）：已加入的节点在「计算节点」页，点「已接入节点」的数字就是只列它们的页面。Slurm 集群的组头有「接入」；调度器不是 Slurm 的集群（PBS 等）没有，组里提示目前只能接入 Slurm 集群；Slurm 集群还不在运行时也没有，组里用一句话写原因和接下来怎么办（还在创建：运行后可以接入；异常或已停止：先在 E-HPC 控制台处理或启动；释放中：不能接入）。云厂商不让这个账号列出集群时不算出错，只是列表为空，并安静地说明：密钥的 RAM 权限里没有 `ehpc:ListClusters` 时提示要放行的这个权限；账号没有开通 E-HPC 时写「该账号没有开通 E-HPC」并附云厂商返回的代码（不同地域的开通状态各自判断，开通了的地域照常列出）。个别地域读取失败（限流、该地域的 RAM 策略不放行、网络）时，其余地域的集群照常列出，顶部用警告列出没读到的地域和原因，那些地域里的集群可能没有显示；所有地域都失败时才是「读不到」，顶部给出原因和「重试」；账号下没有 E-HPC 集群时写「这个账号下没有 E-HPC 集群」。
3. 点「接入」，打开抽屉：名称已填好，填「管理节点接入地址」（填成平台自己的临时公网地址时这一栏会提示换成固定地址），需要时展开「高级」（字段同上），点「接入」创建条目。创建和应用是两步：创建好之后抽屉里有「检查并应用」，也给出接入命令和检查命令，想自己在 Slurm 管控节点上执行也可以。
4. 点「检查并应用」（组头的操作按钮写着名字，还没有节点接入时它是实心的主按钮；条目详情里也有同一个按钮，一行字说明由平台在集群的 Slurm 管控节点上执行，接入命令则折叠在「手动执行」下面，需要时再展开）：平台先让 Slurm 管控节点做一次不改动任何东西的检查，把计划列在弹窗里，见下文；你点「应用」之后才真正执行。应用完成后弹窗列出每一步的结果。现有的 GPU 节点在一到一个半健康检查周期内自动接入（默认最多约 7 分半钟）；以后队列扩容出来的节点在注册时就运行检查，通常几分钟内接入。接入后组头显示状态、GPU 节点数和操作菜单（编辑、检查并应用、复制接入命令、查看脚本、卸载、吊销、删除）。
5. 条目的集群如果已经不在账号里（被删除，或这次读不到列表），条目仍单独列为一组，说明原因，以便卸载、吊销或删除。

「检查并应用」不能用时不隐藏，而是置灰，悬停写原因（服务端给的代码，`operation_blocked`）：条目不是从云账号的集群创建的、云账号已删除、账号的驱动不能在 Slurm 管控节点上执行命令、账号的集群列表里没有这个集群（先检查账号和权限、或同步）、云厂商的集群列表还在读取（`cluster_listing_pending`，稍后自动再查）、集群列表读取失败或缺了某个地域（`cluster_listing_failed`，检查账号、权限和云厂商状态）、集群不是 Slurm、令牌已吊销（吊销只拒绝应用，仍可卸载）。

### 「检查并应用」做什么

先检查，后应用，两次都是平台向云助手发一个在 Slurm 管控节点上以 root 运行的脚本。检查（`dry_run: true`）读同样的东西、什么都不写：不追加 `gres.conf` 行、不写文件、不复制、不改 `slurm.conf`、不 reconfigure、不恢复节点，只报告下面三步分别会做什么；弹窗里列出：要追加的 `gres.conf` 行原文（以及已有行、云账号说有卡而 Slurm 没给 gpu Gres 的节点）、脚本怎么到达各节点（共享存储不复制，否则复制到哪些节点）、要加进 `slurm.conf` 的块、原位注释并串接的原有健康检查、会被恢复的节点、Slurm 管控节点和各 GPU 节点能否访问 server 地址（见下），以及需要注意的事项：`slurm.conf` 里有 `Include`、slurmctld 在跑而 `slurm.conf` 没写的程序、不是 configless、没有 gpu Gres 的节点、有主机访问不到 server 地址（这些会让应用以「有要手工处理的」收尾）。检查失败、被拒绝的原因同应用（见下文的错误码），失败时没有「应用」按钮，可以「重新检查」。应用是确认之后的第二次执行：

平台向云助手发的脚本在 Slurm 管控节点上以 root 运行。同一 Slurm 管控节点上同一时间只执行一次；平台最多等 6 分半钟。请求因为客户端等待超时断开后马上重试，上一次可能还在 Slurm 管控节点上执行，这时得到的是「Slurm 管控节点上已经有另一次配置在执行」（`SLURM_APPLY_FAILED`，原因 `busy`）：等几分钟再重试，不要连续点。它依次：

1. **补 `gres.conf`**：节点和卡数都由 Slurm 管控节点上的 Slurm 自己说了算，不依赖云账号有没有同步过实例：脚本读 `scontrol -o show node`，每个节点配置的 `Gres=` 含 `gpu:N`（带类型的 `gpu:a100:2`、带插槽后缀的 `gpu:2(S:0-1)` 也认，多条 gpu 相加；E-HPC 在 slurmd 登记时用 `--conf "Gres=gpu:N"` 配上它，所以没有 `gres.conf` 行、还没同步、名字不是 `<集群 ID>_<主机>` 的节点也在内）而 `gres.conf` 里没有 gpu 行的，在 `/etc/slurm/gres.conf` 末尾追加 `NodeName=<节点> Name=gpu File=/dev/nvidia0`（多卡为 `File=/dev/nvidia[0-N-1]`，N 就是它的 `gpu:N`）。已有它的 gpu 行（`Name=gpu` 或 `AutoDetect` 不为 `off`，且 `NodeName` 在行内任何位置的表达式覆盖它，或没有 `NodeName` 的通用 gpu 行）一概不动，别的资源的行、别的节点的行不算；云账号上次同步说有卡、而 Slurm 里 `Gres=` 没有 `gpu` 的节点不追加（补了 slurmd 会拒绝它），列在「Slurm 里没有配 gpu Gres、未补行的节点」下（同步没列到的节点不会有这条提示，但上面按 Slurm 的配置补行照常进行），要在 `slurm.conf` 里给它的 `NodeName` 行加 `Gres=gpu:<卡数>`。队列自动扩容出的节点，E-HPC 自己会写这一行（2026-11 实测）；随集群一起创建的初始节点没有，所以需要这一步。缺这一行时，slurmd 登记节点没有 GPU，Slurm 把它 drain（Reason 为 `gres/gpu count reported lower than configured`），Slurm 自己也不能在上面跑 GPU 作业。
2. **执行 setup**：取一次性地址下载接入脚本并执行，做的事同「接入命令做什么」：E-HPC 的 `/opt` 是集群共享的 NAS，脚本目录在共享存储上，不用分发。
3. **恢复被扣住的节点**：Slurm 因缺 GPU 扣住的节点（Reason 以上述文字开头）执行 `scontrol update ... state=resume`；管理员自己设的 drain 不动。

**访问 server 地址**：检查和应用都会问 Slurm 管控节点和每台 GPU 计算节点能不能访问条目的 `server_url`（`/healthz`）。Slurm 管控节点由接入脚本自己问；GPU 计算节点由平台经云助手逐个问：节点清单来自 E-HPC 的 `ListNodes`，只问有卡且在运行的节点，最多 8 台并发、总共 90 秒，与 Slurm 管控节点上的执行同时进行，所以不拖长检查。结果按主机列在弹窗和应用结果里，例如「计算节点 gpu000 访问不到 https://…：连接超时」；没能询问的节点（没在运行、云助手不在线、命令没执行完）单独列出，不算失败；列不出计算节点时（密钥没有 `ehpc:ListNodes`）写明原因。有主机访问不到时检查和应用都以「有要手工处理的」收尾，应用结果里多一步「各主机访问 server 地址」，待处理里说明要换成它们访问得到的地址再应用一次；条目详情里「为什么还没有节点」也据此给出原因。

Slurm 管控节点自己就取不到接入脚本时（检查或应用直接失败，`SLURM_APPLY_FAILED`，原因 `server_unreachable`），错误里写明它访问不到哪个管理节点接入地址和原因（域名解析失败、连接被拒绝或没有路由、连接超时、TLS 错误等）：节点要能访问这个地址。集群所在 VPC 没有公网出口时配置 NAT 网关，或把 gpuworks 部署在同一 VPC 内并填写内网地址。

可以重复执行（例如扩容之后）。结果是「集群已配置完成」，或「已配置，还有一些事需要手动处理」：待处理里列出脚本没能复制到的节点、没有 gpu Gres 的节点、没恢复的节点等。失败时给出出错的步骤和 Slurm 管控节点最后几行输出。

**一次性地址**：云助手的命令里只有一个一次性的 setup 地址（`/slurm/setup.sh?once=<随机码>`）。随机码只存在 server 内存里，十分钟内有效、Slurm 管控节点取一次就作废，apply 结束时没用掉的也作废，server 重启后作废（apply 本身是同步的，不受影响）。集群令牌只出现在 Slurm 管控节点下载到的脚本正文里，由脚本写进仅 root 可读的 `token` 文件，所以阿里云保留 30 天的云助手调用记录里没有令牌。卸载的两步用同样的办法。

### 云账号的权限

| 权限 | 用途 |
|---|---|
| `ehpc:ListClusters` | 逐个地域列出账号下的 E-HPC 集群（名称、调度器、状态）；没有它读不到 E-HPC 集群，列表顶部安静地提示要放行这个权限（不是报错），已有的条目仍单独列出；密钥的策略只放行部分地域时，其余地域的集群照常列出，没读到的地域用警告列出。没有 E-HPC 可以去掉 |
| `ehpc:ListRegions` | 问 E-HPC 在哪些地域有服务，只询问这些地域，列表因此更快、每个集群只列一次。没有它也能列出：改为逐个询问账号的每个地域，慢一些，没有 E-HPC 服务的地域可能显示为没读到。没有 E-HPC 可以去掉 |
| `ehpc:GetCluster` | 查 Slurm 管控节点的实例 ID，「检查并应用」和平台代为执行的卸载要用 |
| `ehpc:ListNodes` | 列出集群的计算节点（实例 ID、主机名、卡数、状态），用来逐台问它们能不能访问 server 地址，以及判断离线的节点是否已被缩容掉；没有它，检查和应用照常进行，只是不问计算节点，并写明原因，被缩容掉的最后一台节点要手动「移除」 |
| `ecs:DescribeCloudAssistantStatus`、`ecs:RunCommand`、`ecs:DescribeInvocationResults` | 经云助手在 Slurm 管控节点上执行脚本并读取结果，以及在各 GPU 计算节点上问它们能否访问 server 地址；这些节点上的云助手要在线 |

缺哪个权限，报错里会直接写出是哪一个（`SLURM_APPLY_PERMISSION_MISSING`），这时也可以自己在 Slurm 管控节点上执行接入命令。完整的权限清单与 RAM 策略见[租用云 GPU · 阿里云](rent-cloud-gpus.md#阿里云)。

不能「检查并应用」的原因（`SLURM_APPLY_NOT_APPLICABLE`，与列表里置灰的原因是同一组代码）：条目不是从云账号的集群创建的、云账号已删除、云上的集群不是 Slurm、账号的驱动不能在管理节点上执行命令、条目已吊销、集群既没有同步过节点、也不在账号的 E-HPC 集群列表里（检查账号权限，或先同步账号），或者这个列表还在读取（`cluster_listing_pending`）、读取失败或缺了某个地域（`cluster_listing_failed`，此时不能断定集群不在账号里）。集群的地域和调度器取自它上次同步到的节点，没有节点时取自云厂商的集群列表：它由 server 在后台单独读取（每个账号同一时刻只读一次，有自己的超时，不受哪个页面请求的等待时间限制），结果缓存 1 分钟；一个请求最多等 5 秒，等不到时用上一次读到的列表（最长 10 分钟），没有时显示「还在读取」，下一次轮询就有结果，所以按钮不会在可用与置灰之间来回跳。更换账号密钥或删除账号会丢掉缓存。

不能「检查并应用」时，条目详情在「还没有节点接入」这句下面给出接入命令，默认收在**接入命令**下，点开才显示，在 Slurm 管控节点上自己执行。

### 和线下集群的差异

计算节点由集群的队列扩缩，平台不给它们开关机、释放或调整规格（409 `PROVIDER_INSTANCE_IN_HPC_CLUSTER`），也不能逐台安装 agent：它们都通过集群条目接入。和 ACK 集群的节点一样，它们不在账号的实例列表里、不计入账号的实例数（「独立实例」组与同步提示里的数量都只算账号自己的实例），随集群作为一组显示。

| | 线下 Slurm 集群 | 阿里云 E-HPC |
|---|---|---|
| 怎么接入 | 外部平台 → 添加 →「Slurm 集群」，Slurm 管控节点上执行接入命令（先用检查命令看一遍） | 云账号下组头「接入」创建条目，再「检查并应用」：先检查、你确认后才应用，不用登录 Slurm 管控节点（也可以复制命令自己执行） |
| 脚本目录 | 默认 `/opt/gpuworks-slurm`，不在共享存储上时命令负责分发 | 同一个默认值，在集群共享的 NAS 上，不用分发 |
| 安装目录 | 默认 `/var/lib/gpuworks` | 同；不要放在 `/opt` 或 `/home`：它们是共享 NAS，所有节点会共用一份 agent 状态 |
| 模型存储 | 有共享文件系统时登记为「已挂好的共享目录」 | 同；集群 NAS 挂在 `/opt`，有节点接入后条目详情里可以一键登记，见[模型放在哪](#模型放在哪) |
| Slurm 配置 | 视集群而定，不是 configless 时要自己分发 `slurm.conf` | configless：slurmd 从 Slurm 管控节点取配置，`reconfigure` 之后自动生效 |
| gres.conf | 管理员维护 | 初始节点由「检查并应用」补行，扩容节点 E-HPC 自己写 |
| 分区 | 视集群而定 | 每个队列是一个分区，默认分区是 `comp`；占位作业自动用节点所在的分区（如 `gpu`），否则会一直以 `PartitionConfig` 排队 |
| 记账 | 视集群而定 | 开了 slurmdbd，只有 root 有关联，但不强制关联：普通用户没有关联也能提交作业 |
| 节点增减 | 管理员维护 | 队列扩容的节点自动接入；缩容释放的节点在平台上先离线，之后自动清理 |

## 模型放在哪

平台默认把模型下载到节点的默认存储（`default`）。经集群条目安装的节点，`default` 在这台节点上的目录是安装目录下的 `models`（默认 `/var/lib/gpuworks/models`，在本地盘上），每台节点各一份：部署换到另一台节点、队列扩出新节点时，都要再取一次模型。Slurm 集群通常有在各节点同一路径挂好的共享文件系统（NFS、Lustre、GPFS、BeeGFS、CephFS，E-HPC 的 NAS），把它登记成模型存储，所有节点共用一份：

从阿里云 E-HPC 接入的集群，有节点接入后条目详情里有一行「集群各节点共用 NAS：把 /opt/gpuworks-models 登记为模型存储……」和**登记为模型存储**按钮（管理员可见）：点它打开**存储 → 添加存储**，类型、目录、名称和按集群标签的适用节点都已填好，试挂通过后保存即可；这个集群的节点有了任何启用的共享存储后，这一行不再显示。其他集群按下面的步骤登记：

1. 在共享文件系统上建一个模型目录（如 `/share/models`），各节点同一路径都能读写；agent 默认以 root 运行，导出开了 root squash 时要给这个目录放开写权限。
2. **存储 → 添加存储**，类型选**已挂好的共享目录**，填这个目录；适用节点选按标签，标签 `gpuworks.ai/slurm-cluster`、值选这个集群条目，以后扩容进来的节点带着这个标签，自动适用。先**试挂**，通过后保存。
3. 部署时**保存到**选这个存储：第一次下载后，其他节点直接读这一份，见[部署时选存储](storages.md#部署时选存储)。

共享文件系统读起来比本地盘慢（比如容量型 NAS）时，引擎加载模型会更久。它是 NFS 导出时，可以改用 **NFS 加本地缓存**（由 agent 挂载，要填导出地址，节点要装 NFS 客户端）：模型在共享存储上只放一份，每台节点先拷到本地盘再读，见[添加一个 NFS 存储](storages.md#添加一个-nfs-存储)。

共享文件系统上的目录要登记成**已挂好的共享目录**，不要登记成**本地存储**：本地存储被当作每台节点各自的一份，放在共享文件系统上（比如 E-HPC 的 `/opt`）时，几台节点会往同一个目录下载同一个模型，在一台节点上删除模型会删掉所有节点的那份。存储页会在这样的存储名称旁标出橘色叹号。

## 运行时能看到什么

- **其他作业的卡**：节点卡片上显示 `Slurm job <作业号> (<用户>)`，不调度。
- **部署借卡**：占位作业名为 `gpuworks-hold-<实例 UUID>`，在 `squeue` 里可见，记在运行账号（或指定的记账账号、`-A` 的账户）名下。排队时实例进度显示 `waiting for Slurm job <作业号>: <原因>`，例如额度不够时的 `AssocGrpGRES`。
- **借到的卡与调度时选的不同**：Slurm 只按数量给卡。agent 用 Slurm 给的卡启动，平台随之把实例改到这张卡上。卡的型号或显存不同时，这次启动失败。
- **作业被结束**：管理员 `scancel`、时限或抢占结束了占位作业，用着这些卡的实例停止，消息写明作业号和 Slurm 给的状态，平台会重新调度。
- **agent 重启**：按作业名找回自己的占位作业（只认请求了本节点的作业：同一集群的 agent 用同一个账号提交，别的节点的作业留给它们自己的 agent），运行中的实例不受影响；重启后找回的作业在 10 分钟内不按空闲归还，因为 agent 要等 server 重新下发实例才知道哪些卡还在用，期间容器照常在这些卡上运行。agent 把提交过占位作业的记账账号记在状态目录的 `slurm-submitters` 里，所以条目的记账账号改过之后，早先账号名下的占位作业重启后仍被认作自己的（继续刷新、到点归还），而不是当成别人的作业一直占着卡。
- **Slurm 不在这台节点上启动作业**：节点被 drain、down，或登记时没有 GPU 时，占位作业会一直排队，部署要等满排队超时才失败。agent 每次上报都读一遍节点状态，发现这种情况平台就停止向该节点调度（节点显示“已停止调度”，原因 `slurm_node_unavailable`），节点详情的运行时一栏显示 Slurm 自己给的原因和手工恢复的步骤（命令可以直接复制）：缺 `gres.conf` 的节点是在 Slurm 管控节点上补一行、`scontrol reconfigure`、`scontrol update nodename=<节点> state=resume`；被管理员 drain 的节点是处理掉原因后 `resume`；down 的节点先查 slurmd。Slurm 恢复后平台自动解除；运维手动设的停止调度不受影响。E-HPC 集群的缺行问题用「检查并应用」一并处理。

## 限制

- 引擎容器在作业外运行：作业的 CPU 与内存只是记账，按需要在条目的 sbatch 参数里调大。
- 一个实例一个占位作业，作业里的卡一起归还。
- 只认 NVIDIA 卡；没有 GPU 的节点不装 agent。
- 不通过集群条目、而是在 Slurm 节点上当普通节点安装的 agent 仍会认出 Slurm 并借卡，它的设置来自环境变量 `GPUWORKS_SLURM`（`auto`、`on`、`off`）、`GPUWORKS_SLURM_NODE`、`GPUWORKS_SLURM_SBATCH_ARGS`、`GPUWORKS_SLURM_PENDING_TIMEOUT`、`GPUWORKS_SLURM_IDLE_RETURN`。经集群条目装的 agent 的节点名与设置都来自条目，这些变量不起作用（`GPUWORKS_SLURM=off` 例外：它让 agent 不进入 Slurm 模式）。
- 还不支持：没有 root 的集群（agent 在作业里运行）、Slurm on Kubernetes（如 Slinky）、NVIDIA 以外的卡、提交前预检额度、按作业剩余时限接力。
