# 使用 AI 助手

**适用场景**：实例启动失败时找根因和修法；判断一个模型在当前集群哪些卡上能跑、要几张卡；部署的副本为什么调度不上；节点和加速卡是否健康。

**前置条件**：

- server 已运行并能登录控制台，见[从零启动并部署第一个模型](../tutorials/getting-started.md)。
- 想要 AI 解读时，需要一个 OpenAI 兼容端点：base URL、模型名和 API key，在“设置 → AI”配置；key 由 server 加密保存。不配置也能用平台检查（见下）。

## 入口：点一下就开始，不需要写提示词

助手是一个常驻右侧的侧边栏，切换页面不会关闭，打开时页面照常可用。不需要自己写提示词：每个入口对应一个「任务」，点下去 server 会自己收集该收集的信息。

| 任务 | 入口 |
|---|---|
| 实例失败诊断 | 部署详情里失败实例面板上的「AI 诊断」 |
| 模型硬件适配 | 「模型」页每个模型上的 AI 按钮 |
| 部署为什么调度不上 | 部署详情里「副本等待节点」提示旁的「为什么调度不上」 |
| 节点健康检查 | 节点详情右上角的「AI 健康检查」 |

也可以点顶栏的「AI 助手」或按 ⌘I / Ctrl+I 打开侧边栏：
- 空白时会列出当前页面上的对象（正在看的部署、节点、失败实例），需要关注的排在前面并标出原因，点任务按钮即可开始。
- 下方输入框可以自由提问，默认针对页面上的第一个对象，可以在「关于」里改选或取消。

每个回答结束后会给出两三个推荐追问，点一下即可；也可以在输入框继续追问。追问会沿用同一个任务和对象，并带上之前的对话。「新对话」会清空当前对话。

## 两部分：平台检查和 AI 分析

| 部分 | 内容 | 需要 LLM |
|---|---|---|
| 平台检查 | 失败实例：日志命中的已知故障（显存不足、KV cache 放不下、NCCL/HCCL 通信失败、`/dev/shm` 不足、磁盘满、端口占用、镜像拉取失败、GPU 架构或数据类型不支持、需要 `--trust-remote-code`、引擎不支持该架构、模型文件缺失、模型仓库下载失败），附命中的日志行和修法。模型：在线集群每种加速卡的硬件适配表（可用卡数与故障卡数、能否运行与最小 TP、精度支持、同节点高速互联组、每卡需要/可用显存、留给 KV cache 的余量）。适配表只讲硬件事实，不代表现在有空闲卡，能否立即部署以部署页的候选节点为准 | 否 |
| AI 分析 | 根因、证据和具体修法（例如要改的引擎参数和新值、需要腾出卡的节点） | 是 |

## AI 分析怎么工作

server 先按引用读取对象，把第一步预先做好：
- 失败诊断：失败消息、实际启动命令、节点硬件、调度解释与显存拆分、最近的实例事件、日志（最新 60 行加更早的最多 40 行 error 级日志，上限 8 KB）。
- 调度不上：每个副本需要什么、节点约束、放置策略、已有实例，以及调度器最近一次拒绝的原因（各状态候选节点数、最接近的节点和差什么）。
- 节点健康：每张卡的健康等级与 agent 证据、节点状态与调度状态、上面的实例、节点和 agent 最近的告警与错误日志。

这些连同一份清单一起交给模型；清单写明哪些内容被截断、去哪里能取到更多。

模型在整个回答过程中都能读平台的只读 API，读到的和提问的用户在界面上能看到的一样（同样的权限、同样的数据）：

- `cluster_overview`：一次读到集群概况——节点按状态的数量与容量、GPU 健康与分配、部署数量，以及需要关注的节点（离线、降级）和部署（失败、待调度）。
- `search_api` / `call_api`：在 [API 参考](../reference/api.md)里按关键词找接口，再读它。列表默认只取 20 条、长字符串截到 300 字、单次结果上限 12000 字符，截断处都会注明；模型可以用 jq 只取需要的字段。时间统一显示为 UTC 加「多久以前」；凡是要节点 uuid 的地方也可以直接写节点名。
- `search_metrics`：在指标目录（`GET /api/v1/monitor/metrics`）里找时序指标，再用 `call_api` 读 `/api/v1/metrics/query`。
- `get_gpu_topology`、`compare_with_healthy_replica`：节点的卡间互联，以及失败实例和同部署运行中副本的差异。

上下文够用时一次调用就回答；不够时自己继续查，最多 10 轮，同一轮里的多个工具并行执行（同时最多 4 个），剩 2 轮时会提示模型尽快作答。一次回答最多调用 30 次工具，超出的调用不执行，模型会收到「已用完」的提示。每个用户同时最多有 2 个问题在处理，再提问会被拒绝（429 `AI_ASK_BUSY`），等其中一个结束即可。

助手看不到的内容：API key、AI 端点配置、节点 SSH 设置与平台 SSH key、终端与终端审计记录、节点文件浏览、实时日志流（日志用检索接口读），以及会访问外部仓库的社区镜像浏览。交给模型之前，返回值里的凭证会被替换成 `[redacted]`：
- 名为 `token`、`secret`、`password`、`api_key`、`access_key`、`credential` 一类的字段，包括环境变量（如 `HF_TOKEN`、`AWS_SECRET_ACCESS_KEY`）和 `{name, value}` 形式的环境变量项；
- 写在字符串里的凭证：启动参数（`--api-key sk-…`、`--hf-token=…`，argv 数组里紧跟在这类参数后面的那一项）、`password=…` 一类赋值（挂载选项、命令行里的 `export HF_TOKEN=…`）、URL 里的用户名密码、`Bearer` 令牌。

数值不会被替换（如 `--max-num-batched-tokens 8192`、`max_tokens=512`），诊断需要它们。`TestAssistantReadsNoPlantedSecret`（`internal/integrationtest/aiassistant`）在各处植入凭证后，以管理员身份经 `/ai/ask` 读遍所有开放的 GET 路由，断言交给模型的内容里一个都没有。新增的 GET 接口要先在 API 参考里写明，或在 `aihelper` 里列为不可读，助手才会用到（`TestEveryGETRouteIsClassified`）。

助手读到的数据会发送给所配置的 AI 服务。设置页的 AI 服务卡片会写明发往哪个主机；配置的是本平台部署的模型（地址与控制台同源）时不显示这条提示。

平台检查命中的已知故障只作为待验证的假设交给模型，模型要对照日志说明它是否成立。适配表的数字由估算器给出，模型只负责解释，不重新计算。

回答是流式的：每次工具调用开始和结束时都会出现在步骤列表里，推理过程（推理型模型才有）折叠在「推理过程」里，正文逐字出现。回答结束后显示首字时间、总耗时、调用次数和 token；server 日志里每次回答也会记一条 `ai answer`，带同样的数字。

关闭抽屉再打开会保留结果；「重新分析」会重新读取并提问。分析中可以随时「停止」，平台检查结果不受影响。

## 边界

助手只读：不会执行部署、删除或修改。建议中的节点、参数和错误证据，请回到对应页面核对后再操作。适配表只算权重加引擎预留，未考虑多机部署和量化版本。外部 Playground 模型只支持 `/api/v1/playground/v1/chat/completions`，不会把外部 key 暴露给实例。

## 评测

`internal/server/aihelper/testdata/eval/` 收录了真实或按上游报错原文构造的引擎启动失败用例。`go test ./internal/server/aihelper/` 离线校验已知故障规则对每个用例的命中情况；`go test -tags aieval -count=1 -v -timeout 60m ./internal/server/aihelper/ -run '^TestLiveEval$'` 用真实端点对每个用例分别跑三种方式——只用工具、只用预组装上下文、预组装加工具——并输出关键修法词命中数、调用次数、token 和耗时（所需环境变量见 `TestLiveEval` 的注释）。
