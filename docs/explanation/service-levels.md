# 出让策略与服务等级：几个部署怎样共用一批 GPU

本文解释出让策略是什么、四个服务等级怎样是它的预设、平台按什么规则让一个部署为另一个让卡，以及这些规则背后的取舍。操作步骤见[使用调度中心](../how-to/scheduling-center.md#服务等级与休眠)，决策记录见 [ADR 0059](../adr/0059-service-levels-and-the-residency-arbiter.md)。

## 为什么需要

可休眠的部署睡下后只在卡上留一点残留，其余显存可以给别的部署用。于是同一批卡上可以放几个部署，同一时刻只有一部分醒着。难点是“谁该醒着”：

- 实时对话随来随用，批处理只要卡空着就该跑；实时来了请求，应该马上把卡拿回来。
- 几个都不常用的模型轮流用一批卡，谁有请求谁醒，但不能来回抖：切换本身要几秒，太频繁就谁都服务不了。
- 没有人和它抢卡，但长时间没人用的模型，也可以自己睡下把显存和功耗省出来。

这三种需要在一个部署上由一个**出让策略**加几个只在适用时才出现的参数来表达，平台按一条规则执行，每个动作都写进时间线。

## 出让策略

出让策略决定部署会不会、什么时候把卡让给别的部署，也就是谁可以抢谁。规则只看这一项。

| 策略 | 含义 | 等级 |
|---|---|---|
| 从不出让（`never`） | 从不把卡让给别的部署。被平台休眠后有请求时，可从闲置自动出让、时间片轮流、随时出让的部署手里拿卡 | 最高 |
| 闲置自动出让（`idle`） | 别的部署在等它的卡、且它已闲置（没有进行中或挂起的请求）满闲置时间，才让出 | 可抢时间片轮流、随时出让 |
| 时间片轮流（`timeslice`） | 与同在这批卡上的其他时间片部署轮流：每轮至少提供最短服务时间，等卡者最早的请求已等满 30 秒才轮到；对从不出让、闲置自动出让的等卡者立即让；闲置满闲置时间时对任何等卡者都让 | 可抢随时出让 |
| 随时出让（`anytime`） | 对任何更高等级的等卡者立即让；对同为随时出让的等卡者，只在自己闲置满固定的 30 秒（不可配置）后让 | 最低 |

两个闲置自动出让的部署不能共用一张卡：两边都忙时谁都不让，各自的请求会一直等对方。平台在改策略时拒绝，放置时也不会把一个闲置自动出让的部署放到另一个的卡上。从不出让以外的策略只用于可休眠的单机部署；多机与 PD 部署的策略必须是从不出让（但可以打开自动休眠）。

### 参数

界面只显示对当前策略适用的参数；API 接受不适用的参数、忽略它们，响应里也不返回。

| 参数 | 含义 | 适用于 |
|---|---|---|
| `idle_sec` 闲置时间（30–604800 秒） | 多久没有请求算闲置 | 闲置自动出让、时间片轮流（闲置满这么久，有人等卡就让）；任何策略下只要打开了自动休眠 |
| `auto_sleep` 无抢占时自动休眠 | 没有别的部署等它的卡，也闲置满闲置时间就休眠。这是平台自己做的休眠，不是保持休眠，之后有请求会唤醒它 | 所有可休眠部署，包括多机与 PD |
| `sleep_level` 休眠级别 | `auto`：L1，主机内存放不下权重时退回 L2；`l1`：严格 L1，主机放不下就拒绝，同运维手动下的 L1 休眠；`l2`：L2。适用于平台替这个部署选的每一次休眠（让卡、自动休眠），运维和定时计划下的休眠不受影响 | 策略不是从不出让，或打开了自动休眠 |
| `min_serve_sec` 最短提供服务时间（0–3600 秒） | 唤醒后至少保留卡这么久才轮得到别人；驻留仲裁会把它抬高到 10 倍实测切换时间（更大时） | 时间片轮流 |
| `unfinished` 出让时未完成请求的处理 | `abort` 立即中断；`wait` 等它们完成，最多 `unfinished_wait_sec` 秒（1–600），到时仍有的被中断；`wait_unbounded` 等完成，不限时 | 时间片轮流、随时出让（闲置自动出让只在闲置时出让，那时没有请求在跑；从不出让从不出让） |
| `hold_max_sec` 请求最长挂起时间（10–1800 秒） | 部署醒来期间网关最多替请求挂多久，超时回 503 并带 `Retry-After` | 策略不是从不出让，或打开了自动休眠 |

`wait_unbounded` 要小心：一个很长的请求（例如长输出的生成）会让等卡者一直等下去，等卡者的请求在网关里最多挂到它自己的 `hold_max_sec`，然后得到 503。不确定时用有限的 `wait`。

## 四个服务等级是预设

四个服务等级是出让策略加一整套参数的预设：

| 预设 | 策略 | 参数 |
|---|---|---|
| 常驻（默认） | 从不出让 | 自动休眠关 |
| 在线 | 闲置自动出让 | 闲置时间 300 秒，休眠级别 `auto`，请求最长挂起 120 秒，自动休眠关 |
| 分时 | 时间片轮流 | 闲置时间 60 秒，最短服务时间 120 秒，未完成请求等待完成（最多 30 秒），休眠级别 `auto`，请求最长挂起 600 秒，自动休眠关 |
| 离线 | 随时出让 | 未完成请求立即中断，休眠级别 `auto`，请求最长挂起 1800 秒，自动休眠关 |

预设不单独存储，部署上存的只有策略和参数。界面和 API 里看到的预设是拿存下的策略和参数与四个预设逐项比较得出的：完全一致就是那个预设，改动了任何一项（比如把在线的闲置时间改成 30 秒，或给常驻打开自动休眠）就是**自定义**。选一个预设就是把它的整套参数填进去。

## 让卡规则

等卡的部署 W 可以让醒着的部署 H 休眠，当且仅当 H 的策略不是从不出让，并且满足下面任一条：

1. **空闲**：H 没有进行中、也没有挂起的请求，已经满它的让卡闲置时长（闲置自动出让、时间片轮流为 `idle_sec`，随时出让固定 30 秒）。
2. **等级**：H 可被抢（时间片轮流、随时出让），且 W 的等级更高（从不出让 > 闲置自动出让 > 时间片轮流 > 随时出让）。
3. **轮流**：H 与 W 同为时间片轮流，H 这一轮已驻留满最短服务时间，且 W 最早的请求已等满 30 秒。最短服务时间取 `min_serve_sec` 与 10 倍切换时间中较大的一个，让切换开销只占服务时间的一小部分。

W 要的卡上若有几个醒着的副本，要么都让，要么都不让：只让一部分会停掉服务，又腾不出地方。几个部署同时在等时，等级高的先，同级里等得最久的先，所以同级不会饿死；更低的等级在设计上可以被饿着，比如实时一直忙时，批处理就一直等。

## 一次让卡怎样进行

1. 请求到达睡着的部署，网关挂起请求并通知驻留仲裁（100 毫秒内处理）。
2. 仲裁先试正常唤醒；放得下就唤醒，网关在部署醒后放行请求。
3. 放不下时按上面的规则判断占卡者。要让卡：
   - 因闲置而让的，占卡者没有请求在跑，直接休眠；
   - 否则按占卡者的 `unfinished` 处理还在跑的请求：`abort` 立即休眠并中断它们；`wait` 与 `wait_unbounded` 先让网关停止给它接新请求（新请求同样挂起），等进行中的请求结束再休眠；`wait` 最多等 `unfinished_wait_sec` 秒，到时仍有请求就中断，`wait_unbounded` 一直等。全部做完才休眠的，以 `mode=wait` 休眠；到时被中断的，以 `mode=abort` 休眠。
4. 占卡者确认睡下、卡上只剩残留后，等卡者被唤醒，挂起的请求放行。
5. 被让卡的时间片轮流、随时出让部署记入待恢复，卡再空出来时按同一条规则拿回。

被中断的非流式请求由网关挂起，部署恢复后重放（最多 3 次），客户端只看到跑完的结果。流式请求已经开始输出，无法重放：客户端看到正常结束的 HTTP 200，`finish_reason` 为 `"abort"`，内容被截断，应据此重试。长任务可交给平台托管的[批处理任务](../how-to/batch-api.md#与离线服务等级搭配)，被中断的请求由它自动重试。

## 为什么平台选的休眠默认用 L1

在 L20 上实测（vLLM 0.17.1，7B 与 14B 模型）：两个模型同卡互换，从让出方休眠到被唤醒方出第一个 token，L1 约 2.5 秒；L2 在模型文件留在页缓存里时约 3.5–5 秒，要从磁盘读时 14B 需要 40–110 秒。引擎第一次 L1 休眠会钉住约 1.9 倍权重大小的主机内存，唤醒后也不释放；而平台在每个可休眠实例启动后都会做一次 L1 预热（掩盖首次休眠的十几秒），所以这块内存从启动起就已经占着。L1 因此不再多占主机内存，切换最快，也不依赖页缓存。

所以休眠级别默认 `auto`：先 L1，主机可用内存放不下权重时（估算偏保守）退回 L2。要严格的 L1（放不下就拒绝，而不是悄悄变慢）选 `l1`；愿意用切换时间换主机内存的选 `l2`。

这也意味着：**打开可休眠的部署，从启动起就占着约 1.9 倍权重大小的主机内存**。同一台主机上多个可休眠部署时，要按这个量规划主机内存。

## 保持休眠

运维或定时计划下的休眠是保持休眠：请求不唤醒它，网关仍回 503，免得请求推翻运维的决定。平台自己做的休眠（无抢占时自动休眠、让卡）不是保持休眠，有请求时会被唤醒。任何一次唤醒都解除保持。

## 放置怎样为共卡留位置

一个按出让策略共卡的部署（策略不是从不出让）睡着时，对与它不共卡的部署（从不出让，或对闲置自动出让而言另一个闲置自动出让）仍按全量占用计算，所以不会有部署落到它的卡上让它醒不回来；对时间片轮流、随时出让的部署只计残留，它们可以放上去。创建部署时就可以选预设，放置和预览都按它的策略计算。

## 限制

- 从不出让以外的策略只覆盖单机部署；多机与 PD 部署的策略必须是从不出让，自动休眠不受此限。
- 新部署启动时卡被醒着的部署占着，平台不为启动让卡，新部署按放不下等待，等对方让卡或休眠后再放。
- 挂起的请求、每轮驻留起点、待恢复名单都在 server 内存里：server 重启后，被让卡的部署要等到有请求时才唤醒。
- 随时出让、时间片轮流部署被中断的请求需要客户端重试；平台托管的[批处理任务](../how-to/batch-api.md#与离线服务等级搭配)（`/v1/batches`）会自动重试，直到任务过期。
- 评估器每 10 秒看一次自动休眠与让卡的条件，所以实际休眠时刻最多比闲置时间晚一个 tick（请求触发的让卡在 100 毫秒内处理）。
