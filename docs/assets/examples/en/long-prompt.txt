Qinghe Archives Collaboration Platform: Six-Week Pilot Record

About this material: This is a synthetic exercise for evaluating long-document comprehension and summarization. The project, people, organizations, dates, business volumes, and performance metrics are fictional. This is not an actual system log or a record of measured results. Operational decisions in the text are for analysis only and should not be applied directly to production changes.

1. Project Scope and Delivery Boundaries
The Qinghe project is building an internal archives collaboration platform for three community archives, providing catalog search, file previews, requests to add missing information, and review notifications. The first phase accepts only public exhibition materials and work records that have already been de-identified; it does not collect residents' identity information. The archives want staff to complete searches during opening hours and import new catalogs in batches after closing. The project team has divided the pilot into six weeks: connect one archive first, then the other two, and finally conduct a handover exercise. Acceptance covers whether users can complete their work, whether data can be recovered, whether faults can be detected, and whether on-call staff can handle them using the documentation. The team explicitly excludes full-text recognition and automatic classification. These will be evaluated separately in a later phase, and entry points for unimplemented features must not appear in the first-phase demonstration.

2. Responsibilities and Time Windows
Product lead Lin Zhou confirms business priorities, application lead Chen He maintains APIs and background jobs, infrastructure lead Xu Lan manages compute, storage, and networking, and archives administrator Zhou Ning checks catalogs and access permissions. One technical staff member is on call each working day; on weekends, only incidents affecting all users are handled. The archives open from 9 a.m. to 5 p.m., and the normal release window is the hour after closing. Emergency changes outside that window require confirmation from both the business lead and the technical staff member on call. The responsibility matrix prepared before the pilot omitted the contact for the notification email provider and did not specify who should take over an import job that remained unfinished into the next day. Both gaps were discovered during the first on-call review.

3. Initial Resources and Deployment Conventions
The platform runs on two application nodes and one separate data node. The application nodes provide the same external service, with an ingress gateway distributing requests. The data node stores the catalog database, files go into shared storage, and caching is used only to accelerate repeated reads. The team agreed that business files must not be written to temporary directories in application containers, configuration must be managed through a unified inventory, and release packages must retain their version numbers and checksums. Initial checks found different log retention periods on the two application nodes: seven days on one and thirty days on the other. Another difference was the location of the preview cache directory, with an old script still pointing to the system disk. The team added these differences to the fix list but had not yet established a check that could compare node configurations automatically.

4. Catalog Import in Week One
The first archive submitted eight thousand catalog records, including files with the same name, missing dates, and duplicate identifiers. The import program could reject records with invalid formats, but it did not include rejection reasons in a report that business staff could download. The administrator had to search backend logs for failed rows, so the first import was submitted three times. The application lead added batch identifiers and per-row results, with the rule that retrying the same batch would not create duplicate catalog records. A subsequent spot check found two records with different identifiers pointing to the same file. The team decided to retain support for reusing files while showing reference relationships in the UI. Deleting a catalog record must not also delete a file still used by other records.

5. Initial User Feedback and Priorities
Ten staff members each completed four tasks: search, preview, request missing information, and withdraw a request. Searches had a high success rate, but users could not find the corresponding records when entering an archive's former name, so an administrator-reviewed alias table was added. The preview page was slow to open the first time and noticeably faster the second time. At that point, only total page load time was recorded, without separating file reads, format conversion, and browser rendering. The product lead required additional measurement before choosing an optimization, to avoid attributing every delay to the network. Continuing to receive old notifications after withdrawing a request was prioritized for correction because reviewers might keep processing withdrawn items, leaving business records inconsistent with email content.

6. Peak-Period Observations in Week Two
After the second archive was connected, the burst of searches just after opening in the morning increased substantially. During one observation, most short catalog queries finished quickly, while lists containing many thumbnails showed long-tail delays when users changed pages. Application logs showed requests waiting for the file preview queue; database queries had not slowed at the same time. The on-call staff member temporarily increased background job concurrency. The queue shortened, but shared-storage read latency began to rise. The team restored the original settings and put catalog queries and preview generation in separate queues. This intervention showed that a shorter local queue does not necessarily mean the whole system is healthier. Future capacity assessments must consider foreground response times, background backlogs, and storage load together rather than selecting just one metric.

7. Storage Growth and Space Warnings
At the end of week two, the team measured space usage separately for files, preview caches, intermediate import files, and logs. Original files were growing as expected, but the preview cache contained incomplete outputs left by repeated conversion failures. The remaining system-disk space could support current work, but the observed growth rate meant it would not cover the following month's batch imports. The infrastructure lead proposed moving the preview cache to a dedicated directory and adding a periodic cleanup policy. Before cleanup, the team must identify jobs that are still writing and files that are still referenced; modification time alone cannot justify deletion. The administrator requested before-and-after space-usage reports and procedures for recovering accidentally deleted files. Neither deliverable was in the original release plan.

8. Backup and Recovery Exercise
The database is backed up every day after closing, while original files use a separate version-retention mechanism. The first recovery exercise took place in an isolated environment. The team restored the catalog list but found that some preview links still pointed to addresses in the old environment. The cause was an address-mapping file omitted from the configuration inventory. After the file was added, sampled searches and downloads passed. However, the exercise covered only the first archive's data and had not verified backup consistency during simultaneous imports from all three archives. The business lead considered a successful backup-job status insufficient proof of recoverability and required the next exercise to record recovery duration, the actual point in time to which data could be restored, and whether permissions, file references, and pending requests were complete after recovery.

9. Release Attempt in Week Three
The week-three release was intended to add notification deduplication and preview queue isolation. Before release, testers verified the new APIs and normal workflows but missed the case where old batch jobs continued running after the new version started. After the first application node was upgraded, some old jobs remained in retry because fields were missing. The team paused the second node's upgrade, directed traffic back to the old version, and retained failed jobs for analysis. The fix was to provide an explicit compatibility path when reading old fields, count unfinished batches before upgrading, and check each batch's status afterward. The rollback checklist was also expanded to include background job version requirements, preventing a rollback that restored only the foreground application while overlooking job processors still running.

10. Notification Delivery and External Dependencies
The notification module sends review results to staff and retains the same content in the platform. During one email delay, the business page still showed that a request had been processed successfully, but the user mistakenly thought the operation had not taken effect and submitted it again. Investigation found that the platform had generated the notification successfully, while the external delivery service was retrying and its status was not promptly reflected in the UI. The team decided to display business completion and notification delivery as separate statuses and add a prominent warning for duplicate submissions. Notification delays beyond the agreed threshold should alert on-call staff, while users must be able to view the official result within the platform. A provider failure must neither roll back the review transaction nor fill other background job queues through unlimited retries.

11. Metric Definitions and Alert Adjustments
The original dashboard showed average response time across all requests, which could hide a small number of slow preview requests. The team began observing request counts, failure rates, and latency distributions separately for search, preview, import, and notifications, retaining request identifiers for tracing. Import jobs needed to record not only completed counts but also the waiting time of the oldest unfinished job. Storage monitoring needed to track growth trends and estimated days of remaining capacity as well as percentage used. After the first alert adjustment, brief batch imports triggered many notifications, making urgency difficult for on-call staff to judge. Later, the team set duration and recovery conditions for each business function and included impact scope and where to investigate in alerts, reducing notifications that provided numbers without guidance on what to do.

12. Permission Spot Checks in Week Four
Before connecting the third archive, the administrator spot-checked access to catalogs across archives. Public catalogs were searchable by all archives, while internal work records were accessible only to their owning archive and designated reviewers. Testing found that once a preview link had been saved in a browser, revoking catalog permissions did not immediately revoke the temporary access URL already issued. The team confirmed that the URL had an expiration time. Shortening its validity would reduce the exposure window but require more refreshes during long reading sessions. The business lead required effective revocation to take priority for sensitive material types while preserving convenience for public materials. Final parameters still needed business confirmation. The current record proves only that this tradeoff was identified; discussion alone must not be treated as closure of the permission issue.

13. Connecting the Third Archive and Data Quality
The third archive's catalog used a different date notation, and some titles contained historical names. Applying the first two archives' validation rules unchanged would reject many genuinely valid records. The team added retention of the source archive and original fields, storing normalized results separately so administrators could review the basis for conversion. Spot checks had to include both successfully converted and rejected records, avoiding quality conclusions based only on successful samples. The archives administrator also specified that incorrect dates could be left blank temporarily but must not be filled in by programmatic guesses. Records requiring human confirmation should enter a review-pending list. The end-of-pilot data quality report therefore needed separate counts for complete records, records awaiting confirmation, and records confirmed as invalid.

14. Failure Exercises in Week Five
After closing, the team simulated one application node going offline. The ingress gateway could redirect new requests to the other node, but jobs already performing preview conversion did not move immediately, and some users saw an unchanged waiting status. Other processors could take over only after job leases expired, and the UI did not show this recovery wait. The application lead added job heartbeats and timeout messages, while business staff requested explicit guidance on whether users needed to resubmit. Another exercise simulated a brief shared-storage outage. Searches could still return catalog records, but preview and import operations failed. The team used this result to describe the impact separately for each function, avoiding a broad declaration that the whole platform had recovered when only some functions were available.

15. Capacity Experiments and Sample Limitations
The capacity experiments used three workloads: search only, mixed search and preview, and foreground queries running alongside batch imports. All groups used the same data volume, request sources, and measurement window, and the team first confirmed that no import jobs were left over. Results under mixed load were noticeably worse than under search alone, showing that release notes must not cite only the fastest group. The team also found that reopening the same set of files produced many preview cache hits and did not represent the wait for first access to new archive materials. Future results therefore needed to state cache conditions, file-size distribution, concurrency, and the number of failed requests. Current samples came mainly from weekday daytime activity and did not cover concentrated public-opening events during holidays, so they should not support capacity promises for every period.

16. On-Call Handover and Knowledge Organization
The week-five handover exercise was performed by a new on-call staff member who had not participated in development. This person could use alerts to find slow requests but did not know when jobs could be retried or how to distinguish missing data from a temporary read failure. The team rewrote troubleshooting material as short procedures organized around specific symptoms: first establish the impact scope, then find the request or job identifier, inspect its current status and latest error, and finally decide whether to escalate or recover using an approved procedure. Operations involving file deletion, permission changes, or reimporting must first verify the target objects and their reference relationships. Handover material should also identify owners and contact details, rather than making “contact the developers” the only troubleshooting method.

17. Cost Records and Optimization Order
The team recorded costs separately for compute, shared storage, backups, and external notifications, finding that frequent preview generation consumed more compute time than storing original files. One proposal was to extend retention for every cache; another was to restrict preview formats and resolutions. The archives pointed out that some drawings required fine detail, so uniformly reducing quality would impair work. Policies should instead vary by usage frequency and material type. The team decided to eliminate ineffective retries and duplicate conversions first, then evaluate cache retention periods, and only afterward consider adding nodes. Cost records must be reviewed alongside users' ability to complete tasks; apparent resource savings must not come from reducing the availability of necessary functions.

18. Acceptance Dispute in Week Six
At the acceptance meeting, the technical team submitted continuous-operation records and average response metrics. The business team raised three unfinished requirements: batch failure reports should identify original rows directly, the recovery exercise should cover data from all three archives, and preview behavior after permission revocation needed a clear explanation. Both sides agreed to assess “functions are usable” separately from “the delivered system can be operated independently.” Completed search, request, and notification functions could enter controlled trial use, but new large batch imports had to wait for the recovery exercise results. The project lead required every open item to have an owner, a completion date, and a retest method, rather than retaining statements such as “continue optimizing” that offered no way to judge completion.

19. Next Observation Round
The next round was planned to run for five working days, keeping the same request categories and metric definitions while adding separate samples for first-time previews and cache hits. The recovery exercise would select a point in time containing data from all three archives and pending requests, after which the administrator would spot-check permissions and file references. The release exercise would cover old jobs continuing across versions and rollback after failure; the on-call exercise would be completed independently by a new member. The team would not add application nodes yet, to avoid masking shared-storage and job-scheduling problems before their causes were clear. If existing resources truly reached their capacity limits, the team would evaluate the benefits of expansion under the same workload and record whether it improved both foreground latency and background backlogs.

20. Log Correlation and Information Protection
During the pilot, every component could produce logs, but ingress request identifiers were not consistently passed to background jobs, forcing investigators to infer relationships from times and filenames. The team decided that user operations, import batches, preview jobs, and notification records should retain the necessary correlation identifiers so an abnormal record could be traced through related stages. Logs should not record entire file contents or private notes entered by users, and temporary credentials in access URLs must be concealed before troubleshooting material is shared. The infrastructure lead also checked node clocks, requiring a common time zone and sufficient timestamp precision for analysis across nodes. Existing daily reports gave times only to the minute and could not distinguish multiple retries within one minute. They were therefore suitable for observing trends but could not replace per-request records. Log retention must balance incident investigation against storage costs; before expired logs are cleaned up, necessary evidence for confirmed incidents should be archived separately.

21. Client Waits and Repeated Actions
On some older computers, opening large files left the browser with no visible change for a long time. Staff clicked preview repeatedly, generating multiple identical jobs and increasing queueing. The application team added an in-progress status and reused results when a valid job already existed for the same file. The frontend waiting limit and gateway timeout had previously been inconsistent: the browser reported failure while the background job continued consuming resources. The team required the next integration test to distinguish user cancellation, ingress timeout, and background failure, and to verify whether cancellation could propagate to the corresponding job. For conversions that could not be canceled immediately, users should be told that the job might still finish and given a way to view it. Acceptance of this improvement must check more than whether the page shows a spinner: it must also check whether retries duplicate resource consumption and whether completion status is accurately reported to the page where the action began.

22. Training and Actual Workflows
Training exercises followed the real work sequence: find materials, check their version, submit a request to add missing information, and view the result. Early materials introduced page buttons one by one. Although trainees knew where each button was, they still did not know whether to edit a catalog record directly or submit a request when its date was missing. The administrator added complete examples for roles with different permissions and clarified that ordinary staff could only propose changes. Two trainees used low-resolution screens where list actions were hidden in a collapsed menu, leading them to believe that withdrawal was unavailable. The team added accessibility checks to trial feedback, covering keyboard operation, help text, zoomed display, and locating errors. After training, the team recorded whether each task was completed independently rather than judging ease of use only by attendance or satisfaction scores.

23. Withdrawing Materials and Long-Term Retention
The first archive requested that some temporary exhibition materials stop being public after the exhibition ended, while catalog change records remained available for internal searches. The team therefore distinguished withdrawing public access, archiving, and permanent deletion: withdrawing public access changes only the access scope; archiving retains files and review records; permanent deletion requires checking reference relationships and completing approval. The existing bulk-action UI offered only a “Delete” button and could not express these three intentions. The administrator worried that an accidental action would require restoring the entire backup. The team listed the long-term retention policy as a trial limitation. For now, the administrator would register expiring materials batch by batch and apply the confirmed handling method. A later solution also needed to explain retention periods in backup copies, handover of exported materials, and who would receive the archives when the business activity ended. Automatic cleanup should not be applied directly to official archive materials until ownership and recovery procedures were clear.

24. Boundaries of the Material for Analysts
These records contain observations, decisions, proposals, and matters awaiting confirmation; summaries should distinguish all four. Items with no recorded retest results remain open, and a successful exercise proves only that the tested scenario passed. The material does not provide complete raw monitoring series, traces for every request, or the provider's internal records. Analysts may therefore identify the causes most worth verifying, but must not claim that all root causes have been proven. Final recommendations should prioritize business impact, evidence completeness, and feasibility, specifying what to observe next, who is responsible, and the criteria for completion. Extract the facts relevant to the question without inventing dates, metrics, approval conclusions, or implementation results.
