# ADR 0084: 扩展等级与判定准则；推送表种类由注册表描述，编译模块与插件包推同一种表

日期：2026-11-27 · 状态：提议中（补充 [ADR 0071](0071-installable-extensions.md) 决策 3、8；不改变已冻结的 `gwx/1` 线上格式）

## 背景

ADR 0071 定下了「判断点在核心、插件推带类型的表」，ADR 0069、0081、0082 又各自决定了某一类东西能不能被扩展：KV 卸载后端编译进来，插件路由按推送的角色授权，厂商只做编译期登记。每份 ADR 都是就事论事地回答「这个要不要开放」，没有一套共同的说法，于是同一个问题反复讨论：

- 「做成插件」有时指编译期注册表，有时指签名的数据目录，有时指 server 子进程，含义不同，代价也差了一个数量级。
- 有人主张默认全部开放。开放一种东西就是在 `pkg/extapi` 冻结一份只增不改的契约（ADR 0071 决策 7），没有第二个使用方时提前冻结，以后改不动；有些东西（设备授予、在 GPU 容器里执行的配置）一开放就多一条安全边界。
- 能开放的前提是这种东西已经只有一处定义。厂商的知识还有 39 个文件在定义之外（`vendor_name_files_outside_definitions`），这时开放等于把散落的分支变成公开契约。

推送表框架本身也不是「加一行」就能加一种表：`internal/server/pushstate` 的 `intake.go`、`rows.go`、`combine.go` 按 `extapi.Kind*` 逐种 `switch`，每加一种表要改多处。资源范围、角色绑定（ADR 0081）、计数上限、KV 卸载后端描述这些计划中的表都要走这里。

另外，编译进来的模块（T1）与插件包（T2）表达同一件事走两条路：T1 调 `app.Host` 上的专用方法（`HoldScheduling`、`ProvideFeatures`、`AddBannerSource`……），T2 推表。同一个概念要设计两次，从 T1 换到 T2 时要重写。

## 决策

1. **扩展等级。** 每种可扩展的东西处在下面四级之一，ADR 与评审用这四个名字：

   | 等级 | 含义 | 谁能加一个新的 |
   |---|---|---|
   | L0 散落 | 知识分布在多处分支里 | 改核心，且容易漏 |
   | L1 单一接缝 | 一处定义（描述行或接口），编译期显式登记，接缝之外不出现它的名字或 id | 改核心，或编译进来的模块 |
   | L2 数据开放 | 行为由核心实现；有哪些、参数是什么来自签名的数据：发布通道里的目录，或插件推的带类型的表 | 受信任的发布者，不用发版 |
   | L3 代码开放 | 第三方代码在进程外运行（server 子进程或节点组件），经协议交出结果；热路径仍只查表 | 受信任的发布者 |

2. **L1 是所有能力的默认要求，L2、L3 按准则开放。** 新的能力在第一个实现里就做成单一接缝，并用 `scripts/arch-constraints.txt` 的预算守住接缝外的名字（如 `kv_backend_id_literals 0`）；L1 还不成立时不开放到 L2、L3，先收敛。

3. **判定准则。** 一种东西要开放到 L2 或 L3，ADR 里要逐条回答：
   1. 已经是 L1 了吗？不是就先收敛。
   2. 变化来自外部吗？不同站点、发布者需要不同的答案，或变化比发版更频繁。不是就停在 L1。
   3. 判断发生在热路径上吗（逐请求、插入、上报、认领、放置）？是的话只能开放成表（L2，或 L3 推的表），核心执行。
   4. 会在 GPU 容器或宿主上执行代码、授予设备吗？会的话只接受受信任发布者签名的内容，并由核心核对产出（设备号、封闭的模板变量）；做不到就停在 L1。
   5. 宣称支持要真机验证吗？要的话扩展内容必须带验证依据，做不到就停在 L1。
   6. 核心新增的机制对没有安装任何扩展的 server 有用、或至少行为不变吗？不是就不加这个机制。
   7. 愿意承担契约成本吗：schema 只增不改、兼容旧插件、文档与黄金文件？没有第二个使用方时，停在 L1。

   ADR 写一节「扩展等级」：现在的等级、目标等级、每条准则的回答。

4. **扩展改答案，不改判断点的位置。** 判断点只在核心增加（ADR 0071 决策 3）；多个扩展的答案按表种类声明的合并规则只会收紧（ADR 0071 决策 8）。

5. **推送表种类由注册表描述。** `pushstate` 里每种表一份描述，框架只读描述，不再按种类分支：
   - 种类名、类别（限制、授权、显示、不透明，ADR 0071 决策 8）、是否特权、行数上限；
   - 严格解码与校验（线上 schema 到核心规范形式，ADR 0071 决策 8 的「持久化用带类型的表」）；
   - 合并规则（并集、取最小、按键独占、全体放行），由框架实现，描述只选一种；
   - 编译成快照的函数，与执行这个快照的钩子；
   - 有时间线时的下一步时刻，掉线降级（授权类）的规则。

   现有五种表（`availability`、`fleet_capacity`、`node_holds`、`banners`、`attestations`）先迁到注册表，线上格式、持久化与行为逐字节不变，以现有黄金文件与契约测试为准。之后每加一种表是加一份描述和它的执行钩子，`pushstate` 里描述文件以外的代码不再点名任何种类。将新增的预算 `pushstate_kind_refs_outside_descriptors`（随实施步骤 1 登记进 `scripts/arch-constraints.txt`）的计数口径是：`internal/server/pushstate` 中除种类描述文件与测试以外，对 `extapi.Kind*` 常量的引用数，基线为 0。它不只数 `switch`，也数 `sortedParts(extapi.KindNodeHolds, …)` 这类写法。

6. **编译模块推同一种表，判定函数类的方法冻结。** `app.Host` 增加一个进程内的推送入口，编译模块按与插件包相同的表种类、同样的合并与校验推表，只是身份来自模块名，而不是 fd。之后新增的扩展概念只设计成表种类，不再为 T1 另加专用的 `Host` 方法。现有方法分两类处理：
   - **能表达成数据的**（声明功能、横幅的静态内容这类注册一次、答案就是一组值的）：改为推表的薄封装，行为不变，以各自的契约测试为准。
   - **判定函数类的**（`SchedulingHolder.Hold`、`CardSchedulingHolder.HoldCard`、`NodeEnrollmentGuard`、`featuregate.Source.Availability`、按查看者计算的 `BannerSource.Banners`）：它们是逐次调用的任意 Go 函数，不能无损地写成一张表，所以**不承诺改写**。这些方法冻结：保留现有行为和契约测试，不再新增同类方法，文档标明新概念走表；某个判定函数的用途已能由表表达时，再单独决定弃用。这与 ADR 0081 取舍一节拒绝 T1 判定函数的理由一致。

   一个概念从编译模块换成插件包时，表的内容不用改。

7. **本 ADR 不开放任何新东西。** 它只给出说法、准则与注册表；资源范围、核心路由的动作授权、计数上限、外部身份、KV 卸载后端描述等表种类各由自己的 ADR 按准则 3 决定。

## 扩展等级（本 ADR 自身）

不适用：本 ADR 是机制，不新增可扩展的东西。注册表本身是 L1，接缝由 `pushstate_kind_refs_outside_descriptors` 预算守住。

## 取舍

- **默认全部开放 vs 默认 L1、按准则开放**：默认开放省去每次讨论，但每开放一种东西就冻结一份契约、可能多一道安全边界，而多数东西没有第二个使用方。默认 L1 的成本是一次收敛，以后开放不用返工。
- **注册表 vs 继续按种类分支**：分支在五种表时还看得清，计划中的表会让它翻倍，而每种表的合并、降级、持久化都是同一套规则，分支只是在重复。
- **T1 推表 vs 保留专用方法**：专用方法类型更直观，但让每个概念设计两次，并且 T1 绕开了合并规则与掉线降级（ADR 0081 取舍一节已因此拒绝 T1 的判定函数）。推表让两条路的语义一致。
