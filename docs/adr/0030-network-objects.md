# ADR 0030: 节点网络是可附加的对象，每节点每角色的解析结果按需计算

**Status**: Accepted
**Date**: 2026-09-25

## Context

节点之间有三类流量需要选网卡：节点间同步模型/镜像（存储同步）、多机推理的集合通信与 PD 分离的 KV 传输（参数）、网关到推理实例（服务）。原先只有全局或按节点的 `model_sync_cidr/interface` 设置，以及多机推理直接用节点的 `direct_address`。这种方式有三个问题：

- 大规模集群没法按机型或机架批量配置；
- IB/RoCE 与以太在 NCCL/UCX 上的配置完全不同；
- RDMA 配错时不报错，只会静默退回 TCP，吞吐腰斩。H200 PD 调研实测：容器没挂 `/dev/infiniband` 时 KV 全走了 eth0。

## Decision

1. **网络是一等对象**：角色（存储同步/参数/服务，可多选）、类型（ethernet/rdma）、默认选择器（CIDR、网卡名通配、HCA 通配）。RDMA 不再让用户区分 InfiniBand 与 RoCE（2026-09-26 由三种类型合并，迁移 99）：链路层按节点端口自动识别，同一网络内出现两种链路层即提示。互通以"是否同一个网络对象"为准，不以类型为准：一个网络对象代表一套 fabric。
2. **附加到节点或节点标签**：直接附加到节点的优先于经标签附加的；同一优先级命中多个同角色网络时，先附加的生效并给出提示，不报错。节点附加可以覆盖网卡、IP、HCA 与 bootstrap 网卡。
3. **解析结果不落库**：每次由"附加关系 + 节点标签 + agent 上报的网卡清单"计算（`store.ResolveNetworks`），页面、下发、调度和内部测试共用这一个函数。只存用户的声明与 agent 的观测，不存派生结果，避免两者不一致。
4. **兜底沿用原行为**：没有网络或没匹配到网卡时，存储同步用原设置，参数网络用 `direct_address`，服务走隧道。不迁移原来的全局 `model_sync_*` 设置，因为"全局"无法用"节点或标签"附加关系表达。
5. **RDMA 参数网络强制 IB 传输**（`NCCL_NET=IB`，UCX 只给一张具体 HCA），配错时大声失败；多机部署要求所有 rank 共用同一个参数网络或都没有。
6. **变更只对新启动的实例生效**，不跟踪漂移。

## Consequences

- 网卡清单成为 agent 必报的数据：proto `NodeStatus.network`，nil 表示老 agent（保留上次清单）。
- 内部测试有测量结果，这是唯一需要持久化的网络派生数据（`network_test_runs`，每网络保留 10 次）。它由 controller 执行，API 只记录请求，符合"后台任务不从 HTTP 层起"的约束。
- 参数网络第一版只覆盖 NVIDIA；昇腾 NPU 直出 RoCE 由 `hccn_tool` 管理，需要另行建模。
- 服务网络不直接暴露引擎端口（引擎没有鉴权，暴露后服务网段内可绕过 API key）。agent 在服务 IP 上起一个很薄的 TLS 转发：连接先出示 `HMAC(节点 token, 实例 UUID)`，再原样拼接到实例回环端口，不解析 HTTP，流式与升级连接天然透传。令牌每实例一个，由网关与 agent 各自计算，不落库、不显示；TLS 密钥由节点 token 派生，网关固定公钥校验。HMAC 密钥用原始节点 token，而不是 server_dial 用的 `SHA256(节点 token)`，避免 server_dial 签名 agent 提供的 nonce 时成为令牌预言机。直连失败时同一请求退回隧道，并对该节点退避 30 秒；网关最近一次结果（直连/隧道 + 原因）按变化写入节点，供页面展示。

## Alternatives Considered

- **每节点一组网络设置**：大规模时不可维护，也表达不了"这些节点在同一 fabric"。
- **只按类型判定互通**：两个不同 fabric 的 IB 网络类型相同却不互通，调度会给出错误的组合。
- **把解析结果写库**：标签、清单、附加关系任何一处变化都要失效重算，容易与声明不一致；解析开销很小（节点数 × 附加数）。

## 更新（2026-09-26）

网络角色 v2 改写了第 4 条和服务网络的回退：

- **兜底改为管理网**：删除 `direct_address` 与 `model_sync_*` 设置。每个节点都在内置的管理网上（agent 连 server 所用的本机地址），某个角色没有独立网络时由它承担，每节点可关闭。存储同步按节点对、参数按整组选网络，组内不共用独立参数网络时回退到管理网并提醒。
- **服务网络不回退隧道**：实例启动前 server 探测一次节点的服务网络转发端口，不通就让实例失败；运行中直连失败的请求直接失败。上文 Consequences 里"直连失败时同一请求退回隧道"不再成立。
- 用词：中文"附加"改为"加载"。

## 更新（2026-09-27）

解析函数从 `store.ResolveNetworks` 移到纯叶子包 `netplan.Resolve`，核心流程经 `network` 服务调用，store 只存取网络行。模块边界见 [ADR 0026](0026-network-module-boundary.md)。

## 更新（2026-09-30）：加速器 RDMA 是第三种类型

Consequences 里"昇腾 NPU 直出 RoCE 需要另行建模"在这里落地。类型从两种变为三种，并改名让三者并列时不含糊（迁移 111）：`host_ethernet`、`host_rdma`、`accelerator_rdma`。

- **为什么必须建模**：在两台 910B4 上实测，昇腾跨机集合通信（HCCL）只走加速卡自带的 RoCE 口。库里没有任何开关能改走主机网卡，也不会自动回退：主机侧握手配对了但卡对不可达时，通信域照样建成，第一次集合通信才失败。而"哪些节点的加速卡网口连在一起"是布线事实，从地址推不出来（两台的卡在同一个 /16 里，实际只有同号卡互通）。实测记录见 `artifacts/archive/2026-09-30-accelerator-parameter-network/evidence/ascend-multinode.md`。
- **字段不变，rail 换来源**：加速器 RDMA 网络沿用 RDMA 网络的形状。CIDR 只选 bootstrap；rail 是一张张加速卡（`npu3`），来自 agent 上报的 `accelerator_ports`（唯一新增的数据，主机内核看不到这些口，只能由厂商工具读出）。
- **bootstrap 一定是主机地址**：没有主机进程能绑定加速卡网口的地址，所以握手（HCCL 的 rootInfo、Gloo、master 地址）走主机网卡，默认取管理网地址。容器拿到 `HCCL_IF_IP`、`HCCL_SOCKET_IFNAME` 和只读挂载的 `/etc/hccn.conf`：少了它们，HCCL 在主机的多个网卡里自选会选错，建通信域就超时。
- **只能承担参数角色**：存储同步与服务是主机进程，同样绑不了那些地址，创建时即拒绝。
- **昇腾多机要求它**：昇腾节点的多机组不在加速器 RDMA 网络上时拒绝部署，而不是启动后在第一个请求上失败。PD 分离按模式的传输方式做同样的检查。

没有采用的做法：由 PD 模式推断"走加速器面"并绕开主机参数网校验。它只修 PD、不修普通多机，而且没有网络对象就没有地方记录布线事实。

### 卡级连通性测试

加速器 RDMA 网络的内部测试多了两种方式：同号卡互 ping 与全卡矩阵。它是部署前唯一能知道"该选哪对卡"的手段，结果是测量值，和其他内部测试一样存进 `network_test_runs`，每对卡是已有的 per-rail 明细的一行，不新增实体。

- **按轮调度**：一张卡同时只能发一次 ping，不通的地址要等满超时，所以决定耗时的是轮数。节点对与卡都按循环移位错开，每轮每张卡当一次源、一次目标；上限按"轮数 × 单轮超时"定，不按节点数或探测数定。实测依据（不同卡可并发、挂起的探测杀掉后可立刻再发、同卡并发不可靠、输出不是流式）见上面的 evidence。
- **结果读路径**：一次全卡矩阵的结果可达数 MB，所以测试结果只在展示它的详情接口读取，不再随每次网络状态加载读出。
- **结论在 server 读出**：节点对的形状和整次运行的结论由 server 从那次运行的结果派生后下发，不另存；它描述的是测试那一刻，不是网络现在的状态，所以只能作为提示，不能当作放置的硬约束。
- **预估与执行同源**：发起前的预估（节点对、轮数、探测数、最长耗时）与实际执行读同一份排程，客户端不自己算。

### 厂商知识的产地

"哪些厂商的加速卡自带网口、要告诉集合通信库哪些环境变量、容器需要主机上的哪些文件"只在 `internal/accelerator`（`CardNetworkOf`）里说一次。网络类型 `accelerator_rdma` 是厂商中立的；放置校验、启动装配和 PD 模式都从这一处取，agent 的卡名与卡号互转也用它。
