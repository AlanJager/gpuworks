# ADR 0073: 推理令牌属于用户，历史零用户批处理按原 key 隔离

日期：2026-11-18 · 状态：已接受

## 背景

控制台批处理记录当前 JWT 用户，但管理接口创建的推理 key 一直写 user_id=0。同用户的推理 key 因此读不到控制台批次；所有历史零用户 key 又被折进同一资源范围。数据库已有 user_id 与 api_key_id，但没有可靠事实能推断历史 key 的创建者。

## 决策

1. **新 key 的归属来自已验证的管理身份。** HTTP 创建时使用当前 JWT 用户，不能由请求体指定他人 user_id。普通用户只管理自己的 key；管理员保留全站管理能力。列表、修改范围和撤销必须执行同一归属规则，UI 隐藏按钮不能代替服务端授权。
2. **正用户批处理仍按用户归属。** 按已有文档，同一用户的任意有效推理 key 可读该用户的批次和文件，其他用户得到资源不存在。部署 scope 继续约束推理执行，不在本次引入另一套历史数据读取 ACL。
3. **零用户不代表全部用户。** 历史 user_id=0 的批次和文件必须同时匹配原 api_key_id；列表 SQL 与单资源检查采用同一规则。匿名 key0/user0 不能读取其他历史 key 的资源。管理员控制台的全站访问是显式权限，与这个兼容规则分开。
4. **历史 key 不自动重新归属。** 不迁移给首个管理员、当前登录者或最近使用者，也不从名字猜测。保留原推理能力和部署 scope，通过已有“创建个人 key、替换调用凭据、显式撤销旧 key”流程重新发放；不新增认领接口或归属表。个人替代 key 不自动继承无法证明归属的历史零用户批次，管理员仍可经控制台管理历史任务。
5. **归属展示使用已有事实。** key 元数据明确带 user_id，零值保留；UI 可据此解释历史 key 与重新发放方式，但不能据这个展示字段授予权限。

## 取舍

- 只把创建时的 0 改成用户 ID，不能解决历史零用户之间互读或 key 管理跨用户操作；身份必须在创建、读取和管理入口闭合。
- 自动迁移旧 key 看似方便，但没有可信创建者依据，可能转移别人的数据。选择显式重新发放，保留既有 key 的推理兼容与管理员管理出口。
- 复用已有 UserID/APIKeyID，不新增迁移、通用 ACL 或认领工作流。将部署调用范围与历史读取范围合并属于另一项产品决策，本次保持既有用户资源契约。

## 验证

真实 HTTP 创建 key 后读取控制台批次与输入/输出；同用户多 key、受限 key 按既有契约可读，执行范围不变；其他用户、匿名和其他历史 key 不能列出、读取、取消或删除不属于自己的资源。验证普通用户的 key 管理隔离、管理员管理、撤销后的认证与历史 key 原推理能力；夹具不能直接塞入理想的非零用户而跳过 HTTP 创建。
