# ADR 0053: 存储文件——整个存储可浏览，只有两个区域可写，传输经数据通道由 agent 落盘

日期：2026-10-21 · 状态：已接受

## 背景

存储（[ADR 0034](0034-model-files-belong-to-storages.md)）原来只承载模型文件，平台没有「把任意文件放上去或取下来」的入口。离线环境要把评测数据集、tokenizer、prompt 集放到存储上，跑在节点上的应用（计划见 `artifacts/work/2026-10-21-apps/plan.md`）产出的结果也需要能下载、沉淀。这个需求与具体应用无关，所以做成存储本身的通用能力，而不是为某个应用单独设计上传接口。

## 决策

1. **浏览全部，写入两处**：管理员可以浏览和下载存储里的任何文件；上传、新建目录、删除、重命名只在 `files/`（通用区）与 `.gpuworks/apps/`（应用数据）两个区域内进行，区域目录本身不可删、不可改名。模型文件目录与 `.gpuworks/` 的其余部分只读，模型文件仍只由模型管理改动。区域定义、路径规范化与可写判断只有一份：`proto.CleanStorageRel`、`proto.StorageRelWritable`，server 预检与 agent 执行共用。
2. **agent 是唯一碰文件系统的一方**：server 选节点、做能预先判断的检查（存储停用、区域、节点在线、数据通道已连接、agent 能力 `storage.files`），然后经数据通道把字节交给 agent。agent 按存储根解析路径，在解析符号链接之后再判断是否仍在根内，拒绝穿出存储根的路径；列目录用 lstat，不跟随符号链接。
3. **上传先落暂存、成功后才回报**：上传写到 `.gpuworks/incoming/<控制面 ID>/upload-<id>`，需要时在暂存里解压（tar / tar.gz / zip，拒绝绝对路径、`..`、链接与设备文件，限制解压后的总大小与条目数），完成后原子改名到目标，agent 此后才回一行结果（`StorageFilesStatus`）；失败时清掉暂存。server 以这一行作为成功的唯一依据。
4. **单请求流式上传，不做分块续传**：浏览器一个 `PUT`，server 不落盘，边收边经 `storage.upload` 流转写。经 Cloudflare 等对请求体有上限的反向代理传大文件不在支持范围内。
5. **下载边打包边传**：文件原样；目录按请求的格式（默认 zip，可选 tar.gz）流式打包，不跟随符号链接。agent 先回一行 `StorageDownloadHead`，有错误时不传字节。目录下载没有预知长度。
6. **短操作走 ctrl RPC**：`storage.files.list/mkdir/rename/delete`。删除先改名进存储的回收目录，字节在后台删除，与模型文件删除一致。拒绝原因用 `proto.StorageFilesError` 的稳定 code 回传，server 映射为 ProductError。
7. **不新增持久化**：文件就是存储上的文件，平台不记录它们。

## 取舍

- 浏览范围包括模型目录与平台元数据：管理员本来就能在节点上看到这些文件，只读浏览不扩大权限；把写入限制在两个区域，避免手工改动破坏平台管理的目录。
- 单请求上传实现简单，代价是大文件中断要重传，以及经 Cloudflare 时受请求体上限约束。
- 下载使用浏览器直链（cookie 鉴权）：浏览器自己流式落盘、不占内存；代价是中途出错时浏览器只显示下载失败，看不到产品错误文案。
- 符号链接检查先解析再操作，校验与操作之间仍有极短的竞态窗口；威胁模型是管理员操作加存储里可能已有的链接，不是同时在存储上写恶意链接的对手，因此接受。
