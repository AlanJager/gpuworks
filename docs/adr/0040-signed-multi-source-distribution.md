# ADR 0040: 服务端升级与官方目录走签名索引的多源发布通道，官方目录最后一次导入生效

日期：2026-10-11 · 状态：已接受

## 背景

server 有三样东西要从发布方拿：新版本的二进制、系统镜像目录、内置推理模板目录。此前它们各走一条路：`gpuworks upgrade` 访问
`gpuworks.zstack.ai`（公网 DNS 解析到内网 IP）；镜像目录「检查更新」访问 `image-manifest.gpuworks.ai`（境外 CDN 代理到香港）；
推理模板只能填一个自定义 URL。实测晚高峰从大陆访问境外 CDN 只有几十到几百 KB/s，并且会卡死；`.ai` 不能备案，任何 CDN 都用不了大陆节点；
境内对象存储的默认域名免备案，速度高一到两个数量级（实测见 `artifacts/work/2026-10-11-update-distribution/`）。

另外，两份官方目录在线更新以后，server 每次启动都把数据库对齐回二进制内嵌的那一份，在线更新在重启后失效。

## 决策

1. **一个发布通道，多个逐字节相同的源。** 发布树（`<channel>/index.json`、`releases/…`、`catalog/…`）同时放在阿里云 OSS、华为云 OBS 的默认域名
   和 Cloudflare R2（`dl.gpuworks.ai`）。默认源是二进制里的常量；CLI 可用 `--source` 覆盖。
2. **客户端同时请求所有源的索引，取第一个验签并解析通过的。** 不排队试，坏源不增加等待。文件先从胜出源下载，失败换源、Range 续传，
   以「多久没有新字节」判超时；最后按索引里的 size 与 sha256 校验。
3. **信任来自签名，不来自源。** 索引是 ed25519 签名信封（签名与正文同一个文件），公钥编进二进制，文件由索引里的 sha256 约束。
   任何源（境外 CDN、客户自建镜像站、离线拷贝）都只是传输，被篡改的索引或文件都会被拒绝。
4. **两个渠道，安装自己选。** `nightly`（滚动预览版，每次 master 构建）与 `release`（正式发布版，`v*` tag）。选择保存在 `server.yaml` 的
   `update_channel`，控制台与 `gpuworks upgrade` 读同一处；不写时跟随构建时注入的 `version.Channel`。只有构建时间晚于当前构建的版本才算更新，
   切换渠道不会被提示降级。
5. **官方目录最后一次导入生效。** 启动时只有当 server 构建与上次重放内嵌目录时不同，才重放内嵌的镜像目录与推理模板目录；否则保留数据库里
   最后一次导入的结果。不比较目录版本号的新旧；「有更新」看目录所属发布的构建时间：渠道里的发布比当前 server 构建早时（nightly 切到 release、构建领先于渠道），它的目录不算更新，仍可上传应用。推理模板的在线更新按 upstream 来源对账，user 档位不受影响（ADR 0011）。
6. **检查由 server 发起，按时间节流。** 打开登录页时浏览器请 server 开始检查（不需登录、不返回结果，同一时刻只有一个检查在跑），管理员登录后页头读取结果；server 对同一渠道每小时最多向外检查一次；浏览器不直连发布源。
   这样结论反映的是真正要下载文件的 server 的网络，验签只在 server，客户只需放行一条外连。

## 取舍

- 默认源是默认域名而不是自己的备案域名：免备案、当天可用，代价是受厂商政策约束（阿里云已对新 OSS 用户禁用中国内地默认外网域名）。
  三个源互相独立，单个源失效时其余源照常工作，新版本再更新常量。
- 不比较目录新旧，意味着升级到一个内嵌目录较旧的 server 版本会先回到内嵌目录，管理员需要再检查一次更新；换来的是没有版本号排序规则，
  也不会出现「数据库里的目录比当前代码能理解的更新」却无法回退的状态。
- 同一个 server 构建重启不再重放内嵌目录，因此依赖「每次启动重放」去补新列的做法只在换构建时生效；补列本来就随新构建而来，这一点不受影响。
- 签名私钥只在 CI 受保护变量里；轮换时在二进制里并存新旧公钥一个版本周期。

## 后果

- `gpuworks upgrade` 默认走发布通道；`--base-url` 保留给内网发布站（旧格式、无签名，信任来自 TLS），新增可重复的 `--source` 与 `--channel`。
- 镜像目录「检查更新」与推理模板「检查更新」都从发布通道取文件；`template_catalog_url` 设置删除。
- 设置页有统一的「版本与更新」，可选择渠道，显示三样东西的当前值和最新值（不展示发布源）；页头在有新版本时提示；三样都可以在界面上传更新。server 在界面升级时自我替换后退出、由服务管理器拉起新版本（因此只在有服务管理器时提供：systemd 单元，或没有 systemd 时 `serve --supervise` 这个守护父进程，2026-10-12 补充），由启动守卫负责失败回滚。
- `image-manifest.gpuworks.ai/manifest.json` 由 R2 继续提供同一份镜像目录，老版本不受影响。

## 补充（2026-10-17）：更新检查随请求报告装机规模

发布方需要知道有多少安装、各自的规模与硬件。发布源是静态对象存储，收不到写入，所以报告只能放在索引请求的查询参数里，由发布方从 OSS、OBS、R2 的访问日志统计（不新建收集服务）。

- **报告什么**：安装标识（用 master.key 做 HMAC 得到的单向值，只为让同一安装每小时一次的检查只计一次）、server 版本、节点总数与在线数、agent 版本分布、GPU 型号分布；分布各最多 16 项。不含主机名、IP、用户、部署、模型。完整参数表见 [配置参考](../reference/configuration.md#镜像目录与镜像拉取)。
- **只发给内置源**：`--source` 或自建站点的客户端收到普通请求；`gpuworks upgrade` 等命令行路径不报告。
- **开关**（2026-10-22 起由 [ADR 0054](0054-usage-report-and-notices.md) 修订：报告改由 `usage_report` 控制，`auto_check_updates` 只管是否自动检查；下面是当时的决定）：`server.yaml` 的 `auto_check_updates`，设置页「版本与更新」里同名开关。默认开；关闭后 server 不自动检查（登录页的预取是空操作，页面加载只展示上一次手动检查的结果），手动「检查更新」仍读索引，但同样不带报告。选择把「是否自动检查」和「是否报告」绑在同一个开关上，是因为报告随检查发出，客户只需要理解一个开关：关掉之后任何检查都不带报告。
- **取舍**：查询参数写进访问日志，对象存储的日志保留与访问控制由发布方负责；R2 默认不开访问日志，需要发布方打开。没有 install ID 的服务端（无 master.key 的测试夹具）报告里 `id` 为空，统计时忽略。
