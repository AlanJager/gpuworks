# ADR 0055: 长期统计与原始观测分开存储：一对象一行、在入库路径上累加、增量写入

日期：2026-10-22 · 状态：已接受

## 背景

平台对外卖 token 后，需要回答「某个 API key 在任意时间段用了多少 token」「某个服务这个月的首 token P95」「哪些卡长期闲置」「每个部署占了多少卡时」。
现有的观测数据都不适合：metrics.db 的原始样本只留 72 小时、一个指标一行；ux.db 的逐请求记录只留 7 天或 2 GB、按天整表删除，流量大时正常请求会被抽样；
网关的 token 计数只分到部署、不分 key。把它们的保留期拉长，代价随节点数、序列数和请求数线性增长：1000 节点 × 8 卡的 GPU 序列降成按小时存 400 天，
会有几十亿行。

## 决策

1. **长期统计是一类单独的数据，按小时与按天两档，各自保留**（默认按小时 31 天、按天 400 天）：Token 用量、服务质量、GPU 利用、卡时。
   监控中心只读原始观测，运营分析只读长期统计，两边不混用。
2. **一个对象一行，数值是带类型的列。** Token 用量一行是「小时 × key × 用户 × 部署 × 来源」，服务质量一行是「小时 × 部署」，GPU 利用一行是一张卡的一小时，
   卡时一行是「小时 × 部署 × 卡型」。不用 metrics.db 那种一个指标一行的通用结构，行数少一个数量级，查询也不用拼接。首 token 与端到端时间存分档计数
   （与请求视图同一套四分之一倍频程分档），是唯一整体读写的不透明快照（`rollup.Histogram` 的编码）。
3. **在入库路径上累加，不回扫原始数据。** 网关结束一个请求时把它交给累加器（每请求一次 map 查找和几次加法，按部署分片加锁，不经队列，所以不会因为队列满丢账）；
   指标入库的单写协程顺手累加 GPU 样本；卡时每分钟按列精简地读一次持有 GPU 的实例。请求按**结束时间**归到小时，长请求跨过午夜也不会落进已经汇总好的天。
4. **增量写入。** 每次写出的是上次以来的增量，存储把它加到行上；写失败的增量还给累加器下次再写，重启最多丢没写出的那一段（Token 用量每分钟写一次，其余每 5 分钟）。
   单写入者保证不会重复累加。按天的行由按小时的行在统计时区里汇总，可以重跑；一个天的小时已经部分超出保留期时不再重算，以免用剩下的小时覆盖它。
5. **Token 用量放主库，其余放 stats.db。** 用量是对账依据，要随主库备份、迁移与升级；服务质量、GPU 利用和卡时是监控类数据，放数据目录下单独的 SQLite 文件，
   与主库事务、metrics.db 的高频写入互不争锁，可以整体丢弃重建。
6. **所有保留期、容量上限、开关与统计时区是一个平台设置**（`data_retention`），设置页编辑、运行时生效；配置文件的 `metrics_retention` 只作为首次启动的初值。
7. **升级时从 ux.db 补一次历史**（Token 用量与服务质量），按天倒序进行，写入与进度在同一事务里，可以中断续跑。GPU 利用与卡时不补：原始样本只有 72 小时，
   补一次要扫全部样本，到集群规模代价大于价值。

## 取舍

- **入库累加 vs 定时回扫原始数据**：回扫最简单，但每小时要读 1000 节点的全部 GPU 样本（约 3000 万行）；入库累加把开销摊到每个样本几次加法上。
  代价是累加器要处理并发与重启，所以选增量写入而不是整行覆盖。
- **主库 vs 统一放 stats.db**：用量放主库多了每分钟一次的小事务（常见规模下几千行 upsert），换来对账数据与平台一起备份；其余统计不需要这层保障。
- **请求按结束时间归属 vs 按接收时间**：请求视图按接收时间筛选，两边在跨小时的长请求上会差一点；按结束时间换来日汇总不需要回补。

## 后果

- 规模目标（1000 节点、500 部署、1000 活跃 key，每个 key 用 3 个部署）下，长期统计约 1.3 GB（用量约 0.5 GB 在主库）；极端组合
  （每个 key 每小时都用全部部署）下用量写入会变大，状态接口报告每次写入的行数与耗时，设置页可见。
- 网关每个请求多约 200 ns、不分配内存；metrics 入库每个 GPU 样本多一次 map 查找。
