# ADR 0086: ui-check 不为只新增错误码文案的改动走页面，这是一次有意的覆盖面收窄

日期：2026-11-27 · 状态：已接受

## 背景

ui-check 的「Walk the UI」按改动文件挑要走的页面，依据是 `ui/src` 的 import 图。locale JSON 不在图里，所以任何 locale 改动都走全部页面：每个页面在 1440/1024 两种宽度、中英两种语言下各走一遍，再与基线构建对比。只新增一条报错文案的改动（#181、#194、#196 都只新增了 `apiError.IMAGE_MANIFEST_LEGACY_PROJECTION`）因此要走 10 到 26 分钟，而只走 0 到 1 个页面的运行是 2 到 5 分钟。

新增错误码文案几乎是每个后端改动都会带的，walk 的时间就落在大多数 PR 上。

最初的提议论证说这类改动渲染不到任何现有页面，所以跳过 walk 不丢覆盖。这个论证不成立：控制台对服务端下发的码是通用渲染的（`ui/src/apiError.ts` 里的 `` t(`apiError.${code}`) ``，以及 `productMessageText`，用在部署预检的非 pass 项、诊断项、设置页的更新检查错误等处）。一个 PR 新增码、并让已有接口返回它时，新文案会出现在现有页面上。ui-check 跑的 experience server 用 PR 自己的代码构建，Go 改动又不会让任何页面被计入，所以这些页面不会被走到。静态地证明某个新码到不了现有页面，需要分析 Go 里哪些接口可能返回它，脚本做不到。

## 决策

1. **只新增错误码文案的 locale 改动不走页面。** 条件由 `scripts/ui_locale_changes.mjs` 判断：只新增 key；每种语言都新增；key 是 `common` 命名空间 `apiError.` 下的错误码文案；不是已有 key 的复数或 context 变体，也不是已有变体的基础 key；未改动的源码里没有字面引用它。其余 locale 改动（改值、删 key 或文件、只在部分语言新增、其他前缀与命名空间）照旧走全部页面。

2. **这是覆盖面收窄，不是等价改写。** 被放弃的覆盖是：同一 PR 让已有接口返回新码时，新文案在现有页面上的布局问题（过长、换行、溢出）。保留的覆盖：文案长度由 `ui_copy_message_strings`（中文 80 字）与 `ui_copy_en_strings` 的预算守住；渲染错误码的组件本身改动时照常走它所在的页面；PR 同时改了渲染它的页面时，那个页面照常被走；`detail-spacing` 与厂商标识检查照常运行。

3. **记录在案。** CI 日志在跳过时写明 `not walked (ADR 0086)` 与跳过的 key；`scripts/arch-constraints.md` 的页面归属一节写明这是收窄并链接本 ADR。

4. **收回条件。** 满足下面任一条件时删掉这条跳过，让 locale 改动重新走全部页面：
   - walk 全部页面的耗时降到 5 分钟以内（例如按页面并行或分片）；
   - ui-check 能从 experience 场景得出每个页面实际渲染的错误码，届时改为只跳过不在其中的码；
   - 发现一次因跳过而漏掉、合入后才发现的错误码文案布局问题。

## 取舍

- **跳过 vs 继续走全部页面**：继续走全部页面不丢任何覆盖，但每个带新错误码的 PR 都多等 10 到 20 分钟。被放弃的覆盖只涉及错误码文案的布局，且长度已有预算守住，所以选择跳过并写明收回条件。
- **只对能静态证明渲染不到的改动跳过 vs 本决策**：前者不丢覆盖，但新错误码文案总伴随一个新码，而新码能否到达现有页面取决于 Go 代码，脚本证明不了，于是能跳过的改动几乎为零，等于不改。

## 后果

- 只新增错误码文案的 PR 不再为 locale 改动走页面；新码在现有页面上的布局问题只能靠文案预算、评审和合入后的定时 ui-check 发现（定时运行走全部页面）。
- 删掉的 locale 文件照常走全部页面：语言包按目录 glob 加载，没有随之改动的 importer。
