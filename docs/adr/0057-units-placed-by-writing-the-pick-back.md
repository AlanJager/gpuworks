# ADR 0057: 多机与 PD 的单元由平台自动放置，做法是把挑选结果写回单元

日期：2026-10-28 · 状态：已接受

## 背景

单机部署有「自动 / 手动」两种放置：自动时没有钉节点，副本每次启动都由候选池重新选（[ADR 0029](0029-deployments-reconcile-as-units.md) 里单机副本的 unit 只有一个 rank，节点是候选列表）。多机与 PD（[ADR 0028](0028-pd-disaggregated-deployment.md)）只有手动：每个 rank、每个 P / D 单元的节点都要运维写，选了卡就钉死。结果是运维要自己判断哪几台节点同网、同架构、卡空闲；PD 钉住的卡被其他部署占着时，同节点有空卡也不用，单元只报「空闲整卡不够」干等了数小时。

让多机和 PD 也能自动放置时，有一个绕不开的结构事实：unit 在整个系统里「写着节点」。

- `planning.MatchUnits` 按角色、节点、钉卡与所记录的 followers 认领 unit（ADR 0029）；
- 网络解析（[ADR 0030](0030-network-objects.md)）按 rank 的节点算每个角色用哪张网、哪个地址，PD 的 KV 网络、多机的 master 地址都由它们决定；
- 换节点与驱逐（先起后切）都是「改写 unit 里的节点」，用的是运维手动改副本列表的同一套校验与写回；
- 多机一个副本的 rank 必须同时创建、同时失败，启动前要知道每个 rank 在哪台节点才能做屏障与镜像预拉取。

## 决策

1. **放置方式是部署上的一个布尔事实。** 新增 `deployments.units_auto`（带类型的列，默认 false，迁移 178）：多机或 PD 部署是否由平台放置。它不能从现有数据推导（单机的「自动」是「没有钉节点」，而多机与 PD 的 unit 总是写着节点），所以值得新增。升级前已有的部署读作 false，保持运维的放置。API 把它叫 `placement_mode`（`auto` / `manual`），创建、评估接受它，详情返回它，`PUT /deployments/{id}/placement-mode` 在两者之间切换（不重启实例；切到自动同时去掉 PD 单元钉住的卡）。

2. **平台挑出的节点写回单元，而不是让单元保持「未放置」。** 创建时（以及多机按副本数扩容、PD 增加单元时），服务端为请求没写的 rank 或单元挑节点，把结果写进与手动相同的位置（多机的 `node_uuids`、PD 的 `placement.pd` 单元），之后请求就像运维自己写了这些节点一样走常规检查与存储。单元始终写着节点，于是匹配、网络解析、换节点、驱逐、屏障全部照常工作，一行代码都不需要认识「未放置的单元」。写着的节点同时就是之后的「优先沿用上次节点」：不需要另存。

3. **创建时按容量挑，单元启动时按试算校正。** 创建 / 评估时的挑选只看空闲卡、节点条件、网络与架构，不做完整试算，成本低、结果可预览（评估返回 `auto_placed`）。单元要启动而没有实例时，控制器用 API 共用的单元试算（`planning.UnitTrial`）按启动的真实条件算一遍：节点都在线且放得下就启动；某些 rank 的节点已停止调度、不满足节点条件或会被调度拒绝（卡被其他部署占了），就**只把这些 rank 换到别的节点**，其余 rank 不动，候选与写回沿用换节点的实现，并记 `UNIT_PLACED`。没有地方可去时单元保留原节点继续等待，约每分钟再找一次。只在单元本来就没有实例时发生，不会打断正在服务的实例，也不消耗重试次数。

   离线的节点仍归换节点（等待时间不变），被驱逐的节点仍归驱逐（先起后切）；自动与手动的部署在这两种情况下行为相同。手动部署不做重新挑选，节点放不下就等待，原因写在 `DEPLOYMENT_UNSCHEDULABLE`；PD 钉住的卡被其他部署占着时原因是 `pinned_gpus_unavailable`，点名占卡的部署。

4. **挑选规则。** 候选是同一计算网络、同一种 GPU 架构、每台有一个 rank 所需空闲卡的节点组（多机以一个副本为单位，PD 以整个部署为单位，因为各角色交换 KV）。组之间 RDMA 优先于以太网，再看已有模型的节点多的；组内已有模型的节点优先，再按放置策略。多机与 PD 未写策略时默认 `binpack`（它们一次要一整组卡，集中放给下一个部署留下完整的空节点），单机仍是 `spread`。PD 在 `binpack` 下，一台节点放得下全部单元就全放一台（KV 不经网络），`spread` 下 prefill 与 decode 尽量不同台。能不能连通只看网络**声明**，不用网络测试或 KV 验证的结果。
5. **卡不写回。** 自动放置只替运维选节点：多机本来就不允许钉卡，PD 自动单元写回时不带 `gpus`，用哪几张卡由调度器在启动时挑。
6. **限制：自动放置的 PD 单元必须一台节点放得下。** 带 followers（跨节点）的单元要自己写节点（`AUTO_PLACEMENT_PD_MULTI_NODE`）；自动放置的多机必须有 `placement.tp`（`AUTO_PLACEMENT_TP_REQUIRED`）以知道每台节点要几张卡。

## 取舍

- **不写回、单元保持未放置、每次启动都全量重选**：看上去更「纯」，但要让匹配、网络解析、换节点、驱逐、启动屏障、镜像预拉取和 PD 的 KV 网络检查全部认识「节点未定」，而这些都假定单元写着节点；多机一个副本的 rank 还必须同时启动，节点在启动那一刻才定，意味着屏障之前的所有检查都要重做。写回把变更限制在「谁写节点」一处。
- **每次启动都重新挑**：会让正在服务的角色因为别处卡的变化而被迁走。现在只在单元没有实例、而它的节点放不下时动，且只动放不下的 rank。
- **创建时就做完整试算**：创建路径、评估与扩容都会逐节点逐组试算，在规模目标（1000 节点）下代价偏大；而试算结果在单元真正启动之前就可能过期，所以放在启动时由控制器做，创建时只做便宜的容量判断。
- **用运维已写的节点作为「优先沿用」而不另存**：不新增持久化事实（ADR 0032）。

## 后果

- 新增一列 `deployments.units_auto`；单元的存储形状不变，旧数据读作手动。
- 同一套候选与试算被创建、评估、扩容和控制器共用（`planning/unit_choice.go`、`unit_trial.go`），换节点也改为按部署的放置策略排候选。
- 创建时的挑选是容量判断，评估预览与创建的结果可能不同；节点放不下要到单元启动时才发现，不是持续监测。
- 网络声明有误（例如交换机不通）时仍会挑出连不通的组，启动后由引擎或 PD 交接自检报错。
- 自动放置的 PD 部署的单元不能跨节点；这类单元仍然手动写节点。
- 只有改变「谁写节点」的是新规则：切换放置方式不重启，也不改节点。
