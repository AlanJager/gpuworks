# ADR 0056: runveil 镜像拉取的连接数由按仓库 host 的预算自适应，慢连接按同伴相对判断

日期：2026-10-27 · 状态：已接受

## 背景

runveil（udocker）节点的原生拉取（`runtime/udocker/native`）用固定的 6 个层并发 × 每个大层 4 个 Range 分段，对同一个仓库最多 24 条 TCP 连接。仓库传输层改为只用 HTTP/1.1 之后（同一 host 的并发请求各占一条连接），这个数字成了真实的连接数，带来两类问题：

- 私有仓库（Harbor、华为云 SWR、阿里云 ACR、registry.zstack.ai）与公司代理常按来源地址限制连接数或请求频率，24 条会收到 429 或被直接断开；被拒的连接立即重连只会加重限制。
- 链路本身慢（海外 CDN 高峰期总共几百 KB/s）时，24 条连接共分一份带宽，既不更快，又让「连接太慢就换一条」的绝对下限（每连接 16 KiB/s）对每条连接都过严；固定数量也无法利用单连接被限速但总带宽充足的链路。

## 决策

1. **叶子包 `internal/agent/connbudget`**：连接预算。`Hosts` 为每个上游地址（仓库 host；经代理时为代理）建一个 `Pool`，`Pool` 的上限是该地址同时在途的请求数；一次拉取是 `Session`，每个请求（含重试）先取 `Lease`，请求（含读完响应体）结束后归还。Session 有自己的目标连接数，节点上同一仓库的多个拉取共用 Pool 的上限。包只依赖标准库。
2. **自适应，不记忆。** 拉取从 4 条连接起步，每 3 秒窗口量整次拉取的聚合速率：有请求排队而目标已用满时，加倍后速率提高不足 15% 就退回较小档并稳定；稳定后每分钟试探增加四分之一，提高 5% 才保留。单连接被限速的链路因此升到最多 16 条（默认上限，`--image-pull-max-connections` / `GPUWORKS_IMAGE_PULL_MAX_CONNECTIONS` 可改，1 为单连接），整个地址带宽已满的链路停在起点。学到的数值不保存：不新增持久化事实，下一次拉取重新开始。
3. **层并发与分段不再乘出连接数。** 同时拉取的层数仍由 `Workers` 限制（磁盘、临时文件与流式解包的需要），但每个请求都要连接预算放行；大于 `RangeMin` 的层至少切 `RangeParts` 段，更大的按约 64 MiB 一段切（最多 64 段），worker 按序领取分段，连接数随预算爬升而用满。
4. **回压而非故障。** 429、503、拒绝连接立即让该次拉取的连接数减半（同一阵失败算一次）并在一段时间内不回升；连续 3 次连接重置同样减半，最低 1 条。`Retry-After`（秒数或 HTTP 日期，上限 2 分钟）作用于整个 Pool：同一仓库的所有请求，包括其他拉取的，都在发出前等够；没写时间的 429/503 从 2 秒起每次翻倍、最长 30 秒，不再立即重连。单个分段连续被限流 5 次后失败，不整层重来，交给候选切换。一条连接什么都没收到，而同一次拉取里其他连接仍在推进时，不算「卡住」，按「别处有进展」多给重试次数。减半后的上限在平静 2 分钟后逐档放回。仓库把 Range 请求答成整文件时，这次拉取只用 1 条连接，并立即改整块读取。
5. **「爬行连接」按相对标准判断。** 绝对下限仍是每连接 30 秒窗口平均 16 KiB/s，但判断交给连接的 `Lease.Observe`，与同一次拉取中的兄弟连接比较：连续两个窗口低于兄弟（至少两条）速率中位数的十分之一，或低于自己此前最高窗口速率的十分之一而多数兄弟没有同样下降，才换新连接；绝对下限立即生效。无论多少条符合，同一窗口内最多换掉一半连接（只有一条时换这一条），所以整条链路都慢时不会把连接一次全部断开。被换的连接从已收到的字节处继续。

## 取舍

- **起点 4 而不是 2**：镜像层多为数百 MB 到数 GB 的单层，爬升一次要几个窗口，起点太低会让小镜像变慢；4 等于旧版一个大层的分段数，也是常见私有仓库每地址连接限制之下。
- **预算在每个仓库 host 上而不是整个节点**：连接数与频率限制属于一个地址。代价是经同一代理访问多个仓库时靠代理键共用一份，而非精确按仓库区分。重定向到的 CDN 域名没有单独建池，因为它的限额不可预知，也随每个 blob 变化；它的拒绝与重置同样会让整次拉取降速。
- **相对判断需要连续两个窗口**：兄弟连接的窗口在不同时刻结束，整条链路突然变慢时，第一个结算的连接会拿变慢前的兄弟数据比较；连续两窗口让兄弟数据赶上，避免误判。绝对下限不需要比较，不等。
- **不做向下探测**：只在有收益时加倍，没有「试着减少连接看速率是否不变」。起点 4 在慢链路上的浪费有限，向下探测的收益不足以抵消复杂度。
- **模型下载不在本决策内**：`connbudget` 保持通用（不知道 HTTP、文件与任务），为模型下载等其他下载预留；草案 MR !538 的 `Pool`/`Session` 设计在此基础上移植，没有合并其余部分。

## 后果

- 新增 agent 参数 `--image-pull-max-connections`（环境变量 `GPUWORKS_IMAGE_PULL_MAX_CONNECTIONS`），默认自动；协议、server、界面不变。
- `native.Downloader` 增加 `Budget`（`*connbudget.Hosts`）与 `Tune`；`Budget` 为空时每次 `FetchAll` 用私有的固定预算 `Workers × RangeParts`（旧行为），既有测试夹具因此不变。
- 测试用 `internal/testenv/fakeregistry`（HTTP/1.1 + TLS、307 到 blob CDN、严格 Range、单连接与整体限速、每来源连接数限制回 429 或重置、中途重置、停滞、忽略 Range）验证吞吐行为、连接数上限、`Retry-After`、令牌全部归还与无 goroutine 泄漏。
