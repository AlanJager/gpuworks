# ADR 0070: 扩展分层与版本边界：开源代码只说可用性，单独构建的 server 经一组接口组合

日期：2026-11-16 · 状态：已接受，部分被 [ADR 0071](0071-installable-extensions.md) 取代（补充 [ADR 0040](0040-signed-multi-source-distribution.md) 的版本作用域、[ADR 0067](0067-runtime-outcomes-as-codes.md) 对扩展码的要求）

> 2026-11-17：[ADR 0071](0071-installable-extensions.md) 改为「通用核心 + 签名插件包」。决策 1（四个层级）被其分层取代，T1 只做核心内部组合；决策 10（按版本名分开的发布与升级）对官方发布流程撤回。其余决策保留，并由 0071 扩充（各条去向见 0071）。扩展路由已改挂在 `/api/v1/x/<名>/` 下。下文保留原文。

## 背景

gpuworks 要能被另一个 Go 模块当作库，编成带额外能力的 server：组织与权限、审计、计费、按功能开通的能力，以及厂商定制。这些能力要碰的地方各不相同：管理请求的路由、节点插入的事务、每次状态上报、控制台菜单、数据库表、安装与升级。

如果每项能力各自改开源代码，开源仓库会长出版本分支、产品专属的词汇和只为某个构建存在的代码路径；如果让扩展直接拿到 Store 或数据库句柄，单一写连接上的死锁、核心表被扩展迁移改写、表名冲突都会出现，而且一旦扩展依赖了这些内部细节，开源代码就再也不能自由重构。

有几件事一旦发布就不能再改：`server.yaml` 里给扩展保留的键名、扩展迁移的记录表、控制台清单的形状、可用性的词汇。它们需要现在定下来。

## 决策

1. **四个层级，能力放在能承载它的最低层。** T0 核心（开源）；T1 编译进 server 的模块；T2 server 子进程插件；T3 节点上的应用。要在每个管理请求、插入或状态事务里做决定，或在任何节点存在前就要工作的，才进 T1。本 ADR 只约定 T0 留给 T1 的接口。
2. **单一入口，零值即社区版。** 单独构建的 server 只经 `cli.Options`（版本名、扩展模块、控制台构建、发布通道、安装钩子、追加子命令）传入一切，再由 `cli` 交给 `app.Config`。不用 `init()` 注册，不加包级全局变量。`cli.Options{}` 就是 `cmd/gpuworks`。
3. **开源代码只说可用性。** 词汇是功能键（不透明，开源代码不解释）与四种可用性：完整、只读、锁定、隐藏，外加不透明的限额、链接和预先构造的 `ProductError`。商业或站点自己的规则与它们的状态，以及谁决定、为什么，只存在于功能来源一侧。社区路径从不查询功能门；只有扩展路由、扩展菜单项与扩展注册的守卫会指明功能键。开源代码从不按版本名分支，版本名只用于显示（`edition_branches` 预算为 0）。
4. **服务端决定，界面只渲染。** 每个门都在服务端的咽喉点执行：扩展路由的包装、节点插入事务、调度保持。控制台按 `GET /api/v1/console/manifest`（版本名、每个已声明功能的可用性、扩展菜单项、横幅）渲染，不自己推导。扩展路由必须二选一地指明功能或标记为社区路由，否则路由构建时 panic；扩展 GET 路由默认不给 AI 助手与 MCP 读。
5. **扩展不拿 Store。** 模块只经 `app.Host` 接触 server：自己命名空间的表（`store.ExtensionTables`，写连接上的事务与读池上的只读事务两个闭包）、日志、总线、数据目录、安装标识、由 master key 派生且与模块名绑定的密钥、自己那一节 `server.yaml`，以及注册路由、功能、横幅、节点插入守卫、调度保持者的方法。注册只在 `Init` 期间有效。保持者需要的节点集合同样经 `Host` 提供：读池上一次读出全部节点保持事实的 `NodeFleet`，与以节点 id 为键、由开源代码定义并读取（`store.NodeFleetChangeOf`）的节点插入、删除、保持事实变化主题；模块不解析事件原因文本。
6. **扩展迁移与核心迁移分开记录。** 扩展的迁移步骤记在 `namespace_migrations`（只在传入迁移集时创建），每个模块一个命名空间、一个以 `ee_` 开头的表名前缀；核心表永不使用 `ee_` 前缀。步骤所建对象不带前缀即回滚拒绝；本构建不认识的命名空间只告警；已知命名空间比二进制新、已记录的步骤缺失或改名都拒绝启动。
7. **`server.yaml` 保留一个 `extensions:` 键。** 顶层仍然严格解码；`extensions.<模块名>` 原样保留，由各模块严格解码自己的一节。没有模块认领的一节只告警，因此换构建后 server 仍能启动。
8. **写事务里的钩子必须是纯函数。** 插入守卫与调度保持者在唯一写连接的事务里被调用，只能从快照作答：一次原子读加一次 map 查找，不调用 Store，不做 I/O，拒绝时返回预先构造的错误。保持者只停止调度、从不驱逐；运维不能恢复被保持的节点，但可以停止调度或驱逐；启动时释放没有模块认领的保持。答案变了的模块请求重新应用（`Host.ReapplySchedulingHolds`）：请求不阻塞、合并，全表写事务之间有下限间隔，在 server 的后台循环里执行，不在调用方或钩子里。
9. **正在运行的负载从不被中断。** 可用性变化只作用于新的请求与写入。
10. **版本作用域的发布与升级。** 签名的发布索引写明版本名，构建的发布通道只接受同一版本名的索引；升级比较新旧二进制的版本名，不同则需显式确认（ADR 0040 的补充）。
11. **每个扩展点在开源仓库里都有对假模块的契约测试**（`internal/testenv/extmodule`），没有模块的构建，路由清单与社区版逐条相同。

## 取舍

- **编译进来的模块 vs 进程外插件**：要在插入事务、每次状态上报、每个管理请求里同步决定的能力，进程外插件做不到；代价是模块依赖开源仓库的内部包，这由契约测试与本页文档约束，单独构建的一方需要持续对开源 master 构建。
- **只给命名空间表 vs 给 Store**：只给表让扩展读核心数据时必须经 Store 的方法、API 或钩子，写起来更绕，但写连接死锁、核心 schema 被改写、开源重构被冻结这三个问题都由类型排除了。
- **只说可用性 vs 在开源里实现商业规则**：开源代码因此不知道任何商业规则，社区版不受任何此类逻辑影响；代价是功能来源一侧要自己把自己的状态映射成四种可用性和带码的说明。
- **隐藏回 404、锁定回 403**：隐藏的功能对这个 server 来说不存在，404 与没有这条路由时一致；锁定的功能在界面上可见，403 带码说明为什么不能用。

## 后果

- 新的扩展需求先问能否用已有接口表达；确需新接口时，它在调用它的包里定义，经 `Host` 暴露，带一个对假模块的契约测试，并更新 `docs/dev/extensions.md`。
- `api.Deps` 只为扩展增加了一个字段（`Extensions`），之后的 API 侧钩子都加在这个结构体里。
- 契约与操作细节见 [扩展点](../dev/extensions.md)。
