# ADR 0074: 节点连接展示来自认证会话，恢复宽限不由展示驱动

日期：2026-11-18 · 状态：已接受

## 背景

持久化的 online 行能跨过控制面进程重启，新的 Hub 却尚未拥有该节点的 session。节点列表、GPU 和镜像视图、诊断及统计若直接展示旧行，会与真正能否路由请求相矛盾。反过来，启动时把所有节点写成 offline/connecting，又可能改变调度依据、触发不必要的替换。

## 决策

1. **online 必须有已认证的实时 session。** 连接事实由 Hub 提供；未经验证的 hello 或其声明的 UUID 不得修改他人节点状态。数据通道重连不替代控制通道身份，也不接受已失效 token。
2. **展示采用派生投影，不写回调度事实。** 有实时 session 时显示 online；没有 session、持久化仍为 online 时显示 connecting，等待既有断连与 stale 规则收敛。已明确 offline 的节点保留现有恢复阶段折叠，而不把所有历史离线都假称正在重连。
3. **对外读模型使用同一规则。** 节点列表、详情、筛选、总数、关联 GPU/镜像状态和诊断、在线统计都使用这个投影。不能只修一个页面，也不能把 Hub 回调注入 Store 让存储读取隐藏网络状态。一次读批量加载所需事实，不按节点再查数据库。
4. **调度与 failover 保留原恢复宽限。** controller 每轮 Run 的 watchingSince/sighted 规则继续为节点重连留时间；展示为 connecting 不意味着运行实例应被删除或迁移。宽限内不创建重复实例，期满仍未恢复则按原失联策略处理。
5. **不新增存储状态或凭据自愈。** 复用现有状态、恢复相位和认证事实，不新建表或持久化 epoch。token 真实失效的原事故需要独立证据，不能通过自动接受、重置凭据或信任 UUID 伪装恢复。

## 取舍

- 直接把持久化 online 当当前在线会产生假事实；直接改写它来修 UI 又会影响调度。派生读模型让展示如实表达等待认证，同时保留既有控制规则。
- 单页面临时修补会让列表、计数和关联视图互相矛盾；共用连接投影在所有消费点保持同一语义。
- 这不是新的全局状态机或多控制面租约设计。以后连接权威改变时应更换事实提供者，不能让各读模型自行猜测。

## 验证

在真实 HTTP 读模型中，旧 online 行配上无 session 的新 Hub 显示 connecting，筛选和计数一致；认证成功后 online、断开后遵循 offline/恢复相位。覆盖无效 token、伪造 UUID、GPU/镜像/诊断读模型与批量读取数量。保留短断、长停、启动和重新连接的 controller 回归，证明宽限内不产生替换或重复容器，期满正常失联处理。
