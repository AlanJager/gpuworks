# ADR 0081: 插件路由按角色授权：路由声明 `access: role`，角色与动作由推送表授予

日期：2026-11-22 · 状态：提议（补充 [ADR 0071](0071-installable-extensions.md) 决策 8、9、11）

## 背景

插件路由的请求管线里，认证之后有一个授权接口点（`authorizeDynamic`，[扩展点](../dev/extensions.md)的第 4 步），今天总是通过。每条路由在签名清单里声明了 `action`（`<包 id>.<动词>`，「授权时用的动作名」），转发给插件的主体里也带着 `route_action`，但核心没有任何东西拿它去对照。

今天能挡住调用方的只有路由的访问级别：`admin`、`admin_session`、`member`、`public`。核心的用户角色只有 `admin` 与 `user` 两个（`users.role`），主体的 `roles` 是只含这一个角色的列表。所以「登录用户里只有一部分人能调这条路由」今天表达不了，只能由每个插件自己读主体、各写一遍判断。

ADR 0071 已经为此留了词汇：T2 包的能力里有「自定义角色」；授权类推送表「按键独占或按角色键取并集、冲突即拒绝」；表种类里保留了 `roles.core_actions`（角色到核心动作，还没有 schema）；卸载预览里有 `UsersAffected`，注明「schema 1 没有绑定用户的表」。缺的是具体的表与执行规则。

有一个约束决定了设计的形状：只有 `admin` 与 `user` 两个角色时，一张「角色到动作」的表能表达的东西，访问级别已经全部表达了。按动作授权只有在用户能持有这两个之外的角色时才有内容，所以角色的来源与动作的授予必须一起定。

## 决策

1. **路由用访问级别声明自己受角色管辖：`access: role`。** 它排在 `member` 与 `admin` 之间：要登录用户或平台令牌（读令牌只能读），并且调用方持有的某个角色被授予了这条路由的 `action`。平台管理员（`users.role` 为 `admin`）总是通过。访问级别多一个取值会改变执行结果，所以这是清单 schema 2；旧核心拒绝安装 schema 2 的包，而不是把 `role` 当成别的级别。
2. **受不受管辖由路由自己的签名清单决定，表只授予、不划定范围。** 没有任何表授予某个 `role` 路由的动作时，它只对平台管理员开放。这样授予方掉线、被卸载或包文件损坏时，结果只会收紧，与 ADR 0071「删除或损坏包文件永远不会放松限制」一致。反过来的设计（动作一旦被某张表提到才受管辖）在授予方消失时会把路由重新向所有登录用户开放，所以不取。
3. **两种新的授权类推送表，都是特权表，证书授予才能推。**
   - `roles.bindings`：行是 `{user_id, roles}`，把核心的用户 id 绑到角色名上。行引用核心 id，不引用用户名。
   - `roles.plugin_actions`：行是 `{role, actions}`，把角色名绑到插件路由的动作上。动作必须是某个已安装包的清单里声明过、且所在路由为 `access: role` 的动作；其余的行整表拒绝，不悄悄丢弃。
   两张表都带 `down_grace_s`，行数有上限，超过即拒绝整表。
4. **角色名是一个词，按键独占。** 角色名沿用主体已有的语法（`[a-z][a-z0-9_]{0,31}`），所以主体的 schema 不变。第一个绑定或授予某个角色名的包拥有它；另一个包再推同名角色，整表拒绝并报冲突。`admin` 与 `user` 是核心的名字，任何包都不能推。一个站点可以有多个推角色的包，各管各的名字。
5. **用户的有效角色 = 核心角色 ∪ 推送的角色。** 主体的 `roles` 带有效角色，已排序；`platform_admin` 与 `local_admin` 仍然只看 `users.role` 与 `users.local_admin`，推送的角色永远不能让一个用户成为平台管理员。平台令牌按它所属的用户取角色。
6. **在现有的接口点执行，不进热路径以外的任何地方。** `authorizeDynamic` 对 `access: role` 的路由读一个快照（一次原子读加 map 查找，不调 Store，不做 I/O，不调插件），拒绝时回 403 与带码的 `PLUGIN_ACTION_FORBIDDEN{action}`。路由的功能键被隐藏时仍然先回 404：禁止动作的 403 不能暴露一个隐藏功能的存在。其余访问级别的路由不读这个快照，行为与今天逐字节相同。
7. **掉线按授权类处理。** 推角色的包掉线超过宽限后，它的绑定与授予都被丢弃：经它才被授予的 `role` 路由回到只对平台管理员开放。启动时在路由构建之前读入这两张表，所以核心重启后、任何插件起来之前就按最后的状态执行。
8. **卸载预览说出受影响的人。** 推过 `roles.bindings` 的包，卸载预览里的 `UsersAffected` 是它绑过角色的用户数。
9. **核心路由不在本 ADR 内。** `roles.core_actions` 继续保留、仍然没有 schema。它将来落地时用同一套角色名与同一张 `roles.bindings`。

## 实施顺序

每一步单独合入，都带对假插件进程的契约测试（ADR 0071 决策 21）。

1. 清单 schema 2 与 `access: role`；`authorizeDynamic` 按空快照执行（`role` 路由只对平台管理员开放）；错误码与文档。这一步之后的可见行为与把路由声明成 `admin` 相同，它的作用是把线上格式定下来。
2. `roles.bindings`：表、持久化、有效角色进入主体、卸载预览。
3. `roles.plugin_actions`：表、快照、按角色放行。到这一步，按角色授权才对用户可见。

## 取舍

- **推送表 vs 由编译进来的模块传入一个判定函数。** 判定函数最省事，但它是第二条授权通道：绕开推送表的合并规则、掉线降级与卸载预览，而且今天没有任何实现方。按 ADR 0071，T1 只做核心内部组合，授权来自权威推送。
- **新的访问级别 vs 路由上加一个布尔字段。** 两者都要新的清单 schema。访问级别本来就是「谁能调」的唯一声明，放在一处读；布尔字段会让 `admin` 加「受角色管辖」这类没有意义的组合也能写出来。
- **平台管理员总是通过 vs 管理员也受角色约束。** 管理员本来就能卸载包、覆盖限制、改任何用户，拦他调一条路由挡不住什么，却会在没有装任何角色包时让 `role` 路由谁都用不了。需要「管理员也不能看」的数据由插件自己按主体判断。
- **角色名用一个词 vs `<包 id>.<角色>`。** 带命名空间的名字不会撞名，但主体的 `roles` 今天按「词」校验，改它是主体 schema 2，所有已发布的插件都要跟着升。按键独占加冲突即拒绝，用安装时的一次检查换来线上格式不动。
- **只有允许、没有拒绝行。** 有拒绝行就要定义允许与拒绝的先后，合并也不再是并集。要收回权限，去掉授予即可。

## 不做的

- 不给核心加角色管理界面或角色表：角色由包定义和推送，核心只执行。
- 不做数据范围：主体里的 `scope_projects` 不由本 ADR 填充。
- 不让站点管理员在核心里改一条插件路由的访问级别；要收紧第三方包的路由，是另一类（限制类）决定。

## 待定

这些是提议里我做了选择、但需要确认的地方：

1. 平台管理员总是通过 `role` 路由（决策 1）。
2. 角色名用一个词并按键独占（决策 4），而不是带包名的命名空间。
3. 一个站点允许多个推角色的包（决策 4），而不是只认一个角色权威。
4. 第 1 步单独合入的价值只是定下线上格式；如果近期没有要推角色的包，可以把三步放在一起做，或整体推后。
