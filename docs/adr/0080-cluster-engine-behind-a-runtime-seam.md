# ADR 0080: 集群引擎经一个运行时接口编进 server，不再用构建标签切分

日期：2026-11-21 · 状态：已接受，尚未实施（补充 [ADR 0070](0070-extension-tiers-and-edition-boundary.md) 决策 2，不改 [ADR 0071](0071-installable-extensions.md) 决策 18）

## 背景

控制面集群的引擎在开源仓库里，由 `dqlite` 构建标签与默认构建隔开。社区发行版不编入它；带集群运行时的 server 用 `-tags dqlite,nosqlite3` 把它编进来，集群命令与数据库辅助程序在企业仓库。

这道标签在一周内把带构建标签的生产文件从 69 个推到 265 个。在 `52f24211a` 上实测：

- 132 个生产文件带 `linux && dqlite`（`app` 98、`store` 17、`cluster` 16、`testenv` 1），另有 15 个带 `!linux || !dqlite` 的存根文件，为同一批符号给出单机实现；
- 132 个文件里只有 13 个真的引用 `github.com/canonical/go-dqlite/v3`（`cluster` 10、`store` 2、`app` 1），其余是因为引用了带标签的符号才带上标签；
- 存根声明 42 个顶层符号，默认构建里只有 14 个有调用方，其余 28 个只为企业仓库的集群命令存在；
- 带标签的代码给 `*App` 加了 53 个方法、给 `*Store` 加了 10 个方法，用到 `app` 的 37 个、`store` 的 33 个未导出标识符；
- 另有 185 个带标签的测试文件。开源 CI 只对带标签的构建做 `vet`，不运行这些测试。

标签也不是引擎的边界。`internal/server/enrollment` 整个包、`store` 里约 51 个集群文件、集群表的迁移都不带标签，默认构建编入它们却用不到。于是「这个 server 是不是集群成员」这个运行时事实被写成了成对的文件：改一个接口要同时改带标签的实现和它的存根，而存根那一半开源 CI 测不到另一半。

`app` 里其实已经有一个运行时接口：`haRuntime`（`ha_runtime.go`，8 个方法，单机时为 `nil`）。标签管的是它之外的部分：谁来打开数据库、谁来构造这个运行时。

`nosqlite3` 是另一回事：go-dqlite 的 `client` 包在没有这个标签时引用 `github.com/mattn/go-sqlite3`，本仓库只用 glebarez 驱动。它是整个构建的开关，不标在文件上。

## 决策

1. **引擎留在开源仓库，收进自己的包，经一个值传给 server。** 单独构建的 server 经 `cli.Options` 把集群运行时交给 `app.Config`；零值是单机 SQLite，与今天的 `cmd/gpuworks` 逐条相同。`cmd/gpuworks` 不引用引擎包，社区二进制不链接 go-dqlite。这是 ADR 0070 决策 2（单一入口，零值即社区版）在数据库这一层的延伸。
2. **`dqlite` 构建标签从生产代码里去掉，15 个存根文件删除。** 平台标签（`linux`）只留在确实调用 Linux 系统接口的文件上。「是不是成员」由传入的运行时回答，不由编译回答。
3. **接口取现有的三处接缝，不新造概念。**
   - `app`：现有的 `haRuntime`，加上今天由标签选择的三个入口：打开一个业务未开放的成员（`openClosedMember`）、打开业务库（`openServeStore`）、观察集群（`observeCluster`）。
   - `store`：五个运行时数据库的打开函数、三个复制错误的判定（`ReplicatedReadInterrupted`、`ReplicatedLeaderUnavailable`、`ReplicatedWriterBusy`）合成一个后端值，在打开 Store 时给定；缺省是 SQLite 后端，三个判定恒为假。Store 上已有的集群回调字段（本地调度 leader、成员授权、传输授权等）随后端一起给定。
   - `cluster`：两个 go-dqlite 专属的构造（`StartDatabase`、`OpenRemoteExistingReadSQL`）。
4. **运行时拿到的是一个窄的宿主，不是 `*App`。** `haRuntime` 的方法今天收 `*App` 并直接读它的未导出字段。引擎出包之后，这些读取收敛成一个接口，由 `app` 实现。它是核心内部的组合，不是 `app.Host` 上的扩展点：ADR 0070 决策 5（扩展不拿 Store 与数据库句柄）继续成立，因为引擎是同一仓库里的核心代码，与核心一起重构、一起测试。
5. **`nosqlite3` 作为构建开关在 Makefile 里统一给出**，不再和 `dqlite` 成对出现在目标里。架构检查新增一条：`cmd/gpuworks` 的依赖闭包里没有 go-dqlite 与 `mattn/go-sqlite3`。
6. **带标签的测试变成引擎包的普通测试。** 需要真实辅助程序的用例在没有 `GPUWORKS_DQLITE_BIN` 时跳过并打印原因，`GPUWORKS_TEST_STRICT=1` 下失败。核心包（`store`、`api`、`app`）的既有测试要能对着集群后端再跑一遍，由 `testenv` 的一个运行时开关选择后端，取代今天的 `defaultDatabase` 标签对。
7. **社区发行版仍然不带集群功能**，集群命令、辅助程序、打包与入口层仍在企业仓库，是否授权仍未决定。本 ADR 只改引擎进入 server 的方式。

## 实施顺序

每一步单独合入，合入后默认构建与带集群运行时的构建都能编译、测试通过；企业仓库的集群命令依赖 `app` 与 `cluster` 的导出函数，凡是改到它们签名的一步，都配一个企业仓库的改动并更新它钉住的开源提交。

1. `store`：后端值取代 `runtime_sqlite.go` 与 `runtime_dqlite.go` 这一对，以及 `replicated_read_error_*`、`import_runtime_*`、`testenv` 的 `database_*`。
2. `app`：三个入口经 `Config` 传入，删除 `app` 的五个存根。
3. `cluster`：两个构造经同一个值传入，删除 `cluster` 的六个存根。
4. 把只有集群用到的 `app` 文件移进引擎包，`haRuntime` 的方法改收窄宿主；去掉这些文件的标签。
5. `cli.Options` 增加集群运行时一项；企业仓库改为传入引擎而不是加标签；加上依赖闭包的检查，并给带 `dqlite` 标签的文件数设一个只降不升的预算，终值为 0。

## 取舍

- **整体移到企业仓库（未采纳）。** 要做的拆包工作与本方案相同，另外还要开源仓库长期保持约 130 到 190 个导出符号稳定，其中包括打开数据库与 Store 的回调，这正是 ADR 0070 决策 5 排除的东西；写路径上的每次重构都变成两个仓库的改动。集群表的迁移与 `store` 里约 5500 行集群代码仍然留在开源仓库，所以开源也不会只剩一个接口。企业 CI 今天在标签下重跑 `store`、`api`、`app` 等约 960 个测试文件，这是唯一验证「核心行为在集群后端下也成立」的地方；引擎在仓库外时，这些包内测试无法再对着它跑。
- **只移 `cluster` 与引用 go-dqlite 的文件（未采纳，可作为后续）。** 这是唯一能让 go-dqlite 离开开源 `go.mod` 的做法，要保持稳定的导出面也小（约 31 个 `cluster` 符号加 3 个判定）。但它留下约 115 个带标签的粘合文件在开源仓库里，并且从此在开源 CI 里永远跑不到。本方案完成后边界是清楚的，届时若授权策略要求 go-dqlite 离开开源仓库，再做这一步的代价是移动一个包。
- **引擎编进默认构建的代价。** 开源仓库的 `go test ./...` 会编译引擎包；需要辅助程序的用例在没有它时跳过，所以要按 `CLAUDE.md` 的规则看清跳过数，不能把跳过当成通过。引擎包需要 `app` 与 `store` 导出一批内部接口，面比今天的同包访问宽，但在同一仓库内可以原子重构。

## 后果

- 改一个集群相关的接口只改一处；默认构建的编译器能看到它的全部实现。
- 新增「只在某种部署形态下存在」的能力时，先问能否经传入的值表达；构建标签只用于确实无法在别的平台编译的文件。
- 企业仓库 `gpuworks-ee` 的 ADR 0017 决策 1（「引擎在 `dqlite` 构建标签后」）在第 5 步随之修订为「引擎经 `cli.Options` 传入」；它的其余决策不变。
