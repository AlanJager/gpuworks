# ADR 0033: 生命周期操作落到副本：排空状态、默认滚动重启、多个多机副本、睡眠意图在实例上

日期：2026-09-30 · 状态：已接受

依据：[实例级生命周期计划](../../artifacts/archive/2026-09-30-instance-lifecycle/plan.md)。修改
[ADR 0028](0028-pd-disaggregated-deployment.md) 与 [ADR 0029](0029-deployments-reconcile-as-units.md) 的若干决策，见下。
术语以 `CONTEXT.md` 为准：**副本**即 ADR 0029 的 unit（代码与线协议仍叫 unit），**实例**是某个副本某一代的一个 rank。
ADR 0028 里"一个 unit 就是该角色的一个实例"的说法按此读作"一个副本"。

## 背景

睡眠、重启、停止、删除原来只挂在部署上；PD 另有按角色扩缩、重试单个副本与整组重启。多副本部署改一处就要整体下线：
重启只对 PD 开放且不滚动，排空只在网关的 PD 路径生效，睡眠意图只有部署上一份，普通多机一个部署只能有一个多机副本。

## 决策

**被点名下线的实例是一个状态：`draining`。** 它由服务端独占（agent 上报不覆盖，除非报告已停止），`MatchUnits`
视它为不活跃（副本立即补位），账本仍把它计为占用，期望状态仍下发给 agent。controller 对它与未被认领的活跃 leader
（Excess）用同一个排空计时，到点退役为 `removing`。网关只转发给 running 的实例，所以排空对所有形态生效。
单实例重启、指定缩容与滚动重启都表达为把某个 leader 标成 `draining`；对 follower 的操作作用于它所在的整代。
不引入"停住某个实例"：停掉一个副本就是缩容并指定它。
*修改 ADR 0029*：排空不再只在网关的 PD 路径生效。

**重启对所有形态开放，默认滚动。** `POST /deployments/{id}/restart {"strategy":"rolling"|"all"}`，默认 rolling。
起点记在 `deployments.restart_requested_at`（迁移 116）：仍有创建于该时刻之前的活跃 leader 的副本就是待换的。
controller 只在全部副本可用时排空其中最早的一个旧 leader，一次一个；全部换完清掉这一列。部署离开 active 时清掉。
*修改 ADR 0028*：整组重启不再只对 PD 开放，也不再只有非滚动一种。

**普通多机可以有多个多机副本。** 副本列表写进已有的 `Deployment.Placement` JSON 的 `units`（形状同 PD 的 unit），
不加列；没有 `units` 的旧部署按 `NodeIDs` 读成一个副本。每一代新生成进程组标识（用户填的组名作前缀），
两个副本同一尝试号也不会撞；参数网络按副本解析；非首个 leader 节点的副本用自己 leader 的参数网络地址作 master。
不同副本的 leader 不能在同一台节点（leader 监听部署的 master 端口）。每个多机副本各自一份重试预算。
网关在代完整的 leader 之间按路由策略选。`nnodes`（每个副本的 rank 数）创建后不可改，改它就是克隆。

**睡眠意图记在每个实例的期望状态上。** 部署级睡眠在一个事务里写全部活跃实例的 `desired_sleep`，
并记下 `deployments.desired_sleep`，含义收窄为"部署整体处于睡眠命令下"，只用作新实例启动的默认值；
对单个副本或 PD 角色的命令只写这些实例。唤醒任何一个副本即撤销部署整体的命令。一个实例休眠失败只回退它自己的意图
（与仍在生效的部署整体命令），其他已睡着的副本不被唤醒。controller 在内存里记每个实例最后推送的意图，只推送变化；
没推过的实例只在上报级别与意图不一致时推一次——server 重启后 agent 重连会拿到完整的期望状态，所以推送记录不落库。
网关逐实例排除被下令休眠或仍在休眠的实例（命令一下达即生效），一个都不剩才返回 503 asleep；
PD 模式允许 prefill 为空时，prefill 全部休眠等同于缩到 0。模式不允许为空的角色只随整个部署休眠。

## 后果

- `settleRetiring` 的阻塞范围仍是整个部署：一个实例还在 `removing` 时，其他副本的新一代也不启动。
  按"同节点重叠 GPU"缩小范围的收益主要在 PD 与多机多副本，但会让普通单机副本（候选节点是全部部署节点）几乎总被阻塞，
  复杂度不值；慢速拆除（如 udocker 删除 rootfs）会拖慢补位。
- 配额（显存/SM 限额、切分后端）变更仍整体替换：dGPU 下能否 surge 需要账本判断，暂不改成滚动。
- 滚动一次只动一个副本，没有 `max_unavailable`。
- 多机副本可以休眠，部署级与单个副本都可以：指令发给 leader，引擎的多机执行器带着 follower 一起睡和醒
  （vLLM 0.25 上真机验证，PD 的两机 decode 副本与普通多机副本同一启动方式），单副本指令的意图写在该副本全部 rank 上。
  follower 不上报睡眠级别，账本按它所在那一代 leader 的上报级别计残留与唤醒准入；部分唤醒以副本为单位。
- 创建时不接受多机副本列表，先建一个再加。
