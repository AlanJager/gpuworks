# 贡献指南

## 开发流程

1. 从目标分支创建范围明确的分支；不要混入无关改动。
2. 先从代码、测试和当前 ADR 确认契约，再修改实现与同层测试。
3. 单文件超过 600 行时拆分；DTO 与 store entity 分离，事务提交后显式发布事件。
4. 运行 [`CLAUDE.md`](../../CLAUDE.md) 要求的提交前检查，再提交 MR，并写明未覆盖分支与外部验收状态。

## 文档落位

- 教程放 `docs/tutorials/`：从零学习主线，不展开原理。
- 操作指南放 `docs/how-to/`：解决一个任务，不重复入门教学。
- 精确字段、矩阵和协议放 `docs/reference/`：不写叙事式操作流程。
- 设计动机放 `docs/explanation/`；不可逆取舍另写 `docs/adr/NNNN-*.md`。
- 开发操作放 `docs/dev/`；内部活台账放 `docs/dev/ledgers/`。
- 一次性计划、验收、审计和真机过程放 `artifacts/`：进行中放 `work/<YYYY-MM-DD>-<主题>/`，收口后
  整个主题目录搬进 `archive/<YYYY-MM-DD>-<主题>/`，独立完成的调研放 `research/<YYYY-MM-DD>-<主题>/`；
  状态只写在计划文件自身的 YAML frontmatter 里，索引见 `artifacts/README.md`。

新增、移动或删除文章时同步[文档索引](../README.md)，沿用现有分类和顺序来源，不另建独立排序。
调整分类、路径或文章类型时说明原因，并检查已有链接。

`docs/` 保留中文原文，`docs-en/` 按相同相对路径保存英文译文；代码、API 字段和 CLI 输出保持原文。现行正文不绑定 M 编号，不依赖
仓库外相对路径；面向公开读者的正文不新增私有 artifacts 引用，设计依据写入 `docs/` 或 ADR。根目录
[`CONTEXT.md`](../../CONTEXT.md) 是术语的唯一完整定义，用户术语表只做子集。

英文翻译保留原文的章节、步骤、限制和示例，不用摘要替代全文。术语优先匹配 GPUWorks 英文界面；
翻译说明与图片替代文本，不改命令、路径、参数或示例值。现有中文截图可复用，但英文正文必须说明截图语言。
源文档改变后复核对应译文，并更新 `docs-site/translations.json` 中已复核原文的 SHA-256；不能只刷新哈希而不检查译文。
运行 `python3 docs-site/check_translations.py` 检查过期译文与代码块；全站英文验收额外使用 `--require-complete`。

## 写作约定

按文档用途组织内容：教程和操作指南帮助读者完成任务，原理说明帮助理解概念与机制，参考手册便于查阅。
人工编辑与自动维护遵循同一套写作约定。下文“必须”为验收要求，“建议”为可按页面内容调整的写法。

### 内容结构

how-to 和教程必须在进入操作前交代完成目标、适用场景和前置条件，让读者先判断是否适用、准备什么。
开头可采用以下模板；这是信息检查模板，按内容选择段落、列表或表格，不要求逐字照搬：

```markdown
# 文章标题

一句话说明本文要完成的任务与完成后能得到的结果。

**适用场景**：遇到什么需求或问题时使用本文；存在范围限制时一并说明。

## 前置条件

- 所需权限，以及已经准备好的节点、模型或服务。
- 影响能否开始的版本、硬件、网络条件；仅列本文实际需要的条件。
```

标题或简介已经交代目标、场景时不再重复增加标签；已有“开始之前”“准备”等同义小节可继续使用。
条件只有一句时可直接写在开头，多个独立条件用列表，需要逐项对照配置时用表格；没有额外前提时不建空章节。
共同前提前置，只有某条操作路径需要的条件写在该路径开始处，不扩大为全文要求。
各类文档必须覆盖下列内容；不要求重复填写开头信息，也不要求照搬全部章节标题。

| 类型 | 必须覆盖的内容 |
|---|---|
| 教程 | 一个明确的完成目标、准备条件、连续操作、最终验证 |
| 操作指南 | 适用场景、必要前提、完成特定任务的步骤、结果检查；有已知阻塞条件时说明处理方法 |
| 参考手册 | 适用范围、按主题组织的术语、字段或能力；存在默认值和限制时明确说明，必要时提供示例 |
| 排障指南（属于操作指南） | 问题现象、检查方法、按检查结果选择的处理方式、恢复验证 |

教程围绕一个明确目标，采用具体、可复现的示例，按连续步骤完成主流程，以目标达成的验证结束。
how-to 按读者要完成的操作组织章节和步骤，不按后台模块或实现过程展开。存在多个可选操作路径时，
先说明选用条件，再分别给出关键动作和完成依据。同一任务在本文范围内的并列方式保留在正文中，详细参数或前置准备可链接专项指南。
推荐某种方式须有文章目标或产品行为的依据，不能因此省略范围内其他方式的关键步骤，或仅留下链接。

教程和操作指南的主流程保留影响方案选择、操作执行或结果判断的信息，包括必要前提、服务中断影响和删除范围；
解释紧跟相关操作。指标的定义与统计口径、状态的含义及变化条件、选项生效后的行为、自动处理的结果与限制，
属于用户理解产品和判断结果所需的信息，必须在相关正文中说明；不能压缩成只有名称、结论或参考链接。

必要解释保留后，内部模块、数据结构、完整算法和协议实现等细节可链接已有参考或原理说明，链接前确认目标确实覆盖相关内容。
没有现成说明、但有助于深入排障的实现细节，可以放在文末补充或折叠说明中；必读的含义、条件、动作、风险和判断依据不能移入折叠内容。

参考手册中的示例用于解释字段或协议，不扩展成叙事式操作流程。
接口路由清单沿用按资源分组的表格，便于先找到接口；简单接口用“方法、路径、用途、鉴权”即可，
在说明中补调用必需的参数与返回内容。写法可参考 [LiteLLM 模型管理 API](https://docs.litellm.ai/docs/proxy/model_management#automation-api)
的简表，以及 [llama.cpp 模型加载接口](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#post-modelsload-load-a-model) 的短说明。

- 按接口复杂度决定信息量，不给每条路由机械套用参数表、完整响应字段表、curl 和错误码表。
  必需输入写清所在位置；默认值、取值范围、空值语义及特殊权限影响调用时必须保留。
- 示例只在请求形状或结果不直观时增加，使用最小有效请求和简短响应；省略字段时明确标注，不能把示意当完整结构或实测记录。
- 返回值优先说明状态、指标口径、异步结果与容易误解的字段。字段名已清楚表达的内容不逐项重复解释，
  同一对象不在列表、详情和操作响应中反复展开。
- 鉴权、分页和通用错误集中定义，接口只补自身差异。较长但必要的说明放在同一资源下的短小节，表格链接过去；
  已有文档确实覆盖的算法或协议细节可引用。不得以精简为由丢掉删除范围、服务中断、状态变化、限制或错误处理依据。
- 调用方不需要的包名、内部执行步骤和历史修改过程不夹在路由说明里；维护说明放在文末。

异常分支、替代方案、资源清理和机制补充均不作为固定章节；与当前目标有关时按需说明，不增加空章节。

### 操作步骤与示例

**必须：** 教程和包含操作步骤的指南按实际操作顺序写主流程，关键步骤说明操作位置、具体动作和完成依据。
页面操作写明入口与按钮；命令写明执行的机器、终端及必要的工作目录。

- 在本文声明的适用范围内，影响操作继续、方案选择或结果判断的异常分支和替代方案，必须说明触发条件与处理方式。
  简短分支紧跟相关步骤，影响能否开始的条件在执行前说明；较长的前置准备或异常处置可引用已有操作指南或排障文档，
  当前任务的并列操作方式按上文“内容结构”保留关键步骤。
  主方案在某种适用条件下无法使用时，提供经过确认的替代方案并说明选用条件；不要求逐一覆盖本文范围外的情况。
- 根据场景写明实际需要的权限、硬件、模型、版本和网络条件；必填占位符说明从哪里取得、在哪里替换。
- 创建、配置、调用和验证使用同一组资源名称和参数；需要说明清理方法时，与创建方式匹配，并说明删除和保留的对象。
- 一个步骤围绕一个阶段性目标；可选操作放在相关主步骤之后，影响能否继续的条件在执行前说明。
  系统自动完成的动作写成该步骤的说明或预期结果，不列成需要用户执行的步骤。
- 命令注明必要准备，代码块标注语言；命令与输出分开，不混入终端提示符。输出注明需要检查的关键内容，
  不要求匹配随机 ID、时间戳等变化值。需要检查结果再继续时，拆开前后命令并写明继续条件；
  相互替代的命令分别展示，说明替换哪一步，避免读者误以为要全部执行。
- 描述代码里的具体行为（错误码、flag、默认值、端口）时先读代码再写；参考手册里的 flag 表以 `--help` 输出为准。
- 最终验证对应教程目标。例如，部署并调用模型的教程需要验证正常响应，不能只检查实例“运行中”。
- 未验证的组合不写成确定可用；示意输入和输出不能标成真实验证结果。

### 截图与流程图

**必须：** 用户教程包含帮助读者跟随步骤、核对结果的配图；涉及 UI 操作时，截图覆盖操作入口、关键配置和完成结果。
相邻动作可以共用一张图，不要求每次点击都截图。

其他文档按内容需要配图：操作指南和排障指南在入口难定位、配置容易选错或结果需要辨认时补截图；
原理说明、参考手册等不强制配图，文字已经清楚时无需增加图片。流程图用于帮助理解关系或过程，不作为每篇文档的必备项。

- 截图放 `docs/assets/screenshots/`，用 `![说明](../assets/screenshots/xxx.png)` 引用；界面用中文，
  分辨率 1440×900 起，避免出现真实地址、令牌和主机名。发布站点由 `docs-site/stage_docs.py` 复制图片并改写成站内路径。
- 图片紧跟对应步骤，图注或替代文本说明应核对什么；正文仍写清路径、按钮、输入和预期结果，不以“按图操作”代替步骤。
- 截图与正文使用一致的版本、场景及资源名称；配置图展示示例填写后的关键值，完成图展示实际达到的状态。
- 截图来自实际界面，不用原型、合成状态或其他场景冒充操作结果。
- 命令、错误信息和关键输出提供可复制文本；CLI 操作不强制配终端截图。
- 需要截图但缺少可用截图时，在评审记录中列明待补内容，不以占位图片表示已完成。
- 流程图用 ```mermaid 代码块（GitHub 与发布站点都能渲染），节点标签含括号、冒号时用双引号包裹。

### 文风与排版

**必须：** 步骤以“打开”“选择”“填写”“点击”“检查”等动作表达；界面名称与实际文案一致。
按钮、菜单和字段标签加粗，命令、路径、参数和 API 字段使用代码格式；必要术语首次出现时简短解释，
并与现有术语定义一致。操作顺序用编号列表；字段对照和条件说明按下表选择形式。

**建议：** 根据内容特点选择表达形式：

| 内容特点 | 推荐形式 |
|---|---|
| 简短背景、目的或一个条件 | 短段落 |
| 多项相互独立的前提或注意事项 | 无序列表 |
| 必须按顺序执行的操作 | 编号步骤 |
| 流程包含几个明确阶段 | 阶段小标题，每阶段组织相应步骤 |
| 多个字段需要逐项填写，或多个选项需要按相同维度比较 | 表格 |
| 命令、配置、请求和输出 | 标明语言的代码块；命令与输出分开 |
| 某一步中的简短条件分支 | 紧跟该步骤，用“如果……则……”说明 |
| 较长且可独立使用的替代流程 | 当前任务的并列方式用独立小节；前置准备或异常处置可链接专项指南 |

优先选择能清楚表达内容的简单形式。不要把连续操作塞进表格，也不要把一句话能说明的条件拆成多个章节。
已有格式表达清楚、信息完整时予以保留，不为统一模板重排或改写。
表格按列内容分配宽度，保证名称和指标列可辨认；窄屏可横向滚动，不靠逐字换行、缩小字号或删减说明挤进一屏。
一个段落讲清一件事，提示框留给影响操作的重要条件。
避免“很简单”“只需”等代替必要步骤的说法。不设置统一的字数、截图数或章节数指标。

### 更新与验收

**必须：** 修改已有文档时，按以下顺序确定取舍：

1. **确认内容范围。** 保留原文仍有效的任务、操作方式、必要条件、兼容限制和结果判断。
   功能变化或明确的范围调整需要增删时，说明依据；不能把“精简”理解为缩小适用范围或替读者选择操作方式。
2. **判断修改程度。** 原文清楚、准确就保留；排版能解决的问题只调整排版；内容有误、缺失或表达不清时修改对应部分。
   how-to 主要在讲内部实现，或操作被说明打断时，围绕操作重组相关正文，保留准确的命令、必要分支、产品逻辑和结果判断，不扩写无关内容。
3. **处理冗余。** 删除重复结论、合并重复解释，内部实现细节按“内容结构”引用或补充。
   不以删除仍有效的用法、必要条件或成功判断来缩短篇幅，也不把后台自动行为改成用户需要执行的步骤。
4. **选择表达形式。** 内容确定后，再按“文风与排版”选择段落、步骤、小节或表格；格式服务于内容，不为统一模板重写全文。

已完成且没有新问题的文档，不因规则细化重复改写。这一原则同样适用于自动维护任务。

**必须：** 行为变化时，同时核对受影响的摘要、步骤、表格、示例、截图和限制，替换失效说明，
不能只在末尾追加新规则而保留前文旧结论。保留仍然正确的结构与无关内容。

- 同一事实保留一处完整定义，其他页面用必要摘要和链接引用；更新定义时检查引用页面是否也需要修改。
- 运行 `make check-doc-links`（已包含在 `make test-unit`）校验相对链接和 `#锚点`，并拒绝 `docs/` 下的 `[[wiki]]` 引用。
  同时核对图片引用和示例语法；仓库内文件存在与发布站点路径有效分别检查，涉及展示时核对构建与预览，检查窄屏表格的名称列、换行和横向滚动。
- 内容评审必须对照改前原文，检查准确性、范围完整性和阅读负担。教程和操作指南逐条核对：
  开头是否足以判断适用场景、完成目标和前置条件，是否遗漏必要准备或把某条路径的条件扩大为全文要求；
  原有仍有效的用法是否有入口和关键步骤，必要条件与兼容限制是否保留，范围调整是否有依据，是否无依据地设定默认路线，
  是否增加无必要的操作或跳转、把后台行为写成用户步骤，以及读者能否准备输入、连续操作并判断成功。

  对删减、折叠或改为链接的内容，逐项检查原有指标口径、状态含义、自动行为和限制是否仍在正文中有足够解释，不能只核对步骤有没有保留。
  必要分支按其触发条件与处理方式验收，不以是否有固定的异常、替代方案或清理章节判断完整性；
  不能仅凭事实无误、字数减少、格式变化或构建通过认定改稿合格。

  原理说明检查概念与解释是否清楚，参考手册检查信息是否准确、便于查阅；有配图和示例时核对其与正文一致。
  接口清单另外核对方法、路径、鉴权与改前一致，参数和限制仍可查到，引用能覆盖移出的信息；
  简单接口没有被扩写成教程，复杂说明没有整段塞进单元格。`api.md` 的 GET 路由说明还会生成 AI 助手接口目录，
  修改后按仓库现有生成命令同步并运行一致性测试；路由摘要应保留用途、必要查询参数及合法取值、用于定位接口的关键字段，不能只剩“见链接”。
  `search_api` 不读取链接正文，且返回的摘要会截断；精简 GET 说明时，还要验证典型字段能检索到对应接口，调用必需的取值仍出现在实际返回的摘要中。
- 新增或实质改变操作路径时验证相应流程；仅修改措辞不机械要求重跑全部环境，此处不替代仓库规定的提交前检查。
  在 MR 或已有验收记录中写明版本、环境、结果及未覆盖部分，证据按仓库约定存放。
- 代码核对、页面检查与真实操作分别记录；静态检查或构建通过不能表述为实操通过，未验证部分不能判为已完成验收。
