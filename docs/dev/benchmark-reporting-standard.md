# 评测信息与报告规范

本规范约束性能压测（benchmark）的信息保留、统计口径、解释与报告导出，覆盖负载生成、
server/agent 发压、聚合、持久化、API、CLI 和 UI。术语以
[`CONTEXT.md`](../../CONTEXT.md) 为准；用户操作见[运行评测并解读报告](../how-to/benchmark.md)。

这是当前生效的开发与评审契约，不是所有能力已经实现的声明，也不规定版本排期。
存量缺口允许逐项补齐；历史数据无法恢复的事实必须标记未知，不得推测回填。
修改某一环节时须核对其影响的信息类别、上下游口径及相应验收；不要求一次改动实现全部缺口。

2026-10-20 的已有/缺失盘点另见[初始盘点](../../artifacts/acceptance/benchmark-information-inventory-2026-10-20.md)，
该盘点不替代本规范，也不代表此后版本的实现状态。

下文按这些层次追溯一次评测：**Run** 是一次完整压测执行，包含一个或多个**点位**；
每个点位对应一组具体参数，例如并发、输入长度与输出长度。多轮场景下，一个**会话**包含按顺序执行的多轮请求；
**逻辑请求**对应计划中的某一轮，发生重试时，同一逻辑请求会有多次实际尝试。

## 信息分类与保留要求

“保留”指事实或可验证的推导依据能供报告追溯，不要求每个格式展示全部字段，
也不要求增加重复持久化字段。优先复用已有事实并在读取时推导；新增数据结构、
持久化和依赖仍须遵守根目录开发规约。

| 类别 | 回答的问题 | 必须保留的内容 |
|---|---|---|
| 负载计划与配置 | 准备怎么测 | 数据集及生成器版本、目标/预算/固定长度语义、平均/首轮/峰值输入、预计上下文、计划会话及轮数、并发或到达率、种子及各点派生规则、负载指纹、时长或数量终止条件、超时/重试/预热/缓存策略 |
| 请求与会话结构 | 结果属于谁 | Run、点位、会话、轮次、逻辑请求及重试尝试的关联；会话起止与终止轮次；同一会话的因果顺序 |
| 实际输入与输出 | 真正执行了多大负载 | 逐请求输入/输出、输入加输出的上下文长度、reasoning/正文拆分（端点可提供时）；均值、分布、峰值及计划与实际偏差；本地估算与服务端 usage 分别保留 |
| 执行结果与完整性 | 做了多少、完成多少 | 计划/发起/成功/失败/跳过/取消数；完整及中断会话；错误阶段、错误文本与状态码、finish_reason、重试次数及耗时 |
| 时序与交互体验 | 时间花在哪里 | 计划到达、客户端等待、实际发送、首个生成输出、首个可见正文、最后生成输出、流结束及会话结束；逐请求延迟、轮次分组和有效样本数 |
| 缓存与复用证据 | 复用了什么 | 设计前缀复用率、逐请求缓存字段及输入 token、上报与未知请求数、分组加权比例、每点开始前的缓存策略与实际执行证据 |
| 吞吐与负载过程 | 系统实际承受多少工作 | token 总量、精确测量窗口及吞吐公式、成功与失败部分输出的处理规则、实际活跃会话与在途请求曲线、空闲/等待、会话耗时与完成速率 |
| 环境与部署快照 | 在什么条件下产生 | 端点、发压点及客户端版本、GPU 型号/数量、TP/EP/DP、模型/tokenizer 版本或摘要、权重/激活/KV 精度、引擎版本、镜像摘要、关键启动参数、服务限制；配置与实际运行证据区分 |
| 比较条件与结论 | 能比较什么、为何推荐 | 负载形状、输出与缓存策略、测量制度、重复次数及波动、体验门槛、候选筛选/排除理由、目标函数、推荐范围与证据缺口 |

## 各类信息共有的属性

- **来源**：区分用户配置、本地 tokenizer 计算、字符估算、服务端 usage、客户端计时、
  部署系统、人工填写、日志和 profiler（性能分析工具）。配置值与实际生效值不能混用。
- **范围**：注明 Run/点位/会话/轮次/请求，以及成功请求、全部发起请求或其他子集。
- **口径**：注明单位、分子、分母、有效样本数、排除条件和公式；分位数注明对应指标及总体。
- **有效性**：区分已观测、估算、未知和不适用。未知不能写成 0；零分母的比例不能写成 0% 或 100%。
- **关联与完整性**：原始事实能定位到请求；记录明细是否开启、是否截断、是否缺失及保留范围。
  原始凭据不入报告；请求正文的保留须受显式配置、脱敏及容量限制控制，身份和口径不应依赖正文。

## 请求与会话的数量对账

逻辑请求是计划中的某一轮，重试是同一逻辑请求的额外尝试；两个层次分别计数。
一次无重试请求也只有一个尝试。成功、失败等逻辑请求终态按最终结果归类，不重复累计尝试。

对于已结束且记录完整的点位，必须能核对：

```text
计划逻辑请求数 = 实际发起逻辑请求数 + 未发起逻辑请求数
实际发起逻辑请求数 = 成功 + 失败 + 已发起后取消
未发起逻辑请求数 = 因前序失败跳过 + 开始前取消 + 其他未发起（须注明原因）
请求成功率 = 成功逻辑请求数 / 实际发起逻辑请求数
会话完成率 = 全部规定轮次均成功的会话数 / 计划会话数
```

运行中须另计排队、在途、尚未到达的请求；取消或记录丢失时不能强行按终态公式补齐。
无重试策略要明确记录“不重试”；有重试时保留每次尝试的结果及耗时、退避等待和总耗时。

Run 的 `done` 仅说明执行结束，不能替代请求成功或会话完整完成。
进度不能把未发起轮次冒充已完成请求；若进度表示计划项已处置，必须明确展示其含义。

## 长度与 token 对账

- 输出预算只表示允许的上限；固定输出目标须记录实际生效的策略，并验证观测值。
  不能因为配置了 `ignore_eos` 就宣称端点生成了固定长度。自然短输出负载须保留，
  固定长度诊断场景单独标识，不混合比较。
- 服务端 usage、本地 tokenizer 计数和字符估算分开保存与展示，分别标注输入和输出的来源。
  精确生成输入不意味着端点观测 token 数一定与本地一致，chat template 等额外开销须对账。
- 报告给出输入/输出分布、峰值和偏差；结合 finish_reason、错误及来源提示短输出、
  超预算或上下文风险，不能仅凭偏差归因于 tokenizer、缓存或服务端错误。
- 预计上下文是计划值；实际上下文峰值应由同一请求的输入与输出相加后取最大值，
  不能把不同请求的两个峰值相加，也不能用平均输出代替峰值请求的输出。
  服务限制未知时标记未知，不能把预计所需长度当成端点实际限制。

## 轮次与缓存口径

首轮/后续轮次与命中/未命中/未知是两个独立维度，不得用轮次代替缓存事实。
至少分别提供首轮与后续轮次的 TTFT、TPOT、完成延迟、有效样本数和缓存统计，
保留按具体轮次分析与定位异常请求的依据。

对任意明确声明的请求集合：

```text
缓存上报覆盖率 = 有缓存字段上报的请求数 / 该集合请求数
上报请求中的缓存比例 = Σcached_tokens / Σinput_tokens
                       （两项求和均只覆盖有缓存上报且输入来源明确的请求）
```

不得直接平均逐请求百分比。至少列出全部实际发起请求中的上报数、未知数及覆盖率；
若另给成功请求覆盖率，须明确标注，不能与全部发起请求口径混用。

明确上报 `cached_tokens=0` 是未命中；未上报是未知。可选字段缺省值不能伪装成显式上报。
缺少同来源输入 token 时，缓存比例也须注明不可计算或估算，不能悄悄混入字符估算。

设计复用机会、服务端缓存比例、客户端时延观测分别保留。没有受控对照时，
不能把相关性称为缓存导致的收益。各点注明清空、预热、沿用或未知，区分计划策略、
实际执行结果和可验证状态；改变 seed 或增加会话前缀不能作为冷缓存/完全隔离的证明。
比较各点须记录其顺序和缓存延续风险；不要求为不可控外部端点虚构清缓存能力。

## 时序、吞吐与统计解释

- TTFT（收到首个生成输出的耗时）须说明首个输出是否包含 reasoning（推理内容）；首个可见正文时间单独保留。
  最后生成输出与流结束是不同事件；请求完成时间须明确采用哪一个，不能共用模糊的 E2E 名称。
- TPOT 是请求解码阶段的平均每输出 token 耗时；报告采用
  `(最后生成输出时间 − 首个生成输出时间) / (输出 token 数 − 1)` 时，
  须说明可观察条件、token 来源，以及短输出、单块、非流式、失败样本的排除规则和数量。
  不可观察值不能当作零耗时参与统计。
- 块可能包含多个 token；块间隔不能直接称逐 token 间隔，块数也不能证明量化内核或推测解码行为。
  `1000 / TPOT P50(ms)` 只表示中位解码交互速度，不包含 TTFT，不等于整体吞吐除以并发。
- 整体吞吐保留墙钟窗口，即测量开始到结束实际经过的时间，包含窗口内首轮处理、轮间等待和收尾；任何稳态或滚动峰值另列，
  标注窗口与计算方法。失败请求的耗时、部分 token 与重试是否计入必须明确，不能静默排除。
- 分别记录计划会话并发、实际活跃会话和实际在途 HTTP 请求；C 表示配置的会话并发值，不能用配置 C 值证明全程有 C 个请求在跑。
  客户端排队与网络/服务处理时间分开，服务端内部耗时缺乏遥测时不能由 TTFT 反推为事实。
- 所有分位数须可核对有效样本数；小样本尾分位和重复测量波动须说明限制。
  会话耗时覆盖完整流程，中断会话单列，不混入完整会话的完成速率。

## 比较、推荐与环境证据

在满足用户指定首字延迟、完成延迟、会话完成率等门槛的可比点位中，按声明的目标函数选择。
未设置的门槛不得虚构；使用默认门槛要显式展示。没有合格点位时允许不推荐。
搜索判定、界面和导出须复用同一套门槛与口径，不能各自实现相互冲突的推荐规则。

比较前检查负载种子/派生策略及长度分布、输出策略、缓存策略、测量制度、重试与超时、
发压位置和部署快照。可比较的是受控的负载生成条件，不要求所有测点复用完全相同前缀；
防止缓存污染的种子变化本身也应可复现、可追溯。

输出明显变短、会话提前终止或条件未知时，提示“比较条件发生变化”或“比较证据不足”，
不能把数字最高直接解释为容量提高。

推荐用语为“本轮已测点最佳”，注明已测范围、门槛、目标和重复测量情况。
寻找稳定边界前不能声称吞吐上限；P99 不能写成通常或平均等待时间。

报告须携带可读部署快照；外部端点读不到时允许人工填写并标注来源、填写时间和未知项。
配置精度与启动参数不等于实际执行内核；后者须由日志或 profiler 证据支持。

## 导出与后续改动的验收

机器可读明细须有稳定字段和版本，明确时间单位、关联标识、错误文本、token 来源及截断标志。
已启用的逐请求 JSONL 应能支撑会话/轮次追溯；截断和禁用不能表现为“没有异常请求”。
聚合解释所需的计数与分组不能只能靠可选或已截断的正文文件才能恢复。

HTML、Markdown、CSV、API 和 CLI 展示同名指标时口径一致；精简格式可提供关联明细或说明省略项。
离线报告须保留解释结论所需的信息，不能仅依赖原服务仍然在线。

修改相关实现时按受影响范围提供行为验证，至少考虑以下反例；本清单是验收要求，
不是声称现有自动测试已经覆盖：

| 场景 | 应证明的行为 |
|---|---|
| 无重试，4 会话 × 13 轮，1 会话首轮失败，其余完成 | 计划52、发起40、成功39、失败1、跳过12；请求成功率97.5%，会话完成率75%；能定位失败会话 |
| 首轮有缓存，后续某轮无缓存或不报 | 轮次分组与缓存事实独立；明确零与缺失，不把首轮一律记冷缓存 |
| 两请求分别输入100/缓存100、输入900/缓存0 | 加权比例10%，不是百分比平均50%；明确覆盖率分母及未知/失败请求处理 |
| 配置输出220，实际自然停止50 | 分别保留预算、实际值与 finish_reason，不标为固定长度已完成 |
| 缺 usage、只有一个生成块、先 reasoning 后正文 | 正确标注估算、TPOT不可观察和首次正文时间，不制造零耗时样本 |
| 非2xx、网络失败、流中断、取消或重试 | 保留失败阶段/文本/计时与尝试关联，数量对账，未发起请求不混进成功率分母 |
| C升高后输出变短、尾延迟恶化 | 中位交互速度不能掩盖尾部和工作量变化；按门槛和可比性解释推荐 |
| 旧记录、明细禁用/截断、外部快照不完整 | 明确未知与证据范围，不猜测会话身份、缓存状态或硬件配置 |

提交说明须列出涉及类别、口径或兼容性变化、验证证据和仍未覆盖的缺口。
仅更新本规范或盘点不代表功能验收完成；新增或补齐自动门禁时须记录其实际覆盖范围。
