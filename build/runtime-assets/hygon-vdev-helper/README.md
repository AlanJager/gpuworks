# Hygon vdev helper

This optional Linux executable is the only CGO component in the Hygon dGPU path. The main `gpuworks-agent` stays `CGO_ENABLED=0`. The helper uses the [HYGON-AI hcu-dcgm/v3](https://github.com/HYGON-AI/hcu-dcgm) Go binding at the revision pinned in this directory's `go.mod`; it is not part of the default build.

Build on a Linux host with GCC and Hygon driver libraries `librocm_smi64.so`, `libhydmi.so`, and `libhydmi_mig.so` available to the linker. The upstream binding embeds its headers and searches `/opt/hyhal/lib` by default; Z100 installations can place `librocm_smi64.so` in `/opt/dtk/lib`, so include both paths. The helper must run on the same host as `/dev/kfd`, `/dev/mkfd`, and `/etc/vdev`:

```bash
LIBRARY_PATH=/opt/dtk/lib:/opt/hyhal/lib CGO_ENABLED=1 go build -o gpuworks-hygon-vdev-helper .
```

Build against a glibc version no newer than the target host's. For example, the Z100 test host uses glibc 2.32; a binary linked on a newer development host may fail before reaching `main`. Install the resulting executable as `/opt/gpuworks/bin/gpuworks-hygon-vdev-helper` on the agent host. At runtime it also needs the host's `librocm_smi64.so.2`, `libhydmi.so.1`, and `libhydmi_mig.so.1` (typically under `/opt/dtk/lib` and `/opt/hyhal/lib`). The executable is intentionally not linked into the static agent binary.

The command contract is one JSON object on stdout on success; diagnostics and upstream DCGM output go to stderr. Errors return nonzero and do not emit success JSON.

```text
create --gpu-index N --cu-count C --memory-mib M [--record-path PATH --pci-bdf BDF] -> {"vdev_id":ID}
inspect --vdev-id ID [--owner-token TOKEN] -> {"vdev_id":ID,"exists":false} or {"vdev_id":ID,"exists":true,"gpu_index":N,"cu_count":C,"memory_mib":M,"pci_bdf":BDF}
release --vdev-id ID --owner-token TOKEN --gpu-index N --cu-count C --memory-mib M --pci-bdf BDF --snapshot-path PATH -> {"vdev_id":ID}
prune --vdev-id ID --owner-token TOKEN --snapshot-path PATH -> {"vdev_id":ID}
```

`create`, `release`, `prune`, and owner-checked `inspect` take an exclusive `/etc/vdev/.gpuworks-vdev.lock` filesystem lock across their native operations; failure to take the lock fails closed. This serializes cooperating helper processes, but external vendor tools can still race the config scan. Before creating a vdev, `create` queries DCGM `PicBusInfo` for the selected physical index and requires it to match the requested `--pci-bdf`. An empty PCI address, lookup failure or changed index mapping rejects the operation before native creation. Standalone creates without the paired record flags derive their expected PCI address from this same physical query. The helper then checks each `/etc/vdev/vdev<ID>.conf` against DCGM and refuses to create while a config lacks a live device or cannot be verified. It calls `dcgm.CreateVDevices` for exactly one device and always requires one newly named config whose embedded ID, PCI, CU and memory match the request and whose live DCGM identity also matches. A normally returned ID must match that verified new config; a missing ID can be recovered only from that same evidence. Missing, malformed, conflicting, preexisting or multiple candidates require manual inspection; multiple returned IDs are never adopted. An unverified result is neither recorded as owned nor automatically destroyed, because it may belong to another workload. With the paired `--record-path` and `--pci-bdf` flags, it copies the driver-generated config to `vdev<ID>.conf` beside the record, syncs the snapshot, and writes a private, synced JSON ownership record containing the verified ID, GPU index, CU count, memory MiB, PCI BDF, and a random owner token. It also atomically stores the current token under `/etc/vdev/.gpuworks-owners/vdev<ID>.json` before emitting success JSON. The snapshot is mode 0644 and its parent is mode 0755 so a non-root workload can read the mounted file; the record remains mode 0600. The record's parent directory must already exist; existing snapshots and records are never overwritten. If snapshotting or recording fails, the helper queries the new ID and attempts an identity-checked rollback, reporting both the persistence and rollback errors. A successful rollback also removes a snapshot created by this attempt. The Hygon driver generates `/etc/vdev/vdev<ID>.conf`. The caller mounts the per-instance snapshot under the native filename in `/etc/vdev/`; its Docker configuration also uses `/etc/vdev/docker/vdev<ID>.conf` on every supported Hygon model, retaining the vendor ID inside the contents. Current Z100 and K100AI hardware checks reject a nonzero native ID mounted as `docker/vdev0.conf`; K100AI HYHAL 1.5 also rejects exposing that alias alongside the correctly named configuration. Expose exactly one Docker configuration file matching the verified native ID. The native filename has not been revalidated on older HYHAL 1.4 environments; those environments must pass the per-GPU probe rather than rely on a fixed-ID alias. `inspect` queries the vdev's physical GPU index, then asks DCGM `PicBusInfo` for that GPU's PCI address; PCI lookup errors fail closed. `release` queries the current device and requires its GPU index, CU count, memory MiB, and PCI BDF to match the expected flags, then compares the host config bytes with `--snapshot-path` under the same lock before `StopVDevice` or `DestroySingleVDevice`. Missing or different config bytes fail closed without destroying the device. It removes only its config file after successful destroy. A Stop error is reported even if Destroy succeeds, so the agent can retry and confirm the final state. The agent passes the recorded owner token on inspect, release, and prune; a previous token is rejected before any native operation even if the ID and configuration are identical. Records created by older helpers have no token and require manual recovery. A DCGM query error other than an explicit absent-device response fails closed; an absent device must use `prune` rather than `release`. `prune` rechecks that the device is absent under the lock, then removes its host config only when its bytes match `--snapshot-path`; an absent host config succeeds. A live device, query failure, missing snapshot while the host file exists, or different bytes fails without removing the file.

Managed creates reject an existing ownership record before native creation. After physical-device and existing-config preflight, the helper exclusively creates a mode-0600 `vdev-create-pending` marker beside `--record-path`, syncs the empty marker and its parent directory, and only then calls native Create. This marker represents a possibly completed creation whose ID may be unverifiable; it deliberately does not claim an ID. An existing marker blocks another managed create. Native errors, malformed or ambiguous config results, interruption and uncertain rollback leave the marker in place for manual inspection. It is removed and the directory synced only after the ownership record and host owner registry are durable, or after identity-checked rollback has destroyed the native device. Failure to persist the marker stops before native Create. Physical/config preflight failures write no marker. Standalone creates without record flags have no durable retry fence and remain the caller's lifecycle responsibility.

The upstream `CreateVDevices` implementation discovers IDs by comparing `/etc/vdev` directory listings before and after creation. The helper's recovery scan has the same exclusivity requirement: do not run another vdev creator concurrently on the host. A different creator could produce an identical candidate, and DCGM exposes no generation token to distinguish it. The helper rejects ambiguous evidence; its `inspect` result describes the driver device, not ownership. The host current-owner registry fences stale agent ledgers; its token is synthetic and only meaningful when all native lifecycle operations on the host cooperate with this helper.

A Z100 create–destroy–recreate test confirmed that an identical request can reuse the same vdev ID, every field returned by `dmiGetVDeviceInfo`, the exact config bytes, and even the config inode. Releasing the replacement with the first device's saved snapshot destroyed the replacement. The helper now serializes its own lifecycle and rejects a stale token after a same-ID recreation. External vendor tools can bypass the lock and registry, so automatic recovery and release still require exclusive gpuworks management of the host vdev lifecycle.

`make test` runs the helper's offline CLI tests with `CGO_ENABLED=0` alongside the main module. A native build and create/release integration test require the Hygon libraries and a suitable test card; never run the integration steps on a host with live workloads.

K100AI HYHAL 1.5 permits non-root HIP workloads to use a root-created vdev, but native creation returns `DMI_STATUS_PERMISSION` for an ordinary user. The container image must provide a passwd entry for its workload UID, readable DTK/HYHAL libraries and configuration, device access, and a writable HYHAL log directory. The minimal probe runs as root and receives a private `/var/log/hylog` tmpfs. Running its root-only scratch filesystem with an arbitrary numeric non-root UID is not a representative inference-user environment.
