# GPUWorks 浏览器 E2E 编写与自审规范

本目录及其子目录遵循根目录开发规约。本文件是**写用例、改用例、提交前自审**的入口；细则以
[浏览器 E2E 测试规范](browser-e2e-testing-standard.md) 为准，组件逐项要求见
[组件检查清单](browser-e2e-component-checklists.md)，领域术语见 [CONTEXT.md](../../CONTEXT.md)。

## 0. 一条原则

E2E 的目的不是“驱动 UI 走一遍并留下证据”，而是**用独立事实证伪产品**。每个断言都要能回答：

1. 期望值来自哪里（外部 fixture 实际发出的字节、协议/schema 常量、独立 API 回读）？
2. 什么错误实现会通过当前断言？
3. 这个断言证明了声明，还是只证明了“页面有反应”？

**断言强度必须等于声明强度。** 算不出精确期望、或产品没有该语义时，manifest 记 `MISSING`/`N/A`，
不要用 `> 0`、`可见`、`startswith`、`HTTP 200` 之类的代理把声明凑成“已覆盖”。

## 1. 正向用例：必须证明什么

### 1.1 五层证据链

| 层 | 必须证明 | 常见假绿 |
|---|---|---|
| UI | 用户操作后的真实渲染/状态：精确文本、数值、单位、名称、影响文案 | 只看 verdict/toast/tag 可见 |
| request | 页面**实际发出**的请求：method、path/query、完整 body、次数、顺序 | 测试自己重放的 GET 冒充页面请求 |
| persistence | 刷新/重进后的权威回读：独立 GET/列表/文件/hash 与 UI 一致 | 只看响应对象或前端缓存 |
| execution | 真实外部边界：agent、容器、引擎、SSE、终端、下载、推理输出 | recording/fake 结果冒充真实执行 |
| cleanup | 独立观察到资源消失/进程退出/handler 归零，失败保留 residual | “调用过 cleanup”即 PASS |

查询/筛选必须绑定页面实际请求与响应（动作前注册 `expect_request`/`expect_response`），测试自行重放的
GET 只作为权威回读。mutation 响应到达后，列表/计数/空态断言使用可重试 locator/`expect.poll`，禁止一次性
读 `all_inner_texts()`/`textContent()` 快照。

### 1.2 独立 oracle 链

期望值必须来自被测层之外，并沿链路逐层比对：

```
外部 fixture wire（实际发出/收到的字节）
        ↓ 精确值、类型、顺序、单位
产品持久化（独立 GET / 文件 / 事件 / 日志）
        ↓
UI（真实单元格、请求体、渲染文本）
```

反例：用产品 API 返回的数值直接断言 UI 单元格——这是同源循环，产品错了两边一起错。正例：fixture
记录它实际发出的 usage，先断言 point 的 input/output/total 等于该 usage，再断言 CSV/UI 等于 point。

本地对话的新建/切换/删除必须断言下一次真实请求体只含本次消息、不含旧对话的 prompt/reply；DOM 清空、
侧栏数量或渲染文本不能代替请求体证据。工具调用类 fixture 的最终回答必须由本次工具结果决定，并核对前置
assistant `tool_calls` 与 tool 应答的 ID、名称、顺序、参数对应关系。

### 1.3 精确值与完整合同

- 完整 schema/表头/列数/字段名，不用首列或首尾格抽查。
- 精确值、单位、默认值、可选字段、边界与换算关系；时间/吞吐/百分比按产品格式断言。
- 资源注册/同步要证明所选节点、存储、路径与权威回读及实际文件/hash 一致，不能只断言列表出现。
- 先核对产品、API 与共享组件合同，再写定位器和 expected；产品漂移先登记并修复，不能放宽断言适配缺陷。
- 先完整盘点实际可达控件及组合关系；快捷标签、同名下拉框等不同请求语义分别登记。

### 1.4 真实边界与 fixture 忠实性

被测操作必须通过浏览器执行；只把已声明的外部边界替换为 fixture（外部模型、Registry、云 provider、
OTLP、LLM 上游等），控制面、数据库、调度和需要验证的 agent 路径保持真实。禁止浏览器 mock 管理 API、
固定 sleep、默认成功分支或提高 retry 制造通过。

fixture 必须忠实实现真实外部 API 的行为，并且先写负例再写 happy path：

- 严格 JSON 类型（布尔/字符串/数字不混用）、必填/可选、默认值、上限与边界；
- 错误形态：状态码、错误体、协议错误、鉴权失败、超时、断连、部分响应；
- 协议结构：多轮/工具调用顺序与 ID 关联、SSE 事件顺序、分页/游标、分片；
- 断连与取消：取消后上游必须观察到释放；held/barrier 场景要可释放、可等待；
- fixture 自测覆盖上述正反例，不能对所有方法无条件返回成功。

### 1.5 资源所有权、清理与 PASS 聚合

- 名称使用 `e2e-{runId}-`；资源创建后**立即**登记 ID、句柄、进程、容器、文件和凭证，不能等 fixture
  全部创建成功；准备阶段任一步失败也走同一回收路径。
- 凭证一取得就登记给脱敏/扫描，避免失败报告泄漏未登记的秘密。
- 清理按依赖逆序、分阶段独立执行；失败 stage 记录后继续其余 stage，agent/server/browser 始终尝试退出。
- 所有权只在独立回读确认 404/消失后清空；失败、超时或查询不可用时保留 ID/名称、最后观测状态和 scoped
  回收入口到 `remaining_resources`，不能因为“调用过清理函数”就清空。
- 外部查询只接受显式、大小写不敏感的 not found/no such；DNS、daemon、连接、权限错误必须判失败并记录 stderr。
- PASS 必须由“业务完成且此前无异常 + 清理观察成功 + browser/context/fixture 正常关闭 + required evidence
  齐全”聚合；`finally` 不得把已记录的 FAIL 改回 PASS，close/stop 异常要有失败自测。

### 1.6 可重复与产物安全

- 每次运行唯一 `runId`、固定 UTC `T0`、独立数据库/agent state/目录/context；端口按约定分配并记录实际地址。
- 禁止固定 sleep 和静默 retry；等待使用有截止时间的条件轮询，循环必须让浏览器事件得到处理。
- 失败先保存证据并冻结现场；带凭证的数据库/trace/agent state 只放受控且 gitignored 的目录。
- 脱敏在序列化前执行并覆盖转义文本、响应体、traceback 和错误消息；扫描/脱敏 helper 要有注入合成 secret
  的失败路径自测。处理秘密的流程默认不保存失败截图，秘密输入到“不回显”断言完成前保持 sensitive phase。
- 共享 trace/HAR/截图/附件写入保留原始字节：只对确认的文本解码/脱敏/重编码，PNG、字体等二进制逐字节复制
  并单独扫描；用真实二进制资源做字节保真自测。

## 2. 反向用例：必须覆盖的失败面

正向主线通过不能代替负例。按合同逐项登记以下适用失败面，并断言**具体错误码/文案/状态/资源结果**：

| 失败面 | 至少覆盖 | 断言要点 |
|---|---|---|
| 输入校验 | 空、超长、非法类型、越界、重复提交 | 前端拒绝不能顶替服务端真实校验；服务端错误码与字段 |
| 认证/权限 | 401、403、非管理员、过期令牌 | 请求被拒、页面不泄漏数据、受保护动作不可达 |
| 业务冲突 | 重名、被引用、唯一键、状态不允许 | 真实后端冲突与提示；客户端格式错误是另一条负例 |
| 执行失败 | 容器启动失败、引擎错误/429、SSE 中断、下载失败 | 错误传播到 UI/状态；资源被回滚或保留可诊断 |
| 取消/断连 | 请求/流进行中取消、客户端离开、上游终止 | 用 barrier 保证取消发生在进行中；上游观察 BrokenPipe/Reset；completed=0 |
| 清理/关闭失败 | cleanup 超时、DELETE 前超时、held handler、prepare 失败、close 异常 | 运行保持非 PASS；其余资源仍回收；残留 ID/状态/回收入口完整 |
| 状态/恢复 | 刷新、重进、断线重连、部分成功、重试 | 恢复后状态正确；陈旧请求不覆盖新结果；重试不重复副作用 |
| 契约漂移 | 缺列/多列、字段改名、类型变化、空响应 | 精确 schema/值断言必须失败，不能静默兼容 |

负例同样要有独立 oracle：fixture 不应“对所有错误都返回同一个 400”，要断言具体错误类型/字段/顺序；
失败注入只在隔离测试环境启用，并限定主体、runId 和作用域。

## 3. 变异与自测：证明断言能杀人

- 每个新增/修改 case 至少做一次**产品层变异**：改产品行为（不是改测试期望），重建，跑用例，必须在声称的
  断言处失败；记录 FAIL 的 runId，再恢复产品。
- 变异要打在同层：声明 UI 指标就变异指标值；声明 CSV 就变异列/值；声明清理就注入 held/timeout/close；
  改测试里的 expected 不算变异。
- 共享 fixture/helper 的失败路径要有自测：close 异常、cleanup 超时、secret 泄漏、二进制 trace、协议错序、
  held handler、DNS/daemon 错误。
- 典型有效变异：`input_tokens` 改成 999；CSV 砍成两列 `concurrency,success_rate`；第二次对话重放旧
  prompt；docker 返回 `no such host`；流 held 时注入失败；删除前注入超时。

## 4. 反模式清单（真实 review 案例）

| 错误写法 | 为什么假绿 | 正确写法 |
|---|---|---|
| `input_tokens > 0` | 999 也通过，不能证明来自上游 usage | 等于 fixture 实际发出的 `prompt_tokens`，并核对 total/actual/approximate |
| CSV 只看首列名、两行、末格 `startswith("100")` | `1,100garbage` 也通过 | 钉完整表头/列数，逐列解析并与 point、fixture、单位换算比对 |
| 新对话只断言 DOM 清空 | 第二次 POST 重发旧历史仍通过 | 断言第二次请求体含新 prompt、不含旧 prompt/reply |
| `docker inspect` 任意非零 → absent | DNS/权限错误被当成已回收 | 只接受 `No such container/object`；其他错误带 stderr 失败 |
| `stop(); fixture_stopped = True` | held handler 仍在，报告却称已清理 | `stop()` 释放 barrier、关连接、等 handler/listener，返回观察结果 |
| 清理失败仍清空 `owned_*` | 残留 ID 丢失，无法回收 | 确认消失后才清空；失败写 `remaining_resources` + scoped reclaim |
| fixture 对所有请求返回成功 | 协议/类型/上限错误永远测不到 | 严格校验类型、上限、顺序、错误形态，先写负例自测 |
| 用被测 API 返回值当 UI 期望 | 产品错了两边一起错 | 外部 fixture → 持久化 → UI 三段独立比对 |
| manifest 按标签勾选 | 声明超出断言（12.7/17.1/20.6/20.9） | 每项绑定具体断言；没有就 `MISSING`/`N/A` |
| 任何破坏性确认都绑 `12.7`、任何页面数字都绑 `17.1`、任何持久化都绑 `1.14` | 标题相似但语义不符，绑定无法反查到断言 | 按完整语义绑定（名称+影响、单元格+单位、独立回读），否则 `MISSING`/`partial` |
| 整节缺失只写一句“键盘/焦点未覆盖” | 整节被一句话吞掉，无法逐项核验 | 逐项登记 `MISSING`/`N/A` 及理由 |
| verdict/toast/tag 可见即业务完成 | 数值、持久化、执行都可能错 | 绑定请求、持久化回读和真实执行结果 |
| `finally` 里无条件改 PASS | close/teardown 异常被吞 | 观察聚合；close 失败保持 FAIL 并记录 |
| `private_state` 写死“no process kept” | 未观察就声明 | 由 stopped/handlers/remaining_resources 生成 |
| 搜索用 chip/普通下拉代替输入 | 没验证真实搜索语义 | 输入搜索词、核对候选过滤与空结果 |
| 工具调用只看最终文本 | 缺前置调用/错序/错 ID 也能过 | 校验 `tool_calls` 与 tool 应答结构和关联 |

## 5. 写一个 case 的顺序

1. **读合同 + 逐页组件盘点**：确认产品实际行为；先列出实际可达组件、字段、选项、状态与请求语义，
   从组件清单选出适用编号并逐项写出断言或 `MISSING`/`N/A`。不能先写主线、最后回来挑编号。
2. **写失败表**：每个声明一行“错误实现 → 哪条断言会失败”；没有对应断言的声明直接 `MISSING`。
3. **写 fixture 合同**：真实行为的类型/默认值/错误/上限/协议结构，先写负例自测。
4. **写正向主线**：UI → 页面实际请求 → 持久化 → 真实执行，全部用精确值。
5. **写反向用例**：输入、权限、冲突、执行失败、取消、清理/关闭失败、恢复。
6. **写清理台账**：创建即登记；观察消失；失败保留 residual；PASS 聚合。
7. **做产品变异**：至少一次，在声称的断言处失败；恢复产品。
8. **clean-tree 验证**：rebase 到目标分支当前 tip，重建，跑 en/zh，记录 target SHA、HEAD、runId。
9. **写 manifest**：只按实际断言绑定 checklist；其余 `MISSING`/`N/A` 及理由。
10. **自审**：按第 6 节问题逐条回答后再提交。

## 6. 提交前自审（必须逐条回答）

- [ ] 已逐页盘点组件/字段/选项/状态，适用清单项逐项映射到断言或 `MISSING`/`N/A`？
- [ ] 绑定项没有按标题相似；`1.14`/`12.7`/`13.5`/`17.1` 等通用项满足完整语义，不是填充？
- [ ] 每个 covered 声明都能指向一条具体断言，且期望值有独立来源？
- [ ] 有没有 `> 0`、`可见`、`startswith`、`HTTP 200`、首列抽查之类的代理断言？
- [ ] 什么错误实现会通过当前用例？产品层变异是否真的在对应断言失败？
- [ ] fixture 的类型、默认值、错误形态、上限、协议结构是否忠实？负例自测是否覆盖？
- [ ] 清理是否来自观察（404/退出/handler=0），失败是否保留 ID、状态和回收入口？
- [ ] PASS 是否聚合了业务完成、清理、close 和 required evidence？`finally` 会不会改回 PASS？
- [ ] 秘密、trace、二进制、失败截图是否按规范脱敏/保真？有没有失败路径自测？
- [ ] manifest 是否把未覆盖项写成 `MISSING`/`N/A`，没有按标签或标题勾选？
- [ ] 是否在目标分支当前 tip 的 clean tree 上重建并跑 en/zh？报告是否记录 target SHA、HEAD、runId？
- [ ] 失败报告是否有失败步骤、期望/实际、method/path/status、最后完成步骤？
- [ ] 是否残留进程、容器、挂载、临时文件或付费资源？是否只清理本次 runId？
- [ ] 新增 Make target 是否只用于多步流程或被引用入口？命令是否写进文件头而不是 README 业务章节？

## 7. 目录与产物约定

- 每个 case：`<business>.py` + `coverage/<case>.json` + 可选 `<business>.mk` + `test_<fixture>.py`。
- 文件头写运行命令与专用前提；业务验证说明只维护在 case 名称、Mainline、步骤和断言中，README 不追加业务章节。
- `coverage/*.json` 维护 case 绑定、字段/CRUD/组件维度及缺口；实际通过状态只来自对应 SHA/runId 的 `report.json`。
- 产物：`secrets/e2e/<runId>/`（report、脱敏日志、失败截图）与 `private/`（受控 DB/agent state），仅清理本次 runId。
- 新增 Make target 放在功能独立的 `test/e2e/*.mk`；只是包一层 `go test -run` 的单用例不加目标，完整命令写进测试函数注释；
  L4 用例仍按 `l4-<provider>-<行为>-<拓扑>` 一一对应。
- 尚未实现的 Registry、runner 或 CI 门禁不得写成已经可用或已通过。

## 8. 文档维护

- `browser-e2e-testing-standard.md` 是规则正文；本文件是其编写/自审摘要，两者冲突以正文为准并同步修正。
- 新增规则先改正文与组件清单，再更新本文件；不要在其他目录复制第二套规范。
- 评审发现的真实假绿/清理缺陷要沉淀为反模式或门禁，而不是只修当前 case。
