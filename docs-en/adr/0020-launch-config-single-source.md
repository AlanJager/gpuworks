# ADR 0020: A Single Source of Truth for Launch Configuration—One Dictionary-Based Parameter Set, With Command Mode as the Only Special Path

Date: 2026-09-15 · Status: Accepted (supersedes the merge precedence in ADR 0007 decision 3; the args storage format in ADR 0009 decision 7 remains unchanged, with args split during import and deployment according to this ADR; the `manual` mode in ADR 0013 becomes the only path that bypasses the parameter dictionary. See `artifacts/archive/2026-09-16-launch-config-single-source/plan.md` for the review draft and catalog statistics.)

## Context

The GPU memory utilization parameter has three different "defaults" in the repository: the parameter dictionary's form default of 0.92, the fallback of 0.9 hardcoded separately in four estimation/scheduling functions, and the engine's own default when the parameter is absent. The form slider only renders the default without assigning it. If you submit without touching the slider, the request omits this key. For the same deployment, the screen therefore shows 0.92, estimation and admission use 0.9, vLLM happens to use 0.9 as well, and SGLang uses its own formula.

The root cause is not inconsistent constants, but two representations of the same launch configuration inside the system: typed `quick_params` and free-text argv (catalog spec args and user extra_args). They are merged with three-layer precedence only at the final stage of command assembly (`deploy/args.go`), while the estimator reads only `quick_params` before the merge. Of the 962 specs in the built-in catalog, 839 specify dictionary-defined flags in args (`--dtype` in 144, `--quantization` in 42, `--kv-cache-dtype` in 8, and so on). The engine receives all these values; the estimator sees none of them.

ADR 0007 decision 3 already requires "splitting args that map to the parameter dictionary into key-value pairs during import, and passing through unmappable args verbatim." When ADR 0009 flattens the catalog, it changes args back to a raw JSON column, and import-time splitting disappears. The reverse parser `ReverseArgs` remains in the code, with zero production callers.

## Decision

1. **The parameter dictionary is the only definition source.** `deploy/param_specs.go` has one row per parameter, containing its key, type, control, default value (which can vary by engine), aliases (such as `half → float16`), and each engine's value flag and disable flag (the on/off forms of Boolean parameters). All defaults, enums, bounds, and key↔flag mappings come exclusively from this dictionary. Remove the handwritten mapping table in `sglang.go`, the handwritten enums in `ValidateQuickParamsForEngine`, the hardcoded frontend key lists, and the polarity exceptions in `structuredQuickFlagSet` and `ReverseArgs.booleanFlagValue`.
2. **Materialize once at the write boundary.** `evaluate` and `create` use the same `deploy.Materialize`: request fields, extra_args, and catalog spec args merge into one complete typed configuration with the precedence "explicit fields > extra_args > template args > dictionary defaults." Dictionary-defined flags are split out of args into fields; flags outside the dictionary remain as residual args. Dictionary-defined flags in extra_args move into fields and are returned as `moved` in the response. Conflicts with explicit field values are rejected (ProductError `LAUNCH_CONFIG_CONFLICT`, with both values provided). From this point onward, there is no second representation inside the system.
3. **Unset means the engine default; the server does not invent values.** Persisted configuration records only values stated in user fields, extra_args, or the template. A key that none of these sources states remains unset, meaning "you have made no choice, so the engine's own default applies," and argv does not emit it. Dictionary defaults are initial form values: the frontend submits every value it displays, so argv for new deployments matches what you see in the UI (GPU memory utilization defaults to 0.9 for vLLM, matching the engine's default, and 0.88 for SGLang). When estimation needs a utilization value that is unset, planning resolves it from the dictionary default in one place (`deploy.DefaultGPUMemUtil`); estimation, reserve, and the scheduler no longer apply separate fallbacks, and invalid values are errors. For keys marked `Automatic` in the dictionary (such as `max_model_len`), the estimator derives values from model facts (config.json) rather than inventing numbers. Hardware-related keys such as `dtype` allow `auto` as an explicit value. Node-specific resolution is covered by T6 in `todo.md`, outside this ADR.
4. **Snapshots are the only launch input.** `Deployment.QuickParams` (the complete configuration), `Deployment.ExtraArgs` (user residual args), and `CatalogSelectionSnapshot.extra_args` (template residual args) are fixed at creation. Instance startup reads only these fields and does not return to the catalog. This is consistent with ADR 0002 and with current behavior; only snapshot contents change from raw args to the split results.
5. **All consumers read this one configuration.** Argv assembly, estimation and scheduling, form rendering, template deviation detection, and the GPU memory ledger for deployed instances all read the persisted configuration. Only two inter-layer rules remain in argv assembly, both applying exclusively to residual args outside the dictionary: user residual args override platform-injected flags with the same name (such as `--host`); user residual args override template residual args with the same name.
6. **Command mode `manual` is the only exception.** When you take over the entire command, the command text is the source of truth: estimation does not apply and the UI states this explicitly, while form parameter fields are disabled. Placement inputs (GPU count, TP, and GPU memory limits) still come from the form, and admission uses weights plus reserve. The platform still rewrites `--port` and `--served-model-name`. The `engine` and `image-entry` modes are not exceptions.
7. **The catalog file format stays unchanged.** Authors still write argv in `args`. `ReverseArgs` moves down from `inferencecatalog` to `deploy`. Import validates that values of dictionary-defined flags can be decoded by the dictionary, rejecting the import if they cannot. `--quantization` (an engine quantization method, such as `modelslim`) and `weights.quantization` (a weight format, such as `int8`) are separate terms; each retains its own meaning, with no consistency validation between them.
8. **Existing data is normalized at server startup, and upgrades do not change launch arguments for any existing deployment.** Because `store` cannot depend back on `deploy`, normalization runs during `app` startup: for each deployment, it splits dictionary-defined flags from the old `QuickParams + ExtraArgs + snapshot args` into fields. It only splits values, never fills them in; it is idempotent, and any failure prevents startup. Instance argv remains identical character for character before and after normalization. Conflicts between fields and extra_args in old data follow the old semantics (extra_args wins) without errors.

## Consequences

- Benefits: the estimator and engine read the same values without manual synchronization; upgrades do not change existing deployments' launch arguments; adding an ordinary parameter requires changing only one dictionary row. Removed duplication includes five occurrences of 0.9, the handwritten SGLang mapping (19 entries, with another 2 entries in the same dictionary column missing from the handwritten table—an example of drift), 62 lines of three-layer merging, 131 lines of template deviation comparison, frontend copies of 46 keys and 16 rules, args parsing in `templatePrefillValues`, and the 16-thread default in `diskKVTransferConfig`.
- Costs and constraints: extra_args semantics change for direct API callers (non-conflicting values move automatically and are returned in the response; conflicts return 400). New SGLang deployments created through the UI change from "engine-calculated mem-fraction" to an explicit 0.88, requiring validation on real hardware; existing deployments are unaffected. UI Boolean switches are always explicitly submitted, so argv for new deployments includes flags such as `--enable-prefix-caching` and `--enable-prompt-tokens-details`, while keys omitted by API callers retain engine defaults. Catalog authors must know that dictionary-defined flags in args are split into fields.
- Rejected alternatives: a runtime resolver (reading and merging four sources whenever estimation input is constructed, institutionalizing dual representations); argv as the source of truth with reverse parsing by the estimator (the scheduler first determines TP, argv depends on TP, and estimation needs to read argv, creating a cycle).

## Amendment (2026-11-02)

Decision 7's "a value that cannot be decoded is refused at import" becomes "does not block the import": when a flag owned by a single key carries a value the dictionary cannot decode, the flag and its value stay in the residual args and reach the engine verbatim, and the import raises a `CATALOG_ARG_PASSED_THROUGH` warning. The dictionary always trails the engines (new tool call and reasoning parsers and KV precisions keep arriving); refusing the import let the platform's vocabulary decide whether a template could be used and pushed authors into workarounds, such as turning a whole spec into a callable engine to use Ascend's int8 KV cache. The cost is that such a value stays out of the typed configuration, so the deploy form and the memory estimate do not see it; a warning on the built-in catalog means the dictionary needs refreshing.
