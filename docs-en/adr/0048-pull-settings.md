# ADR 0048: Node Pull Settings Determine Where Images Are Pulled From; Deployments No Longer Select a Source

Date: 2026-10-16 · Status: Accepted (supersedes the part of [ADR 0018](0018-explicit-deployment-acquisition.md) that requires deployments to explicitly select an acquisition method, and Decision 5 of [ADR 0038](0038-template-image-sources.md), “System rewrite rules apply only to system images”; the other decisions in ADR 0038 remain in effect)

Basis: [Image and Model Pull Settings Plan](../../artifacts/work/2026-10-16-image-pull-policy/plan.md).

## Background

Image sources were previously determined in five places: the acquisition method and network path on the deployment page, global `image_registry_rewrites`, `registry_sources` in the image catalog, `image_sources` in templates, and node `network.rewrites`. The four pull paths (deployment startup, the default chain when a deployment has no record, pulls from the Images page, and multi-node pre-pulls) each calculated their own sources:

- A deployment records “the acquisition method for that node at that time.” When a deployment configured to use “Already local” or “Peer sync” adds replicas on new nodes, its candidates degrade to `[original-ref]` (Docker Hub), with node rewrites and proxies disabled. When a deployment configured to use “Peer sync” or “Archive URL” expands to new nodes, it waits indefinitely for an image that never arrives.
- Multi-node pre-pulls use the global default chain, ignoring both the deployment's selected source and template sources.
- The deployment page does not read global settings, leaving Docker Hub as the only candidate for third-party template images.
- Built-in third-party Docker Hub accelerators are unreliable: DaoCloud has an allowlist and a 1 MB/s rate limit, university mirrors stopped service in 2024, and Alibaba Cloud personal accelerators work only with Alibaba Cloud ECS.
- The management network carries storage synchronization by default, so “the two nodes share a storage synchronization network” is almost always true and cannot indicate whether synchronization is possible. Cloud containers (RunPod, Vast, and AutoDL) typically cannot reach one another.

## Decisions

1. **Three kinds of facts, each with its own owner.** Equivalent image copies belong to the image (template `image_sources`, catalog `registry_sources`, the original name, and `pullref.Copies`); where a node can pull from belongs to the administrator's pull settings; a deployment records only what to run.
2. **Source rules** (`pull_source_rules`, ordered by position) match a registry host or reference prefix and provide ordered alternative addresses. They can disable fallback to the origin and limit their scope by node labels. The semantics match containerd `hosts.toml`: try alternative addresses in order, move to the next one on failure or a stall, and finally fall back to the original address unless origin fallback is disabled. After a successful pull, tag the image locally with its original name. Rules are implemented only on the agent by “pulling another address,” without modifying `daemon.json` / `hosts.toml`, so they apply only to platform-initiated pulls.
3. **One candidate list, calculated in one place.** `pullref.PlanCandidates` places alternative addresses from rules applicable to the node first, in rule order, followed by the image's own copies with a `rank`. If any matching rule forbids origin fallback, that copy itself is discarded; if nothing remains, an error is returned. `planning.PullCandidatesFor` is the only entry point for startup, desired-state replay, pulls from the Images page, and multi-node pre-pulls. Instances persist copies (`image_sources`); candidates are recalculated using the current rules when dispatched.
4. **Nodes rank copies themselves.** The agent probes `https://<host>/v2/` in parallel (5-second timeout, cached for 30 minutes, through the same proxy used for pulling) and sorts candidates within each `rank` segment by reachability and latency. Download speed is not recorded. During a download, 3 minutes without new bytes counts as a stall and triggers the next candidate. Failed or stalled endpoints enter a 30-minute cooldown on that node; during cooldown they are placed last, not removed. Slow downloads that are still progressing are not switched midway.
5. **Sync groups** (`sync_groups`): nodes automatically copy images and models only from nodes in the same group. Both new installations and upgrades create an ordinary group named `default-all-nodes` that selects all nodes (it has no “default” flag and can be edited or deleted). Nodes outside all groups do not copy automatically. Membership across groups is combined, and the strictest rate limit among shared groups applies. Connectivity is not inferred: node pairs that fail a direct connection enter a 3-hour cooldown in server memory. After a copy fails, the instance pulls from the registry itself (or downloads the model). Sync groups express only “reachable, but should not be used.” Rental nodes carry the system labels `gpuworks.ai/provider` and `gpuworks.ai/region`, derived from rental records.
6. **Deployments no longer select sources.** Deployment requests retain only the storage that holds the model and the weight source (which weights to run). They do not accept an image acquisition method, source node, or network path. Evaluation estimates the acquisition path for the nodes specified in the request (already available / copy from a node / pull using candidates); this is an estimate, not a selection. Manual pulls on the Images page also use automatic candidates and cannot specify a registry. Manual copying from a specified source node remains available.
7. **Registry credentials** (`registry_credentials`, encrypted with secretbox) are saved by host and delivered through state.sync. The agent keeps them only in memory. During a pull, it writes a temporary `DOCKER_CONFIG` and deletes it afterward, without running `docker login`.
8. **The platform writes proxies into dockerd on docker nodes.** Node proxies (global settings and node overrides, with the new `no_proxy`) apply per operation for nerdctl / udocker. For docker, the agent writes `/etc/systemd/system/docker.service.d/zz-gpuworks-proxy.conf` and runs `daemon-reload`, without restarting. The agent reports dockerd's actual proxy, live-restore status, whether `daemon.json` also configures a proxy, and its privileges (root / passwordless sudo / none). If settings differ, the UI indicates that they have not taken effect. “Restart dockerd” requires user confirmation (`runtime.restart`). Without privileges, the agent only reads settings and provides commands. SSH is not used.
9. **Migration**: user-added rules in `image_registry_rewrites` and non-URL rewrites in `network` / `network:<id>` become source rules (node overrides are scoped with `gpuworks.ai/node`), and the old settings are deleted. If the old settings contain the internal registry registry.zstack.ai, the rule `gpuworks/ → registry.zstack.ai/gpuworks/` is generated. `acquisition` records in deployment snapshots are deleted. The image catalog seed no longer lists the internal registry.

## Trade-offs

- **Give up “source locked by deployment”**: replicas of the same deployment may pull different content for the same tag from different sources. Pulls do not use digests (digests may be garbage-collected, and manifest digests may differ between copies). Instead, deployment details show each replica's image ID and flag inconsistencies.
- **Probes establish only reachability**: `/v2/` and the CDN serving the data are different locations, so a fast probe does not imply a fast download; stall detection and cooldown provide the fallback. The docker CLI outputs byte progress only to a terminal, so the agent runs `docker pull` in a pseudoterminal. If a pseudoterminal cannot be allocated, it falls back to pipes; stall detection is then unavailable, and only the total time limit per candidate applies (including unpacking, increased from 30 to 60 minutes on 2026-10-20).
- **New persisted facts**: rules, sync groups, and credentials are administrator configuration and cannot be derived; all use typed tables. Dockerd observations and cooldown state are not stored in the database.
- **Rules do not modify the host runtime configuration**: manual `docker pull` commands on a node do not use the rules. In return, no runtime restart is required, and other workloads on the host are unaffected.

## Consequences

- Add `/api/v1/pull/source-rules`, `/api/v1/pull/sync-groups`, `/api/v1/pull/registry-credentials`, and `POST /api/v1/nodes/{uuid}/runtime/restart`; endpoints such as `PUT /settings/image_registry_rewrites` return 410.
- Add the agent capability `image.pull.candidates`: `image.pull` receives the entire candidate list at once and handles fallback itself; for older agents, the server still dispatches candidates one at a time.
- Source rules for model downloads (replacing Hugging Face mirrors in node URL rewrites) and “Disable Xet” are a subsequent step. This ADR covers only images and the sync groups shared by images and models.
