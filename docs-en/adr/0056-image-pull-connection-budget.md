# ADR 0056: Connections for runveil Image Pulls Adapt Through a Per-Registry-Host Budget, and Slow Connections Are Judged Relative to Their Siblings

Date: 2026-10-27 · Status: Accepted

## Background

The native pull of runveil (udocker) nodes (`runtime/udocker/native`) used a fixed 6 concurrent layers times 4 Range segments per large layer, which means up to 24 TCP connections to one registry. After the registry transport was changed to HTTP/1.1 only (concurrent requests to one host each take their own connection), that number became the real connection count, with two kinds of problems:

- Private registries (Harbor, Huawei Cloud SWR, Alibaba Cloud ACR, registry.zstack.ai) and corporate proxies often limit connections or request rate per source address. 24 connections draw 429 responses or dropped connections, and reconnecting immediately after a refusal only makes the limit worse.
- When the link itself is slow (a few hundred KB/s in total to an overseas CDN at peak), 24 connections share one bandwidth, which is neither faster nor kind to the absolute floor of the "replace a connection that is too slow" rule (16 KiB/s per connection), which becomes too strict for each connection. A fixed number also cannot exploit a link where a single connection is throttled but total bandwidth is plentiful.

## Decisions

1. **Leaf package `internal/agent/connbudget`: the connection budget.** `Hosts` builds one `Pool` per upstream address (the registry host, or the proxy when going through one). A `Pool`'s ceiling is the number of requests in flight to that address at once. One pull is a `Session`; every request (including retries) first takes a `Lease` and gives it back when the request, including reading the response body, ends. A session has its own target connection count, and several pulls from the same registry on a node share the pool's ceiling. The package depends only on the standard library.
2. **Adaptive, with no memory.** A pull starts with 4 connections and measures the aggregate rate of the whole pull every 3-second window. When requests are queued while the target is fully used, doubling that raises the rate by less than 15% is reverted to the smaller level, which then settles; once settled, it probes for a quarter more every minute and keeps it only if the rate rises by 5%. A link where each connection is throttled therefore climbs to at most 16 connections (the default ceiling, changeable with `--image-pull-max-connections` / `GPUWORKS_IMAGE_PULL_MAX_CONNECTIONS`, where 1 is a single connection), while a link where the whole address's bandwidth is already full stays at the start. Learned values are not stored: no new persisted fact, and the next pull starts over.
3. **Layer concurrency and segments no longer multiply into a connection count.** The number of layers pulled at once is still limited by `Workers` (the needs of disk, temporary files, and streaming unpack), but every request must be admitted by the connection budget. A layer larger than `RangeMin` is cut into at least `RangeParts` segments, and larger ones into segments of about 64 MiB (at most 64). Workers take segments in order, so the connections are fully used as the budget climbs.
4. **Back pressure, not failure.** A 429, a 503 or a refused connection immediately halves the connections of that pull (one burst of failures counts once) and keeps them from rising again for a while; 3 consecutive connection resets also halve them, down to 1. `Retry-After` (seconds or an HTTP date, capped at 2 minutes) applies to the whole Pool: every request to the same registry, including those of other pulls, waits it out before being sent. A 429/503 that names no time waits 2 seconds, doubling each time up to 30 seconds, and never reconnects immediately. A single segment fails after 5 consecutive throttled answers, without restarting the whole layer, and leaves the decision to candidate switching. A connection that received nothing while the other connections of the same pull still advance does not count as "stuck" and is given more attempts as "progress elsewhere". The halved ceiling is returned a level at a time after 2 calm minutes. When the registry answers a Range request with the whole file, that pull uses only 1 connection and immediately switches to reading whole.
5. **A "crawling connection" is judged by a relative standard.** The absolute floor is still an average of 16 KiB/s over a 30-second window per connection, but the judgement is made by the connection's `Lease.Observe`, which compares it with its sibling connections in the same pull. A new connection replaces it only if it stays below one tenth of the median rate of the siblings (at least two) for two windows in a row, or below one tenth of its own earlier best window while most siblings did not drop likewise; the absolute floor takes effect immediately. However many connections qualify, at most half of them are replaced within one window (just that one when there is only one), so a slow link as a whole never loses all connections at once. A replaced connection continues from the bytes already received.

## Trade-offs

- **Start at 4, not 2.** Image layers are mostly single layers of hundreds of MB to several GB, a climb takes several windows, and a start that is too low would slow down small images. 4 equals the segment count of one large layer before, and sits below the per-address connection limit of common private registries.
- **The budget is per registry host, not per node.** Connection and rate limits belong to one address. The cost is that several registries reached through one proxy share one budget through the proxy key instead of being told apart exactly. The CDN domain a request is redirected to has no pool of its own, since its limits are unpredictable and change with each blob. Its refusals and resets slow the whole pull down just the same.
- **The relative judgement needs two windows in a row.** The sibling connections' windows end at different moments, so when the whole link suddenly slows down, the first connection to settle compares itself with sibling data from before the slowdown. Two consecutive windows let the sibling data catch up and prevent misjudgement. The absolute floor needs no comparison and does not wait.
- **No downward probing.** It only doubles when that pays; it does not try fewer connections to see whether the rate stays the same. The waste of starting at 4 on a slow link is limited, and the gain from downward probing does not outweigh the complexity.
- **Model downloads are outside this decision.** `connbudget` stays general (it knows nothing about HTTP, files, or tasks) and leaves room for model downloads and other downloads. The `Pool`/`Session` design of the draft MR !538 was ported on this basis, without merging the rest of it.

## Consequences

- A new agent flag `--image-pull-max-connections` (environment variable `GPUWORKS_IMAGE_PULL_MAX_CONNECTIONS`), automatic by default. The protocol, server, and UI are unchanged.
- `native.Downloader` gains `Budget` (`*connbudget.Hosts`) and `Tune`. With a nil `Budget`, every `FetchAll` uses a private fixed budget of `Workers x RangeParts` (the old behavior), so existing test fixtures stay unchanged.
- Tests use `internal/testenv/fakeregistry` (HTTP/1.1 plus TLS, 307 to a blob CDN, strict Range, per-connection and aggregate throttling, a per-source connection limit answered with 429 or a reset, mid-body resets, stalls, and ignored Range) to verify throughput behavior, the connection ceiling, `Retry-After`, return of all tokens, and no goroutine leaks.
