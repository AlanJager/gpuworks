# ADR 0010: Package the Inference Catalog as an Executable Multi-File Bundle Alongside Each Model

Date: 2026-08-31 · Status: Accepted (the immutable image reference clause is superseded by ADR 0017, which changes images to tag-only references; the multi-file package structure, `assets/` restrictions, and immutable reference requirements for weights/dependencies remain in effect)

The flat specs in ADR 0009 remain the product's unit of selection, but a single `catalog.yaml` no longer adequately expresses the patches, runtime wrappers, multiple model components, dynamic topology, and API capabilities required in real-hardware validation. The built-in catalog becomes an authoritative multi-file package consisting of a root manifest and `models/<model_id>/model.yaml`. A model can reference only lightweight files in its own `assets/`; images, underlying dependencies, and weights continue to be delivered through immutable external references. The entire catalog package is embedded into the server with `go:embed`. Online sync, offline import, and the built-in seed use the same package format, and the database serves only as a projection. This preserves a single source of truth and single-binary distribution while avoiding base64 bloat, cross-directory references, and test-machine environments presented as reproducible configurations.

Runtime topology is produced as scalar variables by a restricted solver with no I/O, based on the actual GPU set. Relationships between multiple sets of weights are expressed through explicit runtime components and primary/speculative_draft/verifier roles, but components are split only when the upstream command explicitly references an external checkpoint. Fused checkpoints with built-in MTP/DSpark heads remain a single component; a second mount must not be inferred solely from a model name. The inference API contract expresses the operations available after deployment. README files provide human-readable guidance only and cannot replace machine-readable contracts. Asset packages must not contain frameworks, shared libraries, venvs, weights, or image layers. When these dependencies are missing, supply images with digests instead of expanding the catalog package to bypass the restriction.

Launch information follows one fixed, one-way data flow: InferenceSpec contains catalog facts; ImageDefaults contains the image runtime baseline; ContainerOverrides contains field-level changes for the current deployment; ResolvedLaunch is the sole final launch plan produced by merging these with deployment/GPU selections; and InstanceDesiredState adds instance identity and scheduling lifecycle facts on top of ResolvedLaunch. The old RunSpec, InstanceSpec, engine Result, RuntimeSpec, and Assembly are all removed without compatibility aliases. Preview and controller must share the same ResolveLaunch entry point. The database field `DesiredStateJSON` stores only a serialized snapshot of InstanceDesiredState.
