# ADR 0068: Memory-limited partitions share a card with processes outside the platform by the memory left

Date: 2026-11-16 · Status: Accepted (supplements [ADR 0060](0060-card-health-from-hardware-facts.md))

## Context

When a card has compute processes the platform did not start (a vLLM a user started, another orchestrator's container), the agent reports them as `foreign_processes` and the server treats the card as taking no deployment at all: its memory is held by something the platform can neither see nor plan around, and a whole-card deployment would run out of memory at startup.

A memory-limited dGPU partition (nvidia-dgpu and others) only ever wants part of a card, though, and the agent reports how much memory each of those processes holds. A real case: on a 143771 MiB H20-3e, another orchestrator's container held 63982 MiB, and a 50 GiB partition deployment was refused outright; after `foreign_processes` was cleared by hand, it ran stably beside that container on the same card.

Relaxing the server alone is not enough: the agent's rule for processes outside the platform is "while a card holds none of this node's instances, every process on it is foreign", and once a platform instance is on the card it stops examining it. The foreign processes vanish from the next report, the server takes the card for empty, and hands out what is left as if it were all of it.

## Decision

1. **Only partitions share, admitted by memory.** When a card is held by processes outside the platform, every one of their memory figures is known, the card is healthy and an operator has not stopped scheduling on it, a memory-limited deployment may be placed there: memory available = total − what the outside processes hold − headroom − what the platform's instances already claim (sleeping residue included), and it is admitted only if that covers the deployment's limit plus the partition overhead (`estimate.PartitionClaimBytes`). A whole-card deployment is still refused; `store.GPU.CanTakeWork` keeps its meaning, so fleet statistics and SQL aggregates are unaffected; in the scheduling center's card states, a held card a platform instance serves on counts as serving, and any other held card still counts as held by a process outside the platform. The same figure is used when a running partition's quota is changed in place (`planning.QuotaRoom`) and for the GPU list's available memory (`planning.ForeignHold`); on a held card whose foreign use is unknown, a quota changed in place may shrink but not grow, and the GPU list shows no available memory, rather than reading the unknown as nothing held. Usage analytics count a held card as schedulable capacity for GPU time only when the scheduler can actually place a partition there (sharing applies, the agent is at the level of item 5, and a partition backend is ready on the card, `planning.PartitionMayShareHeldCard`), since the partitions' time is charged to it. On a held card an operator has allowed work on, a whole-card deployment is still admitted against whole-card capacity (total memory × utilization) without the foreign memory taken off, and `no_fit` carries the foreign parameters only for a capacity that took them off.
2. **Headroom**: `estimate.ForeignHeadroomBytes` = 5% of the card, at least 4 GiB, the same shape as the host-memory headroom of an L1 sleep. What the outside processes hold is a reading taken once a minute, not a limit they keep to, and an out-of-memory failure costs both sides.
3. **Unknown means no sharing**: a process without a memory figure, a holder that is not a process (a card Kubernetes gave to another pod, which has no PID), or a list that cannot be read all count as unknown use, and the card stays refused.
4. **On a shared card the agent counts foreign processes by slots**: once a platform instance is on the card, the agent no longer examines it in full; but when the card is shared with processes it had found to be foreign, it still reads it every round. Each of the platform's engines keeps one process on a card (the sleep residue reading relies on the same rule), so as many processes as there are platform instances on the card are the platform's own. A process found to be foreign that is still in the list under its PID and process name stays foreign, reported with its current memory (with its last figure when the tool gives none this round); a process already taken for a platform engine stays the platform's; the other new processes first fill the slots of platform engines whose process is not known yet, and any beyond them are foreign—a job the outside user starts beside ours, or a workload the other orchestrator restarted under a new PID. When more new processes appear at once than there are free slots, the ones holding the most are counted foreign: overstating the outside use only refuses a placement, understating it runs a partition out of memory. A foreign process no longer in the list is not reported, but its memory is not offered at once: when no foreign process is left on the card, the card is still released only after 3 free readings in a row, so neither the gap of an exit or a restart under a new PID nor a PID-less entry carried over a reboot stays reported for as long as a platform instance is on the card. A card once shared is read this way for as long as the platform instances stay, so a foreign workload that comes back after being released is found again. When every platform instance on the card sleeps or has left, the card is examined in full again. A round whose probe or process list fails restates the last answer rather than clearing it. The foreign record is kept in the agent's state directory (`card-occupancy.json`) and survives an agent restart or upgrade (the processes taken for platform engines live only in memory and are taken again by slots after a restart); when the file was last written before the running boot started (`btime` in `/proc/stat`, and likewise when that cannot be read) the PIDs mean nothing, so they are dropped as it is read: those processes are matched against no live process, so a platform instance process that happens to get the same PID is not taken for a foreign one, and the card is read afresh by the rule above in the next round. The check uses only the file's existing modification time, and the file format is unchanged. It lives only on the agent and is not a new persisted fact on the server.
5. **Gated by agent capability**: sharing is open only to an agent that does item 4, judged from the node's already-reported `partition_safety_protocol` level, refreshed by every report: `proto.PartitionSafetyForeignTracked` (2) means the agent keeps reporting outside processes when a partition shares their card. It is the next level of the same partition safety contract (level 1 is native vdev ownership); a higher level includes the lower ones, and rolling an agent back revokes new sharing at the next report. Partitions already placed on a held card are not protected by that: the older agent stops reporting the card's outside processes, and the server then takes the card for free and places deployments against all of its memory. Before rolling an agent back below level 2, stop the partitions placed on held cards. No column is added.
6. **Sleep**: a wake onto a card held outside the platform is still refused; to be consistent, a deployment that sleeps is not placed on such a card either, refused with `held_outside_platform_sleep`, or once asleep it could never be woken there.
7. **Say why**: for a request that names its cards, the filters look only at the named cards, so a held card is reported as `gpus_held_outside_platform` rather than "no free GPU"; when memory is short, `no_fit` carries `foreign_bytes`/`foreign_gib` and the headroom parameters so the UI can explain the figures. Whether the card can be picked in the deploy form follows the server's per-card verdict for the current request (`gpu_candidates`); the frontend does not restate the rule.

## Trade-offs

- The agent still does not match processes to containers by cgroup: that needs PID-namespace handling per runtime and per vendor tool, and a wrong answer stops a card the platform is using. A shared card is read by the slot rule of one process per engine per card instead: an outside process that appears while a platform instance is on the card but before its engine's process is up takes that slot and is taken for the platform's; an engine that runs more than one process on a card has the extra ones counted as foreign, which admits less. Only cards that were shared with foreign processes are read this way; other cards of platform instances are still not examined.
- PID plus process name may take a new process of the same name for the original one when a PID is reused, and that new process's memory is then reported; within one boot this is rare, and across boots PIDs are no longer matched.
- After an outside process exits, the card keeps counting its last figure for 3 readings and only then offers it. A workload whose restart takes longer counts as free in between, and is counted foreign again as a new process when it comes back.
- The headroom is a fixed share rather than the outside processes' historical peak: a peak would need a new persisted fact, and 5%/4 GiB covers the reading fluctuation observed; an operator can still stop scheduling on the card.
- Nodes with an older agent cannot share until upgraded: better to ask for an agent upgrade than to take the card for free after the first placement.
- This ADR supersedes the former deferred item T68 in `known-issues.md` ("cards held by outside processes are only excluded whole").
