# Allocation rule coverage catalog

This is the authoritative rule-to-case map; the README describes the directory
layout and combination strategy. Each row states the claim being tested, its
owner and named executable evidence. A link to a package alone is not evidence.
The cases include both this central suite and existing focused tests; their
assertions are not copied into a second test just to move a directory.

## Scope and reading rules

The boundary is server-side allocation business behavior: request shape,
reported capabilities, eligibility, capacity and preferences, node/group choice,
claim accounting, admission/commit, quota changes, release and recovery. Model
memory estimation and vendor probes supply facts to this boundary; their
numeric estimator and CLI parser suites remain with their owners. Actual GPU
isolation, CUDA/NCCL correctness and driver enforcement require hardware tests
and are not claimed here.

A row means **the stated contract has an assertion**, not every possible value
or ordering is exhausted. The added combinations cover independent dimensions
where existing tests proved only one path. `TestCoverageCatalogReferences`
checks unique rule IDs, existing source paths and actual Go test functions. It
cannot judge whether an assertion is adequate; changes to a rule still require
reviewing its expected behavior and affected interaction rows.

## Limits and maintenance

The inventory now names evidence for each contract above. It is **not** a
proof of complete branch coverage, all hardware combinations or arbitrary
higher-order interleavings. In particular the 9-factor scheduler combination model
does not stand in for distributed/PD/runtime sequences: those have separate
rows, existing focused tests and the added critical matrices above.

When adding a dimension, update its owning rule and all interaction rows whose
outcome it can change. Keep at least one success and one refusal with unrelated
gates open. New production behavior needs a new row or an explicit extension
of an existing expectation; a passing reference check cannot do that reasoning.
Run the linked tests, not just the reference check. Renaming/removing a case
must update the catalog in the same change. Concurrency assertions specify the
ordering they exercise; no claim is made for unenumerated orderings.
